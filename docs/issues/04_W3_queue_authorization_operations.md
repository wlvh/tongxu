## 目标

在测试仓库完成 G1 接收闭环：接收席位与下一步、原 PR 发布与读回、目标推进占用、三种授权模式、合并请求与回执、未知恢复。这是 G1 唯一的发布里程碑。

阶段 G1。方案依据 §10、§11、§12、§13.5、§14、§19 W3。

## 前置

W1、W2 可用；受管写入口的授权与交接明确；Issue 00 的 D1、D2、D5 有结论。

## 范围

- 交付状态机按 §10 表：开发中、待接收、接收中、待修正／补证据、条件齐备待执行、合并请求中／回执未知、已合入指定目标；每个状态有责任人与退出条件。
- 接收席位上限为运行参数（默认两项实质接收、同一目标分支一个推进过程），等待依赖的任务不占席位，必要上游可提升顺序（§11）。
- 三种模式：只读／影子、逐次确认、有限委托。委托记录必须绑定 Issue 00 D1 列出的全部字段，范围外、已撤销或来源不明不发新动作（T15）。产品原型里"委托对任何 PR 放行"的行为不得带入。
- 逐次确认按 Issue 00 D5：owner 人类账号的 GitHub review approval 作为确认与审计线索；机器人身份执行合入；分支保护开启"新提交后撤销旧批准"。
- 合并请求使用 head SHA 条件；发出后主干前进时读回真实 merge commit 的树，与受测树不同则显示"已合入，证据待核"并暂停依赖该证据的推进，不伪称 base 原子锁，不自动回滚（T14）。
- Operation 先在本地事务登记再调用外部接口；响应丢失保留未知并查询原对象；重复事件合并到原操作；服务重启恢复原请求与占用（§14 表，T19）。
- `tongxu queue`、`tongxu receive`、`tongxu merge --authorization <已核验引用>`、`tongxu reconcile --operation <原请求>`；receive 与 merge 有显式写模式。

## 交付物

测试仓库完整接收闭环；已有有限委托不重批；无委托不执行；可退只读；丢回执可恢复。

## 非目标

不绕过分支规则，不复制额度，不把生产长期进程当可抢占资源，不实现通用审批 DSL。

## 验收入口

T07、T13–T21、T23、T24、T32（G1 部分）。

## 评审要求

- 关闭线程、CI 变绿、解除 Draft 都不单独清除未复核的阻断问题（T13）。
- 决定已确认、实施证据过期时只重验落实，不让 owner 重选（T24）。
- 生产试点先影子对照现有接收者；明确交接 main 写入责任后再接管，不能双开兜底合并过程（§19.2）。
