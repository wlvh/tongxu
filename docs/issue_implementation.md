# 从已审定 Issue 新建一次受控实现

本入口对应 [#74](https://github.com/wlvh/tongxu/issues/74) 的首次新建片段：已配置项目从固定提交 H0 开始，一名 Codex 实施者只修改获准的已有文件，运行已经登记的测试；成功后由宿主形成实际提交 H1，从原页面读回完整成果。登记、发送、修改、测试、提交、正式审核和用户接受是不同事实。

当前组件场景使用实际 Git、SQLite、HTTP、子进程和现有 Docker 测试镜像，模型为明确协议样例；正常入口的真实 Codex 演练仍需准确的原授权、资源及原生环境证据。本项不能据此标为全部 F10 完成，也不替代 #9 的本人接受。

## 正常页面怎么用

1. 启动正常工作台并选择已配置的 GitHub 项目。在项目页的“已审定 Issue 的受控实现”选择本次工作，核对采用的 Issue、目标、H0 和获准文件，点击“新建本次工作”。无需手写任务计划或挑内部运行脚本。
2. 页面先显示登记和准备。程序从 H0 的 Git 对象复制受管工作区，原来源的未提交内容不作为本次输入；不要求原仓库全局干净。随后沿原本人来源、实施/测试授权和资源消费者重核，条件不足显示等待原因，不把页面钥匙或模型文字当作许可。
3. 实际发送使用独立的 `implementer` 角色和一个新的、有界非持久上下文。普通消息仍只读；本路径不构造 finding，也不进入事实核实/影响核实的旧 repair 循环。模型只有原限定读文件、按预期摘要替换获准文件和运行已登记测试的工具，没有任意 shell、发布或合并工具。
4. 只有实际变更、实施者测试当前文件树、宿主再核注册测试及提交绑定均成立，才显示 H1。没有变更不制造提交。点击“查看原成果与全文”可读完整报告、diff、测试输出及测试树与 H1 的关系；实现完成尚待正式审核和后续交付。

同一启动请求重复进入沿原请求处理。队列席位占用等原因留下“已登记，待补准备”时，页面保留具体原因；条件恢复后点击“继续原请求”，程序核原任务、要求和准备文件，补完原绑定再首次发送。刷新或冷重开仍使用原 ID 和材料，不另建任务。相同请求 ID 更换 Issue 或固定内容会拒绝，Issue 编号本身不是永久任务唯一键；已有任务仍从原入口处理，不承担自动匹配、归并或多任务编排。

如果最终来源检查暂不可用，操作可能只保存了原输入而尚未派发。这类现场只能在原控制器锁内核实：没有派发事件、原操作只有完整输入清单/初始文件树和空的首次尝试目录，当前文件与暂存内容仍是 H0，且没有其他写者占用。满足条件后，“继续原请求”消费原输入完成首次发送，并查回原资源领取；不删除或重写原件。输入损坏、存在原生启动/工具/写入记录、占用或资源未知时继续等待核实。已发送、结果未知或已完成的请求只查原执行和成果，不换编号重发。

## 停止、失败与原件

“撤回未发请求”只适用于尚未登记实际派发的请求，取消与派发在原队列事务中互斥。已有资源领取沿原提供者记录实际取消结果，不推算退款。“停止本次实施”直接保存停止意图，不等待秘书或再调用模型；之后的工具写入、测试启动和宿主提交仍须通过原门禁。

已发生修改不删除。失败或未知时可以查看保留现场的只读 diff，但它明确只是当前观察，不是完整原报告、已结束证明或成功 H1。原输入、捕获、错误、工作区和占用保留；本版不自动接续失败现场、迁移未提交工作或恢复原生会话。完整成果读取会核原始捕获和原输入绑定，损坏原件不能继续显示为完整成功。

合法连续写入更新原工具持有的预期文件树，外部未登记变化仍拒绝。原授权撤销、资源未知、停止或来源不再是采用的 Issue 版本，都阻止新副作用。旧记录保留旧归属，不把新材料换进已固定请求。

## 安装者固定什么

`WorkbenchPlan.issueImplementation` 指向已有私人配置文件及摘要；仅配置项目浏览器入口可以使用本功能。配置文件的 kind 为 `tongxu-issue-implementation-catalog`、schemaVersion 为 1，entries 按准确仓库选择。工作台即使没有已登记开发任务，也可以由安装者配置一个已有队列、已采用范围及该入口；不以制造 PR 或假 finding 初始化。

每项配置固定项目仓库、原队列 `store`、私有执行根目录 `root`、Git 对象来源 `objects`、H0/base/target、原 `QueueContext`、执行配置路径/摘要、获准/材料/受保护路径、注册测试计划路径/摘要、已审定 Issue 的编号/完整正文摘要/审定出处/本次目标和验收说明、已有实施与测试授权引用、原资源预算、实际执行种类和独立的 `demonstrationFixture` 来源标记。真实模型可以处理演练源项目，不能把模型协议样例和来源是否为演练混为一项。浏览器只能选择已配置选项和提供稳定请求 ID，不能提交路径、命令、角色、权限或替换测试计划。

授权引用使用现有本人来源和已获准的范围，例如同一合法委托可以覆盖实施和测试。缺少这类准确依据时，本入口等待；它不会为新请求生成批准、代签本人或放宽原角色规则。资源仍在原账本中领取、查回和记录结果，没有另建余额。配置、Issue 或注册测试变更，需要明确采用后重新准备；不静默更新原请求。

执行配置沿已有 Codex、Node、禁用 MCP、允许指令来源、现有订阅内用量依据和超时字段。当前仅支持 Codex 实施者；保存其他角色的模型偏好不会把它换成未适配的程序。真实原生启动仍由实际程序能力、订阅与用量检查决定，不设永久版本白名单，也不改用 API 或额外计费。

## 首条演练和验证

#74 的基线先具备 `normalizeLabel(value)` 去空格和空标签默认 `Untitled`，本次增加可选回退名称。H0 包含可信准备步骤固定的默认行为及新 `Draft` 回退验收，测试文件只读。实施者不能改变测试命令、测试判定器或权限规则。注册测试使用现有版本 2 Docker executor；macOS 协议测试不能代替真实隔离。

`tests/project-repair/integration.test.ts` 复用原项目/原生协议/Docker准备方式，新增无 finding 的实施消费者，以及正常 HTTP 入口、准确授权和资源、H1/全文、重复/重开、未发取消、来源改变、撤权、停止、发送未知和保留差异的组合场景。`tests/w7/github-projects-ui.test.ts` 执行实际页面脚本，检查双击只产生一个准备请求及切换项目不启动后继；真实浏览器和真实模型另留证。

#71 的成功后补充接续消费本项已结束责任、H1 和完整原报告；它不反向成为首次实现的前置。#72 的正式 PR 流程、#73 的独立技术接收及 #10 的治理启用分别推进。
