## 02｜目标、边界与交付阶段

同序以交付为中心：Issue 定目标，PR／固定产物承担交接，接收者判断，程序连接事实、证据、责任和队列，原生 Codex／Claude Code 负责调查、编码和验证。它不重建编辑器、终端、聊天或全局主 Agent。

| 阶段 | 实际交付 | 完成边界 |
|---|---|---|
| G0 / W0 | 项目事实、政策、工具和材料基线；W1 Bridge 与可编码 Issue | 只读试点，不宣称执行器或写权已接通 |
| G1 / W1—W3 | 原 PR 交接、固定材料、已有检查、临时组合、责任队列与受管操作 | W3 是 G1 受管接收版发布点；此前可交付只读子版 |
| G2 / W4—W5 | 两引擎的审核／核实／修复结果自动转接 | 自动链内不再人工搬运报告；尚非完整运行中消息产品 |
| G3 / W6—W7 | 多任务分配、同／跨工具交接、实际消费、三视图 | 用真实协作验证，而非用 G2 的单 PR 成功代替 |

默认仍是 G1 先；W0 可用真实负担证据提出调整，不为重新讨论顺序而停工。原生接口只阻塞依赖它的 W4/W5，不阻塞 W0/W1。首个部署是单用户、单仓库、单台已验证主机，优先本地 Mac；远端已有交付可读取，不等于远端会话可控制。

最终覆盖三个顶层责任（两位 Codex、一位 Claude Code）及三种子任务安排；这是验收场景，不是生产数量限制。不做通用免审器、通用流程 DSL、跨主机调度、多用户多仓库、自动 rebase 作者分支、自动增加费用或第二套业务账本。集成分支与子 PR 都不强制。无条件自动合并不允许；有效有限委托内的技术合并允许，具体确认模式见 §12。

## 03｜依据与历史退出

原三视图、三种派发、未知不重派和固定产物保留。SEC_metrics 的接收角色、D02 对照工具等是试点线索，W0 必须按实际版本复核，不能把历史转述或候选 PR 写成当前上线事实。不把同一项目多份复盘当成独立统计实验，也不使用未经统计的 PR 数量推算收益。

D1/D2/D8 是落实已有正确性要求，不再要求 Owner 为缺陷逐项批准；D9 是可核查的接口条件；D3/D4 是工程边界；D5 的实际接入路径在 W3 Bridge 核验，不阻塞调查。D6 复用既有验收栏目，D7 已指定只读试点，D10 保持当前顺序。后续只有事实查清仍涉及目标、风险、费用、权限或失败语义的取舍才升级。

## 04｜权威、责任与记录落点

### 4.1 各自的权威范围

Issue 保存目标、采用范围、验收与正式决定；原 PR 保存本次交付叙事和接收／退回；项目索引仅保存授权入口、角色与跨任务等待；GitHub 提供远端对象与结果；执行器提供本次运行事件；原项目账本提供资源事实；平台只保存采用引用、观测、队列、请求与恢复位置。无 PR 的输入包在原 Issue／已有产物入口交接，之后引用而不复制成第二份状态。

### 4.2 下一步交接责任

每项未结束交付能回答：谁、做什么、针对哪份候选、缺什么、完成后交给谁。验证可以并行，收齐结果的责任不能悬空。角色持续不要求会话常驻；独立审核不得继承作者工作对话。失联不取消原写入责任，空闲不意味着业务完成。没有专职接收角色的项目由现有角色承担判断，不因此新增永久岗位。

### 4.3 不与作者争写 PR 正文（D4）

作者／唯一发布者维护叙事与 Review / Fix Record。程序不再循环重写 PR 正文状态区块；机器结果优先通过独立 **check run** 及固定报告入口发布，明确包含候选、base、范围和材料，而非只挂 head 就算完整绑定。W3 核验实际身份、Checks 权限、同 head 多候选与陈旧结果处理；check run 的绿色状态不能独自成为当前接收证明。

W1 只生成与发布后端无关的结果包，不需要先配置 Checks 写权。若所选身份无法发布 check run，保留可读取的报告包；W3 Bridge 可明确选择 commit status 加固定详情入口，但不能静默切换、同时维护两套同义状态，或为了发布而擅自增加权限。不要求先修改上游 coding-workflow。

正式交接仍在原 PR。写入允许的叙事前重读，保留人工编辑并读回；发生并发变化不覆盖整篇。发布失败显示待发布，不把本地文件当远端事实。重读不冒充远端原子锁。

## 05｜共同验收前移（D6）

跨 Agent、共享入口、持久化／复用和旧状态兼容任务，在 **Issue Agent 的 Acceptance Checklist** 内扩展共同验收，不再新增平行文档或普遍开工审批。开发者先写证明，接收者补消费者、反例和组合。

```text
共同交付：用户从哪个入口得到什么结果或准确限制。
分工：谁实现提供方，谁验证消费者，谁确认真实组合。
共同约定：输入输出、单位／期间／来源、错误含义、旧结果处理。
材料：固定位置与身份；各方可取得，缺失直接说明。
验证：复用哪个实际入口；正常与失败场景；谁维护和执行。
预期差异：哪些应改变、哪些必须保留；其余变化怎样解释。
交付出口：哪些可安全先合，什么满足后共同目标才完成。
```

先走通最短真实路径，再扩展覆盖。共同样例不是最终对接证明，必须替换为真实实现与消费。接口、失败含义、保存／复用条件变化或实质新反例出现时，仅重核受影响部分。旧成功可能错误，新拒绝可能正确；比较状态、内容、身份和来源，不制定普遍的“成功只能增加”规则。

## 06｜两类交接，不重复抄事实

提交／返修说明实际改变与非目标、程序固定的候选、命令与预期、原始证据、作者自测／消费者复验／独立审核的区别、上轮反馈处理、旧证据复用理由和剩余限制。

接收／退回说明受审对象、接受范围、已核对项、仍失败命题与触发后果、可复现证据、有限通过条件、下一步责任和只被阻止的范围。非阻断建议独立列出。不能通过不断追加顺便修改让交付没有终点。

同类缺陷反复出现时按共同机制和既有契约修复，覆盖当前输入边界的变体；可枚举则解释为何封闭，不要求证明一切未来自然语言。第一次看见根因即可处理，不为计数等第二次。历史 PR 不因新模板一律倒退；字段齐全只证明未漏填，不证明内容正确。

## 07｜机械检查与判断

程序可确定实际 refs、路径重叠、对象身份、命令退出、工具输出位置、已登记依赖命中和授权字段匹配。目标不符、缺页、候选混用、越权可以阻断。完整消费者范围、财务含义、测试充分性与合理拒绝仍需判断。

文件交集／import 闭包／复用指纹仅提供线索，不能证明清单外无影响；字段 `touches_shared=true` 不证明已查全。patch 相同不自动免审。廉价、关键、可执行事实尽量机械化，不把自然语言声明改成 JSON 后就叫事实机械化。

## 08｜候选、证据、base 与复用（D3）

### 8.1 固定候选

候选 C 保存 repo、PR、head H、实际目标 ref、观测 base B、merge base、可选受测树 T、采用范围 S、政策／提示版本及实际材料。代码与 diff 来自固定 Git 对象；Issue、PR body 和授权文字保存本轮读取快照及来源。H1 元信息和 H2 diff 不得拼成一个候选。

### 8.2 证据记录

证据注明候选／产物、工具版本、实际输入与样本覆盖、exact command 或人工步骤、环境、预期与实际、适用退出码、原始结果、验证者与独立性、限制和副作用。运行成功、比较完整、业务正确分别判断。输入拿不到、样本没执行或工具损坏必须显示缺口；不得填“无变化”。昂贵检查可按风险抽样或复用，写明依据与未覆盖项；新业务调用仍需独立授权。

### 8.3 原审核有效与当前可放行分开

原审核保留实际 H/B/目标/S、材料和覆盖；原始 patch 哈希仅辅助比较。组合检查绑定 H/B/T、输入、工具与环境。**当前接收判断** 引用当前候选及原审核，明确哪些旧证据复用、哪些重查。

base 前进后不立即重开全部审核；临近接收／合入时集中判断增量。原审核仍是历史事实，但单独重跑 CI 不自动恢复适用性。新 head、范围、目标、相关环境或新反例改变判断时重新核对。增量结论的 head/base/范围/原审核身份再次变化后不能继续使用。既不复制旧 PASS，也不要求重做仍成立的全部调查。

重复事件去重；同一 head 有新证据时允许合法重审。PR body 只追加本轮报告引用不使报告自我失效；实质改写测试主张或限制才重核相关内容。

## 09｜已有验收工具

只调用目标项目已有、已获准的命令入口，不复制业务实现或建立第二套准备器。固定代码、工具和输入，隔离现场，收集原始输出并呈现真实分类。D02 的 SAME_OK、CHANGED_OK、FAIL_TO_OK、OK_TO_FAIL、SAME_FAIL、CHANGED_FAIL、NOT_COMPARED 是一项项目适配，不强迫全部项目用它。

两边都成功还需比较内容；两边失败不算正确结果；新成功检查是否省略材料；新失败判断是否纠正旧错误。工具 COMPLETE／退出 0 不等于全业务通过。工具自身也须有漏样本、空样本、范围／出处丢失、工作进程失败和输入变化等负例；优先扩展已有测试。

## 10｜状态与下一步

运行状态（排队、运行、等待、完成、失败、未知）、审核结论（PASS／REWORK_REQUIRED／OWNER_DECISION_REQUIRED）和交付状态分别记录。无有效输出不是第四种 verdict。

| 交付状态 | 下一步责任 | 退出依据 |
|---|---|---|
| 开发中 | 实现者 | 固定交付及证据 |
| 待接收 | 接收角色 | 取得席位并接续 |
| 接收中 | 接收角色，可并行委派验证 | 有范围的接收／退回 |
| 待修正／补证据 | 被点名实现者或验证者 | 回应原失败及有限条件 |
| 条件齐备待执行 | 接收服务／角色 | 当前证据、GitHub 条件与授权 |
| 请求中／回执未知 | 原操作核查者 | 原远端结果，不盲重发 |
| 已合入指定目标 | 交付负责人 | 最终证据与用户验收；不自动业务采纳 |

已合入但树或目标不符／不可核查时附加“证据待核”，只暂停依赖这些证据的推进。状态恢复路径与拒绝路径同等重要。关闭线程、解除 Draft、CI 变绿不单独清除未复核的阻断问题。

## 11｜接收队列

默认主干严重问题优先，其次收尾已验证成果与退回项，必要上游可提升，其他按已批准优先级与等待处理。紧急插队短记原因；不打断长验证，不因积压冻结所有无关开发。

实质接收席位可配置，初始最多两项；等待依赖不占实质席位。同一目标分支只由一个过程推进。按真实负担调整，不把示例数量当永久政策。不要让已阻塞下游永远挡住必要上游。

原生运行有事件流则用事件；GitHub 可用时增量事件优先、低频补查保底，没有已接通 webhook 时允许有界增量轮询，不先建公网 webhook 服务。显示来源时间、最后成功观测和覆盖；空队列不空转 Agent。超时触发核查，不等于同意或退出。

## 12｜授权、身份与资源

### 12.1 三种模式

只读／影子仅采集、验证建议和待发布包；逐次模式执行这次具体确认；有限委托在已核验范围内接续。默认不新增权限，已有有效委托不逐 PR 重批。代码合并不等于采纳、部署或新增调用。

### 12.2 委托按实际动作核对（D1）

委托含来源、角色、仓库／目标、动作、作用范围、必要门槛、资源上限、到期条件（可无固定到期）、撤销入口。每次新请求核对匹配和有效性，不用全局 `grantActive` 替代范围。撤销只阻止未发动作，已发先核查。决定有效但实施证据过期，只重验实施，不要求 Owner 再选。

### 12.3 确认来源、权限隔离（D5）

首版采用 A 档：防善意执行者漏步骤、错误对象、重复动作与顺手越权；不承诺抵御同权限主动恶意进程，不宣称全机锁。

**设计默认保留同序本人入口＋可恢复的正式记录**。写入上线前 W3 必须验证人的入口、凭据及原始确认来源与 Agent 调用分离；关键决定不能只靠私有库解释。机器人发布记录只是转录，不成为自证授权。实际请求绑定 repo/PR/H/目标/方法/S；必要时记录所见 base，不宣称远端原子锁。

GitHub review approval 作为项目可选确认来源，不是唯一入口。使用时核对批准者身份、PR 作者不能自批、stale approval 配置，以及目标／范围／方法等操作含义。不能把普通代码 approval 自动扩为所有操作。W3 Bridge 明确实现所选路径；来源未核实就关闭受影响写入口，不反向阻塞 W0/W1，不自动修改分支保护或迁移账号。

发布端可持有独立机器人／App 身份，但只暴露登记过的发布请求，不提供任意 GitHub URL 或 shell 代理。测试／执行器不携带人的批准或发布凭据。核对 gh、环境变量、credential helper、SSH agent 等常规路径；缺机器人凭据明确失败，不回落个人身份。仓库历史身份不被本次文档自动认证。

### 12.4 原账本唯一

预算、预留、认领和未知处理沿用项目原账本；平台不复制余额或因换会话重新分配。任务授权、执行凭据和成功调用分别核查，未知机会不自动恢复。SEC_metrics 的具体额度与候选实现不写入同序核心，也不据旧 PR 说明认定当前已可调用。

## 13｜分支、组合与合并

### 13.1 关系分开

父子关系、实现依赖、合入前置各有意义。数据依赖不变代码依赖。能独立安全合入则默认直接 PR；必须共同启用或需隔离组合时使用集成分支。任务、会话、PR 不强制一对一。可先增兼容能力再启用消费者，但默认关闭开关不自动证明旧路径无影响。

### 13.2 真实目标同屏

显示实际 base ref、采用目标、最终出口、实际带入提交。合法叠放不是错误，与采用安排不一致才拒绝。不能按标题猜关系或用“已声明叠放”替代真实目标校验。

### 13.3 临时组合

固定 B/H，在隔离现场用已验证 Git 能力构造 T 并执行检查，记录方法、Git／工具版本与输入。`merge-tree --write-tree` 可写对象库，不能声称无任何副作用；冲突退出交回负责人。不得修改作者分支、工作区、index 或自动 rebase/cherry-pick/push。测试环境清理范围明确，不携带发布凭据。仅 `read-tree` 得到的工作树与 HEAD 可能不同；检查会读取 Git HEAD 时须建立正确的候选提交或如实限定证据，不能把目录内容等同提交身份。

### 13.4 复用与组合判断

子 PR 的局部证据可复用，但不能仅凭 diff 并集或无冲突确认父目标。检查接口、共享状态、依赖、消费者及预期失败路径。当前判断可沿差异缩小调查，仍覆盖正式范围；交集只是调查入口，不是只能检查那几行。

### 13.5 请求、回读与恢复（D2/D9）

发送前核对 H/目标/S、必要检查、开放问题、实际权限与确认／委托；使用服务端支持的 head sha 条件。不把发送前重读说成同时锁住 base/目标。受理、队列中不等于已合入，不允许一次确认隐式带入其他未授权工作项。

读回实际 merge commit、目标和树，与受测对象比较。相同只证明代码内容；不符或缺失显示“已合入，证据待核”，保留远端事实与原证据，不自动回滚、不重新合并。对实际合入树取得必要验证后可恢复；错误目标不能靠补测试追认，需要明确处置。迟到历史回执不能把最新远端分支缓存倒退。

GitHub 原生 merge queue 的账户与仓库条件须核对。当前个人账号下 tongxu 不以该能力为前置，不为此迁移仓库或购套餐；支持的目标项目另核配置与 merge_group CI。普通接口仍可按已验证路径使用，明确剩余竞态。[O1]

## 14｜可靠操作与故障恢复

操作先落库，再发外部请求；无跨 SQLite/GitHub 的 exactly-once 承诺。同请求去重，未知查询原对象，页面刷新不修改真实任务。数据库唯一约束与事务保护受管写入口，非前端按钮。

| 情况 | 行为 |
|---|---|
| 读取中断／缺页 | 保留覆盖缺口，不断言不存在 |
| 已发但无回执 | 原请求标未知，不重发副作用 |
| 远端成功、本地中断 | 回读恢复原记录，不再执行 |
| 审核晚到 | 归档旧候选，不覆盖新状态 |
| 批准等待／主进程退出 | 核查原等待与后台副作用，不自动释放写责任 |
| 会话明确退出 | 核对工作区、未提交内容、原操作和远端后移交 |
| 新证据改变旧结论 | 只重核受影响交付，无关工作继续 |

撤销、超时或心跳丢失不抹去已发动作，也不自动抢占现场。主干推进、工作区、源分支发布责任分别协调。

## 15｜最小架构与命令

默认 TypeScript＋受支持 Node LTS＋SQLite，一个本地核心；W0 根据已有条件固定版本。G1 先 CLI／已有 GitHub 页面／导出，G2/G3 复用同一核心加执行器和 UI，不建第二状态机。

模块为 core（候选、占用、状态与下一步）、github（采集和受限发布）、evidence（注册检查调用）、store（持久化与恢复）、adapters（后续两引擎）、web（派生界面）、tests。具体路径由 Bridge 决定，不假称当前已有应用源码。

运行库、原始事件、固定材料、临时 PR body 在目标业务仓库外；正式证据按项目政策归档并可由接收者访问。关键接收依据与授权有正式引用，平台退出后仍可接手。不长期镜像全部聊天。

命令按参数数组调用登记入口，不执行模型文本拼接的 shell。凭据不进 HTML／日志。loopback 不等于权限隔离；Host/Origin、CSRF、人的会话和 Agent 入口需明确。外部 HTML／消息视为不可信，在无控制权限的隔离视图呈现。报告不能借同源读取 token 或调用控制 API。

## 16｜G2 审核循环

先核对目标政策并固定采用流程，不强迫每个项目新增三个签字。采用 coding-workflow@1772cd2c 时：新独立 Codex 正式审核；有需核实 finding 时，新 Codex 查事实／复现、新 Claude Code 查影响与最小修复；Codex 综合；授权后在 Codex 验证会话修复；新独立上下文再审。独立性不只看线程名，要核对作者对话、自动记忆和隐藏状态，必要政策不因隔离被删。

结果转接是 X 明确完成→固定最终结果→填入 Y→启动 Y；运行中投递另在 G3 实现。保留完整报告，最小结构化结果只绑定对象与 verdict；中间 PASS、子代理输出、无效 JSON 或对象不符不触发副作用。有界格式补正不重新执行有副作用任务。

默认先综合再确认修复；明确授予本轮范围内自动修复时不重复请示。只读转修复须实移写责任，旧写入者未知不接管。核实证明 finding 错误，提供反证重审同 H，不造空提交。

讨论分歧最多三轮交换证据；返工计数只计已执行并发布的修复批次，两种计数不混用。超过三次实际修复生成网页端 GPT 简化反思待办，不继续无限开会话。配额／预算／运行界限到达时保留恢复点，不自动改变费用路径。

## 17｜G3 派发与通信

### 17.1 三种安排

同工具新会话、另一工具新会话、并入负责人待办。并入允许后续顺序 Run，不增加竞争写入进程。派发前核对已存在工作与证据；任务、规范化机器＋工作区、源分支发布责任在后端事务取得占用。路径责任事前明确，共享文件串行协调；路径不重叠不证明语义安全。

### 17.2 能力逐操作开放（D8）

准确定位、启动、指定接续、事件／结果、原生批准、投递和中断分别验证。创建回执不是全能证明；握手只授予 **已验证的该版本能力与本次身份／状态实际支持的交集**，无证据不开放。已有版本验证可复用，不每会话重做全部探针。未知不启动替身，已有长期会话先关联观察。

Codex 非交互／App Server 与 Claude 非交互输出／原生消息入口是 W4 候选路径；参数、版本、认证与费用以实际安装帮助、固定源码及官方文档验证。错误轮次不得降级成 turn/start；平台若是批准客户端就必须接住批准或明确停等。CLI 最终文字、轮次结束、子任务结束、进程退出分别判断。不预设订阅可被所有 SDK 产品使用。

### 17.3 消息与产物

逻辑工作项→责任角色→本次准确会话／机器／入口。发送者从真实连接取得；未知旧消息不随角色更换偷偷重定向。正常讨论不改变采用范围，正式变化回到 Issue。无实质变化不发“收到”或多处粘贴报告。

消息：待投递／发送／送达／暂存／拒绝／未知／回复。socket 连通不算送达，送达不算消费。产物：已登记→匹配版本已读→实际消费入口已验证。版本改变重新核对；不可访问的私有路径不能叫可交付。回查成功同步原消息和原 Operation，不新造成功记录。单机固定包和可访问 GitHub 引用足够，不新建对象存储。

## 18｜最终 UI 与外部步骤

最终三个主视图为项目总览、任务／会话／PR、通信与交付；不是方案阅读器。首页回答可用成果、缺口、等待、证据、实际目标和需人事项。任务树、会话状态、代码交付状态分开。PR 右侧抽屉显示当前候选、下一步、原始证据、授权和原请求，七格只是证据导航，不每格一 Agent。

委托 UI 显示实际覆盖而非全局开关；合入异常有“已合入、证据待核”及补证据恢复；新会话只显示有证据的操作。本人可在同序处理选择，不默认被迫跳到 GitHub 自批。重要记录仍可恢复。

网页端 GPT 的技术解读、多次返工简化反思及用户验收计划合意作为外部步骤，准备固定材料、登记输出与适用版本，不替换执行者，不造报告模型。新候选下报告归历史；reject/request_evidence 不变完成。组合验收前置不冒充合并后用户验收；可核对复用不受影响的证据。

当前单文件 UI 由 `prototypes/build_product_ui.py` 从冻结视觉模板确定性生成。无运行时补丁加载、无外部依赖。该生成器仅维护原型，W7 使用真实同源状态界面时退役；冻结旧 HTML 不再作为当前产品入口。

## 20｜完成与收益

G1 允许既有 Agent 仍手工接任务，但交接事实、责任、可重跑证据和受管操作成立；读写未获授权时只可称只读子版。G2 自动链内的结果搬运、重复填写已知 ID、平台引起的同一决定二次确认应为零。G3 再证明真实多任务协作，不以单 PR 通过替代。

观察首次有效反馈时间、有效通过至合入等待、退回原因／同类返工、合入后严重遗漏、人的机械操作和必要决定、新增维护。区分处理与等待，注明工作时段／观测缺口；没有运行事件不能把没有 commit 等于等待。一批试用不证明长期节省率。

观察覆盖、重算、代码合入、有效业务结果和正式采纳分别报告，不混成无分母完成率。只有更早发现问题、等待减少、严重遗漏不增、维护收益为正共同出现才证明改进。

## 21｜验收与证据

现行 **T01—T32** 逐项操作／预期保存在 `acceptance/T01-T32.json`；这是覆盖清单，不是已通过记录，不等于 32 套测试框架。旧 A 项保护的行为继续由 T 项承担。缺失或失败不能靠写“不适用”绕过；可选能力剔除时对外承诺也同步缩小。

逻辑契约、本地组合、真实接口、用户路径四层分开。每项记录同序与引擎／工具版本、候选和材料、授权、session/turn/request（适用时）、exact command 或步骤、实际结果、原始证据、限制与清理。截图只证明显示。优先复用和参数化扩展，必要真实组合不能被 helper 全绿代替。

已知七类旧缺口继续回归：拒绝验收不变完成、报告不过度沿用、真实修复批次计数、原消息和原操作一致恢复、决定实施可以重验、分操作能力开放、工作区双写拒绝。新增落实：D1 多维委托，D2 实际树核对及恢复，D3 当前 base 增量判定和迟到拒绝，D5 确认非 GitHub 唯一路径。产品原型断言通过不算 G1/G2/G3 完成。

## 22｜现场验收

G1：授权测试仓库准备独立、合法叠放和共享路径 PR；只读导入，核对真实目标与下一步；模拟席位竞争／依赖提升；跑已有工具，缺材料明确失败；构造 B＋H，不动作者分支；分别验证只读、逐次、有限委托、撤销、范围外和丢回执。检查最终树；生产故障注入禁止。

G2：真实可复现缺陷经采用流程审核、核实、综合、修复、再审；准确候选且无需人工转发报告。可控响应再覆盖错误 finding、同 head 新证据、Owner 待决、无效最终输出和配额停止，明确与真实发现分开。

G3：三责任和三种派发、固定产物跨工具实际消费、仅相关范围阻塞、直接与必要集成路径、退出会话后的安全接手。共同目标不因子 PR 全合自动关闭。

最终未参与实现者只看 UI 回答：什么可用、什么缺失、谁等谁、哪个证据适用何版、实际进入哪里、需要我决定什么。后台正确但 UI 误导仍失败；功能可用却维护吞掉收益仍需调整。

### 23.2 Issue 发布规则

指定一个执笔者：先读当前 GitHub 正文与新评论→处理有效决定并更新 `docs/issues/`→按授权发布对应 Issue→读回核对。讨论可以在评论，最终实施条件必须归并正文。文件／远端不同步时显示差异，只暂停依赖不明条件的编码，不自动用旧文件覆盖新决定。无需增加长期同步服务；当前任务只发布一次核验一次。验收表、JSON 或原型受实质影响的对应内容同时更新，历史快照不追改。

### 23.3 编码与审核包

每个可编码 Issue 必须自足：Why、范围／非目标、契约／SU、Bridge、代码触点预测、文档／测试影响、验收、风险与 Owner 边界。作者交实际 diff、测试范围／环境／限制、Review/Fix Record；独立 reviewer 沿输入→授权→固定对象→真实接口→状态→回读→恢复验证。未核实重大命题不得 PASS，P0/P1 必须有触发后果与证据。测试数、语法通过或作者主张都不自动升级为真实全链验收。

### 23.4 入口

当前仓库没有 `tongxu inspect/collect/verify/merge` 应用；这些是后续 Issue 的待实现命令，不可在 W0 声称可运行。当前可运行入口为原型构建、Node 局部断言和仓库已有 Git 实验，见 README 与 verification 说明。正式应用命令在真实 TESTING 入口统一维护，不复制多份命令。

## 24｜退出、来源与本次范围

接口不可用只关闭对应能力；状态缺陷先复现再最小修复；业务取舍归原 Issue，无关任务继续。运行中断保留原记录，升级前停止新派发、备份数据库与证据引用；迁移失败不清空、不重派，可退只读。关键结论与下一步具有正式引用，平台停止也能接手。维护成本高于收益时停止扩展，保留已验证有用的交付层。
