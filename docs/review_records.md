# 原队列退回接修复、判断反馈与按需复盘

本条接续原 #7，固定前置 PR27 `ee09b135fc02d3357fdf16f46e432be9f6f423bf`，分支 `feat/w5-review-records`，真实目标 `feat/w5-project-repair`。来源为本人持续 goal，不新增授权、费用或宏观产品版本。实现、夹具、真实原生结果和全量 Issue 验收分别记录。

RF01 原队列中准确候选、范围 S、执行安排 r、packet 和原独立接收判断必须仍可核。仅完整 `RETURN_FOR_WORK` 可进入修复；`INSUFFICIENT_EVIDENCE` 走原补充材料路径，未知或已放行不制造返工。程序重新读取原捕获，将完整报告及 finding 作为数据装配给原受控修复器。负责人另行固定工作区、允许路径、测试和既有授权；模型报告不能产生这些权限。

RF02 复用原 QueueStore 的 operation、claim、events 和 blobs。修复是该接收 operation 的后续阶段，不建立第二队列/余额。固定 sole executionRoot/operation，进入前登记请求和输入，保留原判断；已有原执行时只能检查/恢复原件，不能换根或未知重派。活动或未知写者占用原 claim，明确停止/候选变化在新投入与写入前检查。旧队列客户端必须拒绝有新阶段的存储格式。

RF03 复用已交付工程修复执行器、原官方认证/订阅和工具门。修复结果由原 terminal-record、源码、工具收据和完整模型捕获重验，再回写同一 operation。若中断只恢复已结束原执行；部分修改和原失败不清空。缺授权、未准备完或未知现场仅阻断该动作。明确撤销保留已发生结果；不以释放 claim 替代核实子执行已结束。

RF04 分开记录证据交流、模型调用/恢复尝试、写权交接、实际文件修改、新候选和实际发布的返工批次。现有三次写入尝试上限是资源/权限边界，不叫三个已发布返工。发布批次只从原发布读回、匹配新 H 的接收记录与原修复关系取得；重复读回、重传、没有代码变化不计新批次。超过三批时在同一事件记录中创建有来源的既定简化反思待办，含原问题/反例/负责人回应入口；不自动启动新的网页模型或增加额度。

RF05 判断反馈绑定原判断 ID、候选、任务和风险类别、覆盖窗口、模型/提示/工具版本与原证据。后续观察、反证、新需求、后续代码、归因争议和未观察分别保存，不改旧判断、不把“没人报错”当正确。正常放行与异常均可被固定选中核查；技术复盘先有负责人回应记录，再作评价。无小样本排行榜，不从反馈扩大权限。

RF06 按需整体复盘复用独立 reviewer，无常驻角色。可信输入固定触发事件和四类材料：上一批已接受目标/规则/能力的原出处、累计变化、当前行为、当前文档。技术记录不是本人采用凭证；缺真实已接受基线就明示缺口且不宣布无漂移。程序固定材料 hash、候选、提示和报告，保存一次真实提交/回读或明确未运行状态；重复入口不重新发同一任务。已有准入与费用条件保持。

RF07 验收用明确夹具覆盖：退回到真实文件修复器的程序装配、候选/判断/范围不匹配、并发与未知占用、暂停/撤销、准备和捕获中断、同 operation 恢复、原判定不被覆盖；不同计数、发布重传去重、四批触发一次反思、正常/异常抽样、争议和负责人回应、缺基线与材料变化。已有真实工程修复原件只按准确范围复用，不把夹具当新真实供应商调用。必要新模型验证须有具体接口差异才投入，不为了计数重复整条链。

RF08 本阶段不推送受管修复候选到原作者分支、不批准/合并/部署/改保护、不增加付费渠道或操作 SEC_metrics。实际采用和合入需要相应权限；软件接口与拒绝/恢复路径继续自主完成。此交付后继续原 #5/#6/#8/#9 的剩余前置，不能据此声明全部 Issues 或完整 G2 已通过。

## 入口与当前边界

先在无活动/未知 operation 的原队列运行 `node dist/src/review-records-cli.js enable --store ABS`。这是显式启用存储格式 8，保留原表/字节/事件和既有补充、双任务保护；旧客户端会拒绝此格式。`status --store ABS` 读取判断与后果，原 `queue-cli status` 继续显示接收与修复的完整历史。

`repair --plan ABS [--reconcile-ended]` 的可信 plan 固定原 store、operation、packet、judgmentId、bindingHash、完整 context，以及工程请求和执行器配置的路径/hash。工程请求中的 findings 必须为空；由程序从原捕获装配，完整原报告随项目输入交付。新候选仍在独立受管副本，原 PR 和原作者工作区不被修改。错误或中断保留原 claim；明确结束恢复不换根、不重复替换已写文件。单独调用旧 `repair-cli` 无法绕开已绑定的队列控制。

`record --request ABS` 支持判断分类、后续证据、正常/异常取样、实际发布返工关联和既有简化反思结果的明确导入。反馈材料只作证据，未验证的说明不能变成新权限。反思按同一 PR 与准确范围的修复链计数，不把四个无关任务各自一次修复累加成“四次返工”。真正网页反思的运行、费用及本人采用另行核实；导入记录不会冒称程序发过网页请求。

`overall-prepare|overall-run|overall-reconcile --plan ABS` 按需比较四类固定材料，一次运行使用新的独立 reviewer，并将原输入/输出回存同一队列。当前可信采用身份接口尚在原 #5 的剩余范围，因此接受基线的输入状态仅支持 `missing` 或 `supplied_unverified`；两者都输出明确缺口和 `noOverallDriftEstablished=false`。这能执行技术对照，不能单靠计划中的一个布尔字段宣布“基线已采用”或“整体无漂移”。后续 G01 的真实采用记录接入前，这个边界保持。

开发验证使用 `TONGXU_TEST_DOCKER_CONFIG=ABS` 指定已有隔离配置；遗留跨平台测试以规范临时路径运行（Mac 可设置 `TMPDIR=/private/tmp`）。新测试的模型响应全部是明确 fixture；项目测试、Git 修改、队列事务和恢复实际执行。真实供应商工程链沿用 PR27 的原证据，不能把本套夹具算作新增真实模型验收。
