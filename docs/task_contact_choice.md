# 原任务角色提出有限联系请求

对应唯一当前余项 `completion-coverage.json.currentRemainder.items[F01]`（原T38，关联T28/T29/T35）。原 A 保持负责人，秘书不参与逐句转发。正常 f847 试用和已固定的原退回结果保持。

用户从已登记任务入口启动原 A。A 读取实际材料，需要联系时在完整回复中返回固定格式的联系请求及预登记 ID；无需联系时返回原格式的完整报告，后台不启动其他角色。后台核原最终捕获与任务材料，再沿原 TaskInbox 给准确 B 投递固定问题和 A 的完整原文；B 完整回复及消费确认返回后，程序交回原 A 综合。新会话如实记录，不把同一负责人写成同一原生会话。没有联系需要时不启动 B。

可信计划固定原 A、有限选项（最多8项）、每项 B 的任务/角色/执行程序/输入/授权和回 A 的请求。模型只选择 ID，不提供任务、路径、命令、新权限或收费渠道。整个计划摘要进入原 A 的固定输入，改选项或后续模板不能复用已登记 A 请求。原报告只是选择和证据，不是权限来源；实际发送继续核原候选、责任、停止、资源、认证用量和执行边界。

状态与全文从原 TaskInbox、消息计划、捕获、消费回执和资源结果重建；不另建发送账本。只有完成且已核原捕获的 A 回复可触发 B，只有 B 完整且资源结果已核才能回 A。已发未知不重发、不改收件人；关闭入口不启动下一阶段。重入先核同一原运行，保留全部失败、等待和部分结果。

联系选择使用现有只读角色的结构化报告通道，不新增 shell、网络、任意工具或通用调度。最初选择报告不是组织协调已完成的证明；需要协调反馈时，最终原 A 的完整反馈仍走原协调消费者。普通的固定 A→B→A 入口和旧捕获继续可用。

本轮验证以一次实际需要的联系和完整回读为主；另核不联系、未知选项/角色、旧候选、停止、重复/并发、已发未知和关闭后不派发。真实原生选择及回读与明确故障夹具分开。V01的在途写者/未提交共享工作证据按同一实际关系补齐，优先复用现有写责机制，不另写接管平台。本文是实现契约，不是验收通过。

初始请求保存明确的联系选择标记及整个计划摘要；有组织协调材料时，选择请求与最终协调反馈的输出契约分别说明。选择本身不记为共享部分通过；B与最终A的正常反馈仍由原协调消费者核验。页面启动前可展开查看固定联系项、实际工具/角色及问题；完整报告保留准确原run、会话、轮次、原文与消费关系。

## B 联系原 Issue 实施负责人 A

这是原 F11 的有限扩展，字母按工作责任区分：A 是已由 Issue 实施入口登记的写入负责人，B 是有自己固定调查材料的另一任务。B 先读自己的实际材料并提出问题；A 正在写入时只收件，不能启动另一个写者，也不能把尚未提交的做法称为接口确认。A 安全结束后，系统核对其原请求、完整捕获、资源结果、当前提交、文件与已采用需求，用新的只读上下文让同一逻辑负责人回答。完整答复再交给原 B 的后续输入。这里“同一逻辑负责人”指原任务责任与结果身份保持；前后原生会话不同，不冒充原会话恢复。

正常入口由安装者一次配置现有 `controls` 目录。联系计划使用 `schemaVersion: 2`，增加 `authorization: {coordinate: "已验证委托摘要"}`；原 B 的 `initial` 和每项 `request`、`followup` 各自固定独立的 `authorityIntent`、资源预算及原有费用证据。只有联系原实施者的选项增加 `originalImplementation: {source, requestId, task, operation, requestSha256}`，五项必须指向同一已登记原件。`request` 指向原 A，`followup` 返回原 B；不允许夹带会话续接或换成最新任务。旧 schema 1 计划和历史捕获继续按原方式读取。

工作台在所选项目中识别实施入口已登记的 A，只为有限联系扩充收件人识别。目录的初始 B、范围控制及其他消费者仍沿各自原配置；模型输出不能登记新任务。这个首条路径要求 B 的独立材料在期间保持有效。若 B 使用与 A 同一工作区，A 的提交使 B 原输入过期，应保留原记录并核对当前材料，不能默默换基准继续原问题。

A 的安全成功可以是实际 `completed` 的 H1，也可以是完整 `no_change` 且原树确实未变的 H0。后者没有新提交，不能造一个 H1 作为标记。H0 仍属于原操作时，原实施消费者明确准入只读消息资源阶段，保留原实施结果和 SQL 保护；每次只读输入仍通过原 MessageResources 独立申请和结算，不能复用 implement/test 的占用或额度。

同一服务中，原 A 完成会唤醒已经收件的准确联系，且不依赖秘书配置。A 结束时 B 尚在回答，系统等待该原动作结束后复核一次；没有待办的问题不会被启动。冷重开或读取报告新增输入为零；用户从原按钮明确“继续原联系”后才继续。重入使用同一请求和捕获，不重新发送 B 的已有问题。

页面分别说明“B 的问题已登记”“尚未交给 A”“A 的完整答复已交给原 B”。撤回只处理下一段已证明未发送的输入；已有捕获与资源结果保留。A 的原提交、暂存区、文件、写者占用、捕获、已采用需求或原结果身份变化时，旧报告仍可查看，但不能作为当前接口确认发送。停止、未结资源、失效费用证明、未知原执行或旧协调安排仍沿原检查等待，不借联系取得写入、测试、发布或合并权限。

已绑定但未提交输入的联系，恢复时仍读取当前原 Issue；程序在新消息资源准备、实际新领取及新输入发送前复核来源，同时保留本地原结果、文件、捕获与发送事务的同步检查。远端读取与本地事务不是跨系统原子快照。来源在领取前已失效时不新增输入或领取；若原领取完成后来源才变化，则阻止输入，保留该原领取，沿确证未发取消核清，不能改称没有发生过。已发送、送达或未知的原运行先重放原捕获并核原资源，来源后来变化不会阻止事实恢复；完整结果仍可读，但交给 B 的新输入继续受当前来源检查约束。

实现与组合证据在 `tests/project-repair/integration.test.ts` 的 original owner feedback 场景，以及原有限联系、消息和页面套件。组合中的 Git、SQLite、子进程和登记的 Docker 测试实际执行，模型和外部来源为明确样例；这不替代正常安装的真实模型路径或本人验收。
