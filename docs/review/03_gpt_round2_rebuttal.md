## 一、它补对了什么：这些应进入下一版方案

### 1. 网页端 GPT 的几个节点，应作为外部步骤接入，而不是悄悄换执行者

这一点我们已经基本一致。原工作流的合并后技术解读、用户验收计划合意，以及多次返工后的架构反思，都明确涉及网页端 GPT；不能因为平台先接了两种原生执行器，就默认改由它们代劳。

但不需要因此再建设"第三种完整执行器"。

**最小做法是让平台承认：有些步骤在外部完成。**它提供准确的 Issue、候选版本和提示入口，接收报告或正式记录的位置，并说明产物由谁、针对哪个版本、完成了什么判断。没有经过验证的自动接入，就显示外部待办，不假装已经自动执行。

这既保留你的原流程，也不要求你回到平台重新做一遍已经完成的判断。

同样，HTML 中简化的角色提示不能直接用于生产；不过，原型已经明确写了"简化模板，不冒称仓库提示原文"，所以这里属于**生产接入需要落实的要求**，而不是原型冒用了上游原文。tongxu_issue_workbench_complete…

### 2. "移交写入责任"必须是实际动作，不能只有一句提醒

Fable 对这一点的强调是对的。原工作流要求先在新的验证对话中调查，必要时再在 Codex 验证对话中修复；协作规则也要求只读调查需要修改时，显式移交写入责任。

关键不是多加一个"已移交"状态，而是把行为讲清：

```text
旧执行者结束本轮写入，并交代未提交内容和产物
    ↓
核对工作区、当前版本与实际运行状态
    ↓
新执行者接收明确范围，取得写入责任
    ↓
开始修复；旧执行者不再同时修改该现场
```

**旧执行者状态未知时，不能靠修改数据库里的负责人字段完成交接。**

这可以复用派发时的单写入保护，不需要另外发明"交接系统"。而且，用户已经明确要求按核实后的结论修复时，不应再机械地增加一次同义批准。

### 3. PR body 与 Review／Fix Record 确实需要进入合并准备核对

我上一轮没有专门检查现有的 merge-readiness 工作流，这是遗漏。

PR 模板第 6、7 节确实分别要求测试证据和 Review／Fix Record；它们不是装饰性说明，而是后续审核者理解当前交付、已处理问题和剩余限制的重要材料。

但接入现有工作流时，有一个比"增加一行条件"更重要的发现：

**现有工作流成功，不等于它的审核结论是 PASS。**

我执行了它的 `Validate generated report` 校验片段，结果是：

| 报告里的结论 | 校验步骤退出码 |
|---|---:|
| `PASS` | 0 |
| `WARN` | 0 |
| `BLOCKER` | 0 |
| 非法状态词 | 1 |

源码里的分支明确接受 `PASS|WARN|BLOCKER`，随后可以正常上传报告、发布评论。这个步骤检查的是**报告格式合法**，不是**允许合并**。

此外，它读取 PR 元信息、diff 和基于分支名的文档，并没有建立一套固定 head、固定 base、固定 PR body 的完整快照保证。因此，不能未经补充核对，就把某次绿色 workflow 映射成"当前候选已满足交付条件"。

我的修改建议是：

> **把现有报告作为可引用的审核材料，核对它的实际结论与适用范围；不要用运行成功代替语义通过，也不要默认把上游仓库的一项工作流变成所有目标项目的新强制门。**

## 二、最重要的分歧：审核不能只绑定 patch，但也不必每次从头重审

Fable 的问题意识是对的：**不能因为提交身份变化，就机械地重复全部调查。**

但"审核绑 patch、合并绑 head，两套键分开"还不够。它少考虑了：**同一份改动，在不同依赖和需求之下，可能不再正确。**

### 1. 先把 HTML 实际发生的事情说准

我重跑原 HTML 后看到的顺序是：

```text
兄弟 PR 合入目标分支
    ↓
本 PR 的 head 没变，原审核仍绑定这个 head
    ↓
base 新鲜度与 CI 条件失效
    ↓
执行"模拟更新 base"，生成新 head
    ↓
旧审核不再绑定新 head
```

所以，并不是"兄弟一合入，其他 PR 的审核马上全部失效"；失效先发生在 base／CI 条件，之后更新 head 才影响审核。对应代码确实如此。tongxu_issue_workbench_complete…tongxu_issue_workbench_complete…

如果每次合并后立即更新、重审所有剩余兄弟，确实会产生接近二次增长的重复工作；但这是**特定调度策略的最坏结果**，不是使用 head 绑定必然导致的结果。只在候选接近实际合并时刷新，就已经能避免一部分无效重做。

### 2. 我实际跑出的反例：patch 字节不变，行为仍然错了

这是人为构造的两模块例子，不是声称你的业务代码存在这个缺陷。

最初，数据源返回：

```python
{"amount": 100, "unit": "yuan"}
```

两个独立改动如下：

| 改动 | 修改文件 | 在原基线上的结果 |
|---|---|---|
| A：增加"收入，单位元"的业务导出字段，直接读取 `amount` | `exporter.py` | 导出 100 元，检查通过 |
| B：数据源改用"分"，同时正确标记单位 | `record.py` | 返回 10000 分，原通用导出也保留单位，检查通过 |

合并后，A 依然直接读取 `amount`，于是导出：

```python
{"revenue_yuan": 10000}
```

实际金额还是 100 元，但导出成了 10000 元。

实验同时确认：

**两个改动没有修改同一个文件；合并没有冲突；正反合并顺序得到同一棵代码树；集成 diff 恰好是两个子 diff 的拼接；A 在新旧基线上的 patch 原始字节与 SHA-256 完全相同。**

这不是哈希碰撞，也不依赖某种宽松归一化算法。即使采用精确字节哈希，结论仍然成立。

因此：

> **patch 相同，只证明"这份局部改动相同"；不能证明"支撑原审核的全部前提仍相同"。**

另外，实际实现若选择 `git patch-id --stable`，还要注意它会忽略 patch 内的空白。我也跑出了 `"a b"` 与 `"ab"` 的变更获得同一 patch ID 的例子。这是该具体算法的附加限制，不是说 Fable 已经指定使用它。[Git](https://git-scm.com/docs/git-patch-id)

### 3. 正确的简化，是复用调查，而不是自动复制 PASS

我建议保留这样的区别：

| 对象 | 应说明什么 |
|---|---|
| 原审核 | 审了哪份候选、依据哪版需求、覆盖什么范围 |
| 差异比较 | 代码、基础依赖或正式范围发生了什么变化 |
| 新候选复核 | 哪些原证据仍可用，哪些变化需要补查 |
| 合并确认 | 人实际确认的候选和目标是什么 |

这不要求新增一套复杂的哈希台账。已有审核记录中保存固定版本和范围；新候选出现时，把变化交给复核者即可。

例如，base 只新增与该调用链无关的文档，可以有根据地复用原调查；base 修改了被调用接口的金额单位，即使本 PR 的 patch 不变，也必须重新核对相关行为。**Issue 的正式目标变了、代码没变，同样不能自动沿用旧判断。**

仓库本身要求的是：审核绑定实际审阅内容，变化后复核受影响部分；同时，正式工作流要求对最新 exact head 执行审核。两者可以通过"针对当前候选作判断，复用仍有效的证据"共同满足，而不是二选一。

### 4. 集成审核也一样：可以缩小，但不能只剩"检查冲突提交"

Fable 已经保留了组合验收，这点应认可。上面的反例不证明所有集成都必须逐行全量重审；它证明的是：

> **"只有冲突解决提交需要新审核"这个边界不成立。无冲突的接口组合，也可能产生新问题。**

集成时可以复用各子 PR 已经完成的局部调查，重点检查接口衔接、共享状态、依赖版本、执行顺序和组合验收是否覆盖这些风险。最终仍应对集成候选给出独立判断。

**"检查两个模块能否正确配合"与"把两个模块各自再读一遍"不是同一种工作。**前者有必要，后者未必。

这也正是 `TESTING.md` 已有的区分：各层分别通过不能自动证明真实组合路径闭合。

## 三、"GitHub 账号证明本人确认"是这份反馈里最危险的假设

Fable 写道：

> "模型会话拿不到你的账号，自然冒充不了。"

**这个前提没有被证明，而且不能作为系统默认。**

GitHub CLI 可以使用环境中的 `GH_TOKEN`，也可以使用已经保存的登录凭据；个人访问令牌本来就是代表用户访问资源。一个能执行命令的 Agent，如果能够使用这些凭据，就可能以用户账号执行允许的写操作。这里不需要知道密码，也不需要突破 GitHub。[GitHub CLI](https://cli.github.com/manual/gh_help_environment)

因此必须区分：

> **这条记录通过了哪个账号的认证？**
> **这个具体取舍是否确实由人作出？**

前者不自动证明后者。

现有 merge-readiness 工作流里的 `author_association` 检查，用来限制哪些仓库相关账号可以触发任务；它接受 `OWNER`、`MEMBER` 和 `COLLABORATOR`。它不是"识别人类本人点击"的机制，也不是特定产品决定的授权证明。

**最小改法不是再给决定加一句固定格式，而是明确权限边界。**

执行者是否能使用你的 GitHub 写权限？能修改哪些工作项？能否改写批准依据？合并凭据由谁持有？原生会话中的用户确认有没有可靠的来源信息？这些必须按实际接入核实。

能区分人的确认和模型写入时，沿用原确认，不让你重复批准；区分不了时，就应显示"发现了一条账号记录，尚不能自动认定为本人授权"。

这也意味着我同意 Fable 补充启动权限配置，但还需要再往前一步：**沙箱模式、允许工具集和可用凭据应一起核查。**"不允许越权"的提示文字，不能替代实际边界。

不过，不能仅因这份产品类似"Studio"，就自动继承一个面向主动恶意执行者的完整安全工程范围。DEC-002 区分了防善意执行者误操作与同权限恶意对抗；首版应明确采用哪种威胁模型，而不是靠产品名称升级安全承诺。

## 四、长期会话和消息权威：风险真实，但它给出的解决方案过头了

### 1. 长期负责人不违背仓库规则，永久依赖其记忆才有问题

仓库不是"每一步都新开对话，让所有对话无状态"。

`AGENTS.md` 明确要求同一执行任务不重复派发，**增量优先交给原执行者**；另一方面，独立审阅不得继承作者工作对话，甚至提醒"新线程不等于隔离"。

所以，应该区分三件事：

**责任可以持续。**谁负责这个 Issue，不需要每轮重新发明。

**执行会话可以复用，也可以交接。**是否继续使用，取决于当前工作、上下文质量和执行状态。

**正式需求与决定不能只存在于会话记忆里。**换一个执行者后，应能从 Issue、固定产物和必要记录恢复工作。

原方案其实已经提出"长期任务、负责人角色和原生会话应当分开"。真正需要补实的是会话更换和责任交接，而不是把所有协调问题都交给新会话。粘贴的文本 (1)

"请解释已发布接口"可以交给一个只读新会话；"你当前正在写哪个文件、未提交的输出放在哪里"，则不能让另一个只读会话代替实际执行者回答。

**角色寻址与准确会话定位并不冲突：前者决定找谁负责，后者决定这一次消息实际送到哪里。**

### 2. 应拒绝未获批准的范围变更生效，而不是拒收相关讨论

"会改变范围的消息必须引用 Issue 修改，否则平台拒收"，这条规则太粗。

例如：

> "我发现还需要补一个离线运行场景，建议增加到验收范围，你怎么看？"

这是一条正常提议。它当然还没有对应的已批准 Issue 修改，否则就不需要讨论了。

正确的边界应该是：

> **消息可以讨论和建议变化；只有正式范围被有效确认并写回 Issue 后，执行者才能把它当作新的实施依据。**

普通消息不直接更新任务的"采用范围"，也不赋予额外权限。正式变化通知引用 Issue 中的决定；提议没有批准，就保持提议。

这样既守住 Issue 的唯一实施入口，也不需要平台先准确理解每一句自然语言，才能决定是否允许发送。原工作流要求聊天不另造一套实施权威，不等于禁止聊天讨论下一版契约。

### 3. "已验证"不能只靠命令、退出码、哈希三个字段

Fable 提议补这三个字段，方向是让证据更可核查，我赞成。但它们仍不充分：模型可以在文字里声称执行过这些命令；真实退出码为 0，也只证明那条命令成功，并不证明它检查了该检查的行为。

最小充分的证据应说明：

> 在哪个候选和环境中，通过哪个实际消费入口，检查了什么预期行为，得到什么结果，原始证据在哪里。

能从执行器直接读取的事实，不让模型自行填写代替；测试是否覆盖关键行为，仍需要判断。这与模板已有的 command、scope、result、environment 要求一致。

也不应强迫所有交付都具有命令退出码：人工体验验收、接口说明审核，可以有不同证据，但必须准确标明证明范围。

## 五、集成分支、路径所有权与合并接口，应按真实边界处理

### 集成分支改为可选，我继续支持

父子 Issue 表达目标拆分，不必自动决定代码分支结构。**能分别进入 main 且各自保持可用的子改动，通常没有必要再经过集成分支。**

只有多个改动必须共同存在才能交付，或者确实需要一个隔离的组合验收候选时，集成分支才有明确收益。这里我与 Fable 没有实质分歧；原方案的"有子任务默认有集成分支"应修改。粘贴的文本 (1)

但"集成 PR 的 diff 等于已审核子 diff 的并集"只能帮助确认有没有额外改动，不能独立证明组合正确，前面的实测已经说明。

### 路径所有权要补，但不要把它误当成全部并发安全

我复现了原型的缺口：在另一个受管会话已占用 `/demo/52` 的构造状态下，给未分配的 #52 派发任务，仍然会创建第二个指向同一路径的会话记录。

因此，Fable 关于**工作区维度的派发检查没有实现**是成立的。tongxu_issue_workbench_complete…

不过，"并入负责人会话只改了一行事件文字"不准确。原函数也更新了任务的 `owner`、`mode` 和负责人的 `tasks`，而且不新增会话；只是这些关联更新还不能证明真实原生待办已经执行。tongxu_issue_workbench_complete…

我会把两类问题分开处理：

**同一现场双写**，属于派发和写入责任问题，必须在启动前阻止。

**不同工作区修改重叠文件**，属于集成协调问题，按现有协作规则提前声明范围、安排共享文件的修改顺序，并在交付时核对。路径不重叠也不代表语义不冲突，刚才的两模块反例已经证明这一点。

不需要第一版建设实时"全仓库文件锁平台"；但也不能等 PR 出来后看一眼文件列表，就声称并行风险已经解决。

### GitHub 的 base 原子约束问题成立，但原方案文字已经承认了边界

我核对了当前 GitHub 文档：普通同步和异步 PR 合并接口提供的是 **head 必须匹配的 `sha` 条件**，没有对应的 `expected_base_sha` 参数。[GitHub Docs](https://docs.github.com/en/rest/pulls/pulls)

因此，HTML 中"在同一个回调里比较 head、target、base 后更新目标"的模拟，确实比真实跨系统调用更强。我上一轮肯定了这个模拟保护，却没有充分说明现实接口的差异，需要补上。

但文字方案本来已经写明：

> 发送前读取一次状态，不应被当成跨系统原子保证。粘贴的文本 (1)

下一版需要明确，用户确认的是"这个 head 合入这个目标，并遵守目标分支的实际规则"，还是"必须合入我刚才看到的精确 base"。后者不能仅靠普通 API 请求承诺。分支保护的最新状态要求、合并队列等服务端机制可以承担相应约束，但仍须核对实际配置，不能把"发请求前又查了一遍"包装成保证。[GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## 六、我会怎样修改实施顺序

**我接受"先做单 PR 审核循环"的建议，但不接受把跨工具通信的可行性验证完全后移。**

原因是：单 PR 循环已经需要 Codex 与 Claude Code 之间传递 findings、核实结果和综合分析。可以不做通用消息中心，却不能靠你人工搬运这些内容，再声称执行循环已自动接通。

### 第一阶段：验证最薄的真实接入

仍然验证准确会话定位、原生运行事件、批准处理、权限和停止／接续语义。再做一条最小的跨工具交接：固定输入送达正确对象，返回结果能够关联原任务。

不做消息中心、父子任务树或长期协调记录的完整产品化。

### 第二阶段：跑通一个现有 PR 的审核—验证—修复循环

这是本轮我对上一版方案最大的调整。

选一个已经存在、确实需要处理的 PR，跑通：

```text
固定候选的独立审核
    ↓
必要时，Codex／Claude Code 分别核实本批 findings
    ↓
综合分析；需要人取舍的事项停在实际影响处
    ↓
按已有授权移交写入责任并修复
    ↓
更新测试、文档、PR body 与 Review／Fix Record
    ↓
对新候选复核；复用仍有效的调查
```

平台承担的是开对会话、填对提示、传对版本、转交结果和检查真实回执，而不是替模型决定缺陷是否成立，也不是替你决定范围与合并。

这一阶段可以不做集成分支，不做通用通信界面，不做用量展示，不维护额外的 PR 镜像评论。**先证明它确实减少你今天反复做的机械操作。**

### 第三阶段：再扩展到多 Issue 协作

在前两步已经形成的任务、会话、操作和结果记录上，增加子任务派发、角色寻址、必要交接及可选集成拓扑，而不是另建一套平行调度器。

这里还应保留原方案真正的产品目标：减少寻找会话、转发接口、追问产物是否被消费、拼接多个任务进展的工作。**单 PR 循环成功，是阶段成果，不是"多 Issue 协作台已经成功"的替代证明。**粘贴的文本 (1)

至于规格表达，我赞成减少反复出现的"不做什么"，补清关键对象、动作、触发者与失败恢复。但不能把现有 HTML 状态机直接升格为正确规格——我们已经确认其中有状态不一致和缺失保护。代码可以帮助暴露规格问题，不应反过来让原型缺陷成为产品契约。

---

**最终对齐后的方向是：接受它的收缩顺序和补漏，但拒绝用机械相等替代语义判断，用账号身份替代人的授权，用新会话替代责任连续性。**

最值得采用的简化，不是删掉独立审核，而是**不重复调查已经成立的事实**；不是删掉协作，而是**先用一个真实 PR 证明调度有收益**；不是增加更多确认，而是**把原有确认的来源和作用范围接准**。

下一版应该因此更小，但不能因此更会"自动变绿"。
