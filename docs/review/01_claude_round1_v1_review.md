# 第一轮：Claude 对《同序 v1》的评审

来源：Claude Fable 5.1 在 2026-10-16 的回复原文。对照对象：coding-workflow@1772cd2c 全部工作流文档与 v1 HTML 原型脚本。

---

我把仓库里的工作流 README、decisions、五个 prompt、九份模板和根目录 CI 全读了一遍，也把 HTML 的全部脚本读完了。下面是对照后的看法。

**总体判断。** 方案里的约束清单大部分与仓库一致，我逐条对过原句。它真正新增的是一套仓库里不存在的拓扑：父子 Issue、集成分支、长期负责人会话、跨会话消息。我 grep 了整个仓库，集成分支、子 Issue、父 Issue 一个都没有。所以准确的说法不是"基于 README 扩展"，而是"把 README 第 7 到 13 步做成可并发的多实例，再在外面包一层从未被任何决策背书的协作模型"。这不是坏事，但那一层要按 DEC-008 的复杂度守恒自己证明价值。

## 一、对照仓库：忠实的部分和漂移的部分

忠实的部分不展开：三个审核出口、第 12 步暂停、决定三分法、审核绑定版本、单写入者、独立审核不继承作者对话、Draft 转 Ready 独立。这些都能在 README、decisions、PR 核对清单和 AGENTS 协作一节找到原句。

漂移有五处：

- **技术解读的归属写错了。** 仓库第 11 步明确由网页端 GPT 的 apps 功能生成总结，存档在 PR 评论区。第 13 步验收计划要 GPT 网页版和 Claude Code 合意，第 10.9 返工超三次也是去 GPT 对话。方案和 HTML 都写成"原生负责人或原生执行器生成"。这不只是措辞问题。平台只建了两种执行器适配，而你流程里三个关键思考节点都在第三个没有 API 的工具上。要么把这些步骤定义成只认链接的外部产物登记，要么承认执行器模型覆盖不了它们。
- **七格流程条是方案自己压缩出来的。** 它对应第 7、8、9、10、合并、11、13 步，README 里没有"七格"。可以用，但要标成派生视图，否则 README 改了流程条不会跟。
- **修复的写入权转移没有建模。** 仓库 10.6 规定修复在 Codex 验证对话里做，而那个对话是以"先不动代码"的只读身份启动的。方案第十节提了一句"先移交写入责任"，HTML 里完全没有。这是单写入者保护在你自己流程中最容易破的点。
- **你仓库已有的 merge-readiness CI 被忽略了。** 根目录 `.github/workflows/claude-merge-readiness.yml` 由评论触发，输出 PR 叙事、测试证据、文档闭合、可操作性四维的结论。方案"第一层工作流条件"六项没有一项关于 PR body 证据，而 PR 模板第 6、7 节恰恰是你最在意的东西。至少加一行条件：Review / Fix Record 对应当前 head。
- **HTML 里的角色 prompt 是改写版。** 不是 prompts 目录的原文。方案说"不静默追随上游提示变化"是对的，但起点应该是原文加版本号。

## 二、HTML 真正实现了什么

它确实把几条不变量写成了代码，不只是文案。合并请求比对确认时与回执时的 head、目标、base 三者，先比对再写。审核结论带 head，head 变了旧结论进历史。CI 绑定 head 加 base。决定分记录、确认、实施三态。页面刷新后未确认的动作一律变未知，不自动重做。这些值得保留。

但有三处比方案文字弱，演练时要知道自己演练的是哪一半：

- **重复派发只查工作项有没有负责人。** 方案说的第二维"同一会话或工作区正在写入"没有实现。并入负责人会话的分支只改了一行事件文字。
- **合并比对里的 base 相等在 GitHub 上做不到。** GitHub 合并接口只支持 head SHA 必须匹配，没有 base 约束。base 新鲜度只能靠分支保护的"必须最新"间接保证。真实实现会有一个 base 的时间窗，HTML 的模拟比现实严。
- **审核新鲜度用 head SHA 做键，在集成分支拓扑里会连锁重审。** 看代码路径：合入 #101 后集成分支 SHA 变，兄弟 #102 和 #103 的新鲜度变红，更新 base 生成新 head，新 head 让审核失效。于是每合一个子 PR，剩下的全部重审，三个子任务接近平方级。PR 核对清单的原话是"绑定其实际审阅的内容，例如 diff 或 commit"，对受影响内容复核。干净的 base 更新 diff 不变，按仓库自己的规则不必重审，只需重跑 CI。建议审核绑定 patch 内容哈希，人工确认和合并比对绑定 head SHA，两套键分开。

## 三、我认为真正的盲点

- **长期负责人会话和仓库哲学相反。** 仓库每一步都新开对话，让 Issue 承担状态，对话无状态。方案把"负责 #40 的 Codex"做成跨天存活的会话，要协调子任务、回答接口问题、自己做 #43。这种会话会被多次压缩上下文，之后它对早先决定的记忆只是模型转述。方案自己写了"角色和原生会话应当分开"，但紧接着要求消息必须送到那个具体会话。建议拆成两种寻址。正在写入的工作必须精确到会话和工作区，这是单写入者的要求。提问和协调只需寻址到"角色加 Issue"，由一个读过 Issue 的新会话接。负责人的记忆就是 Issue 加一条协调记录，不是某个进程。
- **消息通道会变成第二权威。** 仓库第 4 步的全部理由是让 Coding Agent 不要同时面对多份可能漂移的上游指令，Issue Agent 的 prompt 原话是聊天只引用 Issue 中的决定。方案的"通知：契约发生变化"和"需求变化后通知负责人"正好打开这个口子。补一条硬规则就够：任何会改变范围的消息必须引用一次 Issue 修改，否则平台拒收。
- **集成分支的代价没有算。** 它带来每行代码两次合并、base 连锁，以及一个没定义的问题：集成 PR 合入 main 前要不要第 9 步正式审核。严格按清单要，全量重审是脱裤子放屁。便宜的答案是机械比对：集成 PR 的 diff 等于各子 PR 已 PASS 的 diff 之并，只有冲突解决提交需要新审核，组合行为靠集成分支上提前跑的用户验收。反例也值得想：#40 真的需要集成分支吗？三个子 PR 直接对 main、声明合并顺序、父 Issue 在 main 上验收，少一层审核和一条会漂移的分支。你的第 5 步工程量镜头会问这个。
- **路径所有权完全缺席。** AGENTS 协作一节已经写了"并行写入前明确不重叠的路径所有权"。单写入者保护在会话层，两个独立工作区各改同一个文件照样在集成时冲突。给每个子 Issue 声明允许触碰的路径，PR 时核一下变更文件列表，几乎零成本，而且是现成规则。方案列了"第一版不做语义冲突预测"，但路径所有权不是语义预测。
- **第一版的 ROI 顺序可能倒了。** 仓库里写得最细、重复最多、最机械的是第 9 到 10 步。每轮返工要新开一个审核对话、两个验证对话，在验证对话里修，再新开审核对话，每个都要固定 head 和填对 prompt。这件事是单 Issue 的，不需要父子拓扑和跨工具消息就能验证两种适配器，并且立刻减少你今天的手工劳动。方案把它和派发、跨工具通信、产物交接捆进阶段二。我会把"一个 PR 的审核循环执行器"单独做成阶段二，消息系统等真的同时有两个负责人在跑再做。
- **"已验证"和"有效确认"缺少机器可查的定义。** 产物三态里的"已验证"若由接收会话报告，就回到了"模型说完成了"。按 TESTING 模板的口径定义它：精确命令、退出码、产物版本哈希。决定的"有效确认"同理。仓库现行做法是 owner 把结论补回 Issue，所以有效确认就是由你的 GitHub 账号写入 Issue 的文字。模型会话拿不到你的账号，自然冒充不了。merge-readiness 工作流已经在用 author_association 做同类判断。
- **DEC-002 留给 Studio 的东西没接上。** 那条决策把进程外 harness、沙箱和权限分离推迟到"Coding Workflow Studio"。这份平台就是那个 Studio，而它对自动启动的写入会话用什么权限模式一个字没写。方案说负责人"不能通过消息扩大权限"，但没说靠什么机制。第一版至少要写明每次启动会话时传入的沙箱模式和允许工具集。

**关于规格本身。** 散文里大量篇幅是"不做什么"，这是把你的约束复述了一遍，读起来严谨，但可建的部分只有第十二节一段。HTML 里 intent、job、session、PR 四个状态机反而是更好的规格。建议反过来：把它们抽成实体、转移、谁有权触发的表，散文缩到只解释取舍。

**我会改成的落地顺序。** 阶段一的适配器验证不变。阶段二只做单 PR 审核循环执行器，顺带把审核绑 patch、合并绑 head 两套键做对。阶段三再加派发、路径所有权、带 Issue 引用约束的消息。集成分支作为可选拓扑，用一个真实 Issue 对比有无它的审核次数再决定。第一版砍掉 PR 镜像评论和用量展示。
