**我支持做，但不建议把这份"完整 v1"直接拆成一批 Issue、同时开工。**

它最有价值的地方，是把 coding-workflow 从"怎样把一个 PR 做正确"，扩展成"多个 Issue、多个执行者怎样共同交付"。最大的风险则是：**平台本来要替你承担协调工作，最后却变成需要你维护的第三套工作现场。**

我核对了 `coding-workflow` 当前主干的 `1772cd2c` 版本，阅读了方案与 HTML，并执行了 HTML 中部分状态和动作函数的定向测试。下面区分三件事：方案是否值得做、怎样接入才不偏离目标、现有原型实际证明了什么。

## 一、方向是对的，而且有几处边界值得坚持

### 1. 它解决的不是"缺少一个看板"，而是"责任与执行没有连起来"

方案中最重要的一条线，其实不是七格 PR 流程，而是：

> **工作项 → 当前负责人 → 实际会话 → 本次执行 → 固定产物 → 谁接收和验证。**

这条线一旦可靠，你才不必反复回答："应该找哪个会话？它还在运行吗？这个结果是谁负责接？对方究竟用了哪个版本？"方案明确区分逻辑负责人、原生会话、机器、工作区和执行标识，并禁止用"最近一次会话"代替准确定位，这是必要设计。粘贴的文本 (1)

我的判断是：**这条对应关系比首页做得多漂亮、能显示多少指标重要得多。**

### 2. 它没有把模型表态当成客观事实

方案把下面几件事分开了：

- 会话空闲，不代表 Issue 完成。
- 消息送达，不代表产物被正确使用。
- CI 成功，不代表独立审核通过。
- 子 PR 合入集成分支，不代表父目标完成。

这些区分不是无意义的流程细化。它们分别改变下一步该做什么：继续执行、等待消费、补充验证，还是请求合并。粘贴的文本 (1)粘贴的文本 (1)粘贴的文本 (1)

所以，我不会因为它有消息状态、交付状态、操作回执，就简单批评它"过度工程"。

**判断标准应该是：这个状态是否对应一个真实的协调问题，是否有人根据它采取不同动作。** 有实际消费者的运行记录，与为了证明"我遵守了流程"而堆出的记录，不是一回事。

### 3. "原生做事，平台协调"是合理边界

不另造编辑器、终端、完整聊天历史和全局主 Agent，能避免平台迅速变成一个需要长期维护的编码客户端。方案也明确保留了原生工具的上下文管理、子代理和批准交互。粘贴的文本 (1)粘贴的文本 (1)

但这里有一个后面必须处理的限制：

> **不重建聊天界面，不等于可以不承担执行控制端的责任。**

只要平台能启动轮次、发送输入、请求中断，它就必须知道这些动作的真实语义，以及批准问题究竟由谁接住。产品边界可以薄，责任边界不能模糊。

## 二、它并不只是 coding-workflow 的界面化，已经改变了部分流程

这不是反对修改原流程，而是需要把"展示原流程"和"采用新流程"分开。

对照原文，有三处值得明确：

| 环节 | 原 coding-workflow | 这份方案的变化 |
|---|---|---|
| Finding 核实与修复 | 新 Codex、新 Claude Code 分别核实事实和影响面，由 Codex 综合；需要修复时，在 Codex 验证对话中继续 | 方案概括为核实、修复、复核，并允许原开发会话继续修复；没有完整写出双模型分工 |
| 技术解读 | 合并后由网页端 GPT 使用 apps，基于源码与开发记录做 Tech Lead 解读 | 方案强调由原生负责人生成，平台集中呈现 |
| 用户验收 | GPT 网页版和 Claude Code 对验收计划形成合意，再交给 Codex 实际执行 | 方案保留了验收阶段与固定候选，但没有完整保留上述角色分工，并增加合并前的父任务组合验收 |

原流程依据见第 10、11、13 步；方案依据见第十章及"项目总览"的报告生成安排。粘贴的文本 (1)粘贴的文本 (1)

**这些改变未必不好。** 比如组合验收前置，我认为通常比"全部进 main 后才第一次发现组合不通"更合理。

但应该明确采用哪一种：

> "同序沿用原流程，只负责传递与呈现"；
> 或者"同序采用经你确认的新变体，以下步骤和角色有所调整"。

不能给两个不同的行为保留同一个名称，让未来的 PR 审核人以为它们完全等价。

另一个值得保留的原则来自 DEC-008：新增机制要说明改变谁的下一步动作、覆盖什么独立风险、为什么现有机制不足，以及替代或缩小了什么旧机制。它并不要求"只能减少复杂度"，而是要求对新增复杂度诚实记账。

因此，同序真正应该替代的是你现在的机械动作，而不是在原有动作之外，再要求你登记一次、确认一次、维护一次。

## 三、最需要补实的，不是更多功能，而是三个关键连接

### 1. 把"恢复会话"与"向正在运行的原会话送消息"分别验证

这两件事表面相似，实际不是同一个验收。

"拿到一个 session ID，调用 resume，成功得到回答"，只能证明某种恢复路径可用。它还没有证明：

> 你已经打开、正在工作的那个原生会话，可以在不产生第二个竞争执行者的情况下收到平台消息；处理后，你还能在正确的原生现场继续工作。

方案已经明确写了"不能把新建会话冒充恢复原会话"，方向正确。我建议把这句话升级为首个真实验收场景，而不只是设计原则。粘贴的文本 (1)

我核对了当前官方接口，存在可以利用的真实落点：

**Codex：**App Server 提供 `thread/resume`、`turn/start`、`turn/steer` 等能力。其中 `turn/steer` 是向正在进行的轮次补充输入，要求匹配 `expectedTurnId`；它不是再启动一轮执行。这为接入提供了明确接口，但仍需验证你实际使用的客户端、会话与服务实例之间的关系。[OpenAI Developers](https://developers.openai.com/codex/app-server?utm_source=chatgpt.com)

**Claude Code：**现在已有原生跨会话通信，使用 `ListAgents` 和 `SendMessage`。接收方运行时在工具调用之间读取消息；空闲时可以由消息触发新轮次。原生通道也明确区分消息被送达、暂存或拒绝。**同工具通信不应该默认重建。**[Claude](https://code.claude.com/docs/en/cross-session-messaging)

**外部系统进入 Claude 原生会话：**Channels 能把事件推送到已经打开的 Claude Code 会话，并通过回复工具形成双向通道。不过它仍属于研究预览，且依赖会话保持开启及对应认证、组织设置。它值得优先验证，而不是直接用 SDK 新会话替代原生现场。[Claude](https://code.claude.com/docs/en/channels)

我的接入建议是：

> **先研究怎样连接已有原生能力，再研究怎样统一两种执行器；不要先写一个统一执行器抽象，再强迫原生工具适配它。**

还有两个不能留到最后的问题。

**批准问题由谁接住？** Codex App Server 的部分工具批准，是服务端向客户端发出请求，再等待客户端回答。平台自己启动执行器时，不能未经验证就假设"用户回到某个原生窗口一定能处理"。要么已有原生控制端确实能够接住，要么平台提供最小的原生批准转交；不需要另造审批制度，但必须打通。[OpenAI Developers](https://developers.openai.com/codex/app-server)

**认证和费用走哪条路径？** 不能把"原生 Claude Code 能登录"自动推导成"第三方 SDK 产品可以直接复用相同登录和额度"。官方对第三方产品提供 claude.ai 登录或额度有明确限制。个人本地接入与对外产品也不能混为一谈，应按最终选择的具体路径验证，而不是提前承诺完全沿用订阅。[Claude](https://code.claude.com/docs/en/agent-sdk/overview)

### 2. 不仅要有"平台向 Agent 发消息"，还要有"Agent 主动向平台交接"的出口

方案的通信目标是负责人之间直接合作，不再由你转述；但目前 HTML 的发送入口，是人在表单中选择发送方、接收方、关联任务和正文。作为演示合理，却还没有说明真实执行者怎样主动完成同样的动作。粘贴的文本 (1)tongxu_issue_workbench_complete…

**真正需要验证的是这条完整路径：**

```text
Codex 负责人形成一个固定版本的接口或产物
    ↓
在原生会话内调用一个轻量交接工具
    ↓
平台根据接收工作项，找到准确的负责人和会话
    ↓
通过接收端支持的原生通道投递
    ↓
接收方读取、使用并返回实际验证结果
    ↓
平台更新交接与等待关系
```

这个"轻量交接工具"可以通过原生扩展接入，例如提供发消息、登记产物、回复交接的少量工具。发送者身份由实际连接确定，不让模型随意填写"我是 Owner"；正文继续用自然语言，不必发明一套复杂的 Agent 通信语言。

更重要的是：**消息可以到达，不意味着平台有权抢占接收者的工作。**

运行中的消息怎样进入、空闲时是否唤醒、等待批准时如何暂存，都应服从接收端的实际能力与权限。不能把所有情况都简化成"收到消息就再启动一次执行"。

这个连接完成后，平台才真正减少转述；否则只是把复制粘贴从两个聊天窗口搬到了一个漂亮表单里。

### 3. 审核绑定的"版本"，不能只有代码版本

方案很重视 head 变化后旧审核失效，HTML 的 `headFreshReview()` 也确实检查审核 head 是否等于当前 head。tongxu_issue_workbench_complete…

但还要回答另一个问题：

> **同一份代码，审核时对应的是哪一版已确认需求？**

举一个假设场景：

原 Issue 只要求"能导出 CSV"，审核通过。之后你明确增加"必须在断网环境下完成导出"，代码没有变化，因此 head 也没变化。

这时旧 PASS 不能证明新目标已经满足。

方案已经要求正式范围变化后通知受影响负责人，但"通知了"与"旧审核不再能直接放行"还需要连接起来。粘贴的文本 (1)

我建议利用派发时已经保存的**已认可范围快照**，让审核记录同时引用它。无需给每条评论建立哈希链，也不需要普通证据链接更新就全面重审；只要能识别：

> 本次判断针对哪份代码、哪个目标，以及哪一版已经确认的实施范围。

这样才能避免"代码版本绑定很严谨，但审的是旧需求"。

## 四、我会调整一个默认项：有子 Issue，不必默认有集成分支

方案已经把父子关系、实现依赖和合并前置分开，这点很好；但它随后又规定，带子任务的顶层 Issue 默认建立集成分支和集成 PR。粘贴的文本 (1)

**这不是逻辑错误，但默认值偏重。**

我的判定标准会改成：

> **这些子改动能否分别进入 main，并各自保持可用、可验证？**

能，就未必需要集成分支。父 Issue 仍可负责整体目标和最后的组合验收。

不能——例如几个接口必须一起改变，单独合入会留下不完整的用户入口——那么集成分支就有明确价值。

一个简单反例：父 Issue 是"改善导出体验"，子任务分别是修复中文编码、补充错误提示、完善使用文档。它们可以有父子关系，却不必因此增加一条长期集成分支。

这里的成本不只是多一个分支。按方案，每个子 PR 和父集成 PR 都需要检查、审核、明确的人工合并，以及后续版本核对。拆得越碎，这些动作越多。粘贴的文本 (1)粘贴的文本 (1)

因此，我会坚持人工合并边界，但避免通过过细的 PR 拆分制造大量人工合并。

**不要先把 PR 拆得过碎，再用自动合并来治疗自己制造的负担。**

同理，"一个子任务""一个会话""一个 PR"也不应被隐含地绑定为一对一。小任务并入负责人后，完全可能共享同一个交付 PR；只有需要独立审查和独立交付时，才单独建立出口。

## 五、HTML 是有价值的交互原型，但有四处状态不一致值得先修

我在 Node 中执行了原 HTML 的状态与动作函数，替换了 DOM 呈现和计时等待。**这不是浏览器端到端测试，也没有连接你的真实 Codex、Claude Code 或 GitHub 执行现场。**

## 六、我建议的推进方式：保留三阶段，收紧第一阶段的验收

原方案"先验证接口，再跑一个子任务闭环，最后扩到三个顶层 Issue"的顺序是正确的。无需推倒重来。粘贴的文本 (1)

我只会把第一阶段写得更具体，防止最后交付的是"SDK 能调用"，而不是"你的工作流能接通"。

### 第一阶段：证明不会破坏原生现场

选定真实 Codex 和 Claude Code 会话，确认会话、工作区、控制端和认证路径。

随后分别验证空闲时的双向通信、执行中的安全投递、等待批准时的处理，以及断开后的核查。验收重点不是"返回过一段文字"，而是：

> **消息到的是原目标；没有出现第二个竞争执行者；原批准没有被绕过；你还能回到准确的原生现场继续工作。**

已有长期会话先关联和观察；需要验证的新能力在独立测试会话完成。方案对"不为测试平台而迁移或重启长期任务"的限制，应继续保留。粘贴的文本 (1)

### 第二阶段：证明它确实替你完成一次交接

让一个负责人交付固定产物，另一个负责人通过自己的消费入口验证；平台收集真实回复，而不是你手动把状态改成"已验证"。

随后完成一次绑定代码与需求范围的独立审核，由你明确确认合并，再读回实际结果。

这一阶段不必先完成全部三视图、三种派发方式、PR 镜像评论和用量展示。那些功能可以逐步补；**"交接不再靠你搬运"必须先成立。**

### 第三阶段：再增加并发和层级

前面成立后，再扩展到三个顶层负责人、子任务独立会话和共享会话待办。

集成分支按真实交付需要创建；不同任务之间只有数据依赖，就不要额外增加代码分支依赖。不要为展示更完整的任务树，制造本来不需要的拆分。

最后，在一次真实交付后的现有 PR 或 Issue 中复盘即可：你少做了哪些转述、寻找和核查？平台又新增了哪些维护动作？不用为了评价它，再开发一套复杂度统计系统。

## 最后的判断

**这个方案值得进入"原生接入验证＋一个真实交付闭环"的开发阶段；还不值得按完整功能清单全面铺开。**

我最希望保住的是它的责任划分、固定产物交接、独立审核和人工合并边界。最希望修改的是：默认集成分支偏重、与原流程的角色变化没有完全说清，以及对真实双向接入的验收还不够具体。

真正的成功不是"你终于在一个页面看见所有 Agent"，而是：

> **你仍然负责目标、判断和取舍，但不再需要记住每个执行者在哪个会话、搬运哪条消息、核对谁收到了哪个版本。**

只要第一条真实交付链证明了这一点，后续界面和功能扩展就有依据；没有证明之前，再完善十个状态和三张页面，也不能替代它。
