三份文件都读完了：v2 方案全文，两份 HTML 的全部状态逻辑在 Node 里跑过探针，`merge-tree` 实测过，GitHub 文档核过。结论先说：v2 吸收了前两轮几乎全部对齐项，方案文本现在比 HTML 可靠；但两份 HTML 对三条关键规则的实现互相不一致，也和方案文本不一致；另外有两处和你仓库现行规则的冲突，三方到现在都没人指出。

## 一、v2 吸收了什么，我撤回什么

吸收的部分我逐条对过：A 档威胁模型和机器人凭据、网页端 GPT 作为外部步骤、修复的写入责任移交、七处原型缺口映射到 T 场景、集成分支改可选、范围变更只经 Issue、转接与运行中投递分开。第 16.2 节写的"X 完成→固定结果→填入 Y→启动 Y"就是上一轮的转接定义。产品原型里修复流程也真的建模了移交：核实会话先只读，确认后作者会话转为已暂停并记录移交对象，任务负责人切到核实会话，修复批次计数只在发布后加一。

**我撤回 import 闭包自动免审。** v2 第 8.3 节把判断放在接收时刻，每个候选只判一次，而接收本来就要判一次，所以判断不是额外事件成本。第 7 节又把闭包碰撞保留为提示信号。这比我的机械规则好。条件只有一条：接收记录要写明哪些旧证据复用、哪些重查，第 6.2 节已经要求了。

**G1 先于 G2 的顺序，取决于一个只有你能回答的事实。** 如果你一周的机械劳动主要在第 9 到 10 步的审核循环里，G2 该先做；如果主要在接收多个 Agent 的 PR、跑对照工具、决定合入上，G1 先做是对的。我无法访问 SEC_metrics，#153、#264、#287、#293 的说法我只能当作 GPT 的转述。v2 自己给出的"G1 只读子版"门槛够薄，所以无论哪种答案，第一刀都不大。

## 二、两份 HTML 实测：修掉了什么，还剩什么

上一轮七处缺陷在产品原型里全部有对应实现，我逐项验证过：验收选拒绝或待补证据时流程格不再变绿；技术解读绑定版本，新 head 后自动解除；连续两次负面审核返工数不变，只有修复批次加一；查回原消息时消息和操作一起恢复；D2 在新 head 后可以重验落实；派发检查工作区占用，包括路径穿越写法；席位上限、只读模式、条件不满足时拒绝接受结论、决定改变范围后旧审核失效，也都成立。

但三条规则两份 HTML 各做一套：

- **委托范围。** 方案第 12.2 节要求委托绑定目标和作用范围。v2 演练页的委托只覆盖范围 S1 合入 main，指向集成分支的 PR 被拒。产品原型的委托没有任何目标或范围绑定，开着委托时，指向 integration/50 的 #151 和父集成 PR #150 都会被判为可按委托合入。产品原型才是将来要变成真界面的那份。
- **发出后主干前进。** 方案 T14 要求保留"已合入，证据待核"。v2 演练页做了：发出后主干前进，回执里标记证据待核。产品原型在同样场景下合入成功，历史记录固定写"受测树与合入树相同"，没有任何待核标记。
- **判断是否绑定 base。** 产品原型里审核不绑 base，只有组合检查绑 base；v2 演练页把接收判断严格绑到 base，主干一动判断就失效；方案文本写的是"相关 B"在接收时判断。三个版本。这条规则我们争了两轮，到现在还没有写成一种可执行的形式。

小项一条：新会话一拿到创建回执就获得暂停和接续能力，方案第 17.2 节说的是按已验证的具体操作开放。

`merge-tree --write-tree` 的说法成立：无冲突返回树，有冲突返回树加冲突清单并退出 1，工作区不动，它确实往对象库写树，结果树能读进隔离 worktree 跑测试。

## 三、与你仓库的两处冲突，以及建议

- **PR 正文的程序区块会被你的流程每轮冲掉。** README 第 8 步原话是"在仓库外创建临时 Markdown body，并覆盖已有 PR"，第 10.6 步每次修复后复用这条。v2 第 4.3 节让程序在正文里维护一个区块并写前重读，两者相遇的结果是每轮修复后区块消失、程序再补回、正文来回抖动。建议把机器事实从正文里拿出去：head、base、受测树、结论作为 check run 或 commit status 挂在 head SHA 上。这样天然绑定版本，不和正文争写，而且 check run 正好需要我们已经要的机器人身份。正文留给人和 Agent。
- **逐次确认只存在于同序本地库。** 第 15.3 节的本人确认是本地回环页面上的一次点击，第 24.1 节又要求关键结论不能只靠私有数据库解释。建议逐次确认直接用 GitHub 的 review approval，由你的人类账号作出；机器人合入，"owner 账号的批准"既是确认也是审计线索，分支保护里的"新提交后撤销旧批准"免费给出 head 绑定。委托记录同理，是你账号写在 Issue 里的文字。两种确认都落在 GitHub 上。
- **共同验收应该是 Issue Agent 第 9 节的扩展。** 那份 prompt 已有 Acceptance Checklist，按 DEC-008 的扩展现有机制，不要另起一节。
- **接收者角色不在 coding-workflow 里。** 对只用 coding-workflow 的项目，G1 的接收闭环会坍缩成"PASS 加 CI 后 owner 确认合入"，那就是 v1。G1 的价值集中在 SEC_metrics 这类有接收角色和对照工具的项目，方案应直说试点对象是谁。
- **merge queue 可用性。** 方案第 13.5 节把它列为优先。我抓的官方页面没有任何可用性说明；我的记忆是它只对组织所有的仓库开放，你的仓库都在个人账号下。先在仓库设置里看一眼，再决定要不要写进方案。

如果出 v2.1，我只改五处：委托绑定目标和范围并以产品原型为准；发出后主干前进走"已合入待核"路径；把 base 绑定规则写成一句可执行的话并让两份 HTML 对齐；机器事实挂 check run 而不是写正文；逐次确认换成 owner 账号的 GitHub 批准。其余不动。
