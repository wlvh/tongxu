# 一、这版最终采用什么方案

## 1. 中心是"交付"，会话只是执行现场

同序主要围绕这条线组织：

> **用户目标 → 共同验收 → 实现分工 → PR／固定产物 → 接收与复验 → 按授权合入 → 确认用户成果。**

Issue 定义做什么；原 PR 承担本次代码交付的交接；接收者判断能否进入目标；程序管理事实、证据、责任和队列。

会话仍然重要，但不能成为唯一记忆。换一个 Agent 后，应当能从 Issue、原 PR 和固定证据接手，而不是要求你重新解释全部历史。

最终保留原方案的三个主视图：**项目总览、任务／会话／PR、通信与交付**。只是它们的第一关注点改为成果、下一步责任和交付障碍，而不是会话数量或消息数量。粘贴的文本 (1)

## 2. 先连接已有机制，不再重新建设一遍

对于 SEC_metrics 这样的试点：

**已有接收入口就复用接收入口；已有对照工具就接入工具；已有额度账本就引用原账本。**

例如，#264 的 D02 对照工具已经合入，方案不再把"整理出一个普查工具"当作待开发成果。应做的是固定候选和材料、调用实际入口、收集结果、把范围与限制展示给下一步负责人。

同序通用核心不应写死公司、年份、D02 或具体调用预算。项目工具继续由项目维护；平台负责调用和关联，不接管业务实现。

## 3. 授权分三种模式，不一律重批，也不默认扩权

| 模式 | 允许的行为 |
|---|---|
| **只读／影子模式** | 采集、比较、排队建议、生成待发布交接包，不执行远端写操作 |
| **逐次确认模式** | 执行这一次具体获准的发布、修复或合并 |
| **有限委托模式** | 在已核验的角色、范围、目标、条件和资源限制内接续执行 |

**已有有效委托，不要求每个 PR 再找你批准；没有委托，就不能因为平台具备按钮而执行。**

这项修改来自真实项目差异：#153 的书面分工已经允许条件明确的技术合并，同时将业务定义、新真实调用、费用、正式采纳、部署和破坏性操作保留给用户。平台不能把这些区别重新压成"所有合并都重批"，也不能把技术委托扩大成其他权限。

接入时仍需核验授权来源与执行身份。多个 Agent 共用你的 GitHub 账号时，账号上的一句"已同意"本身不能证明是你本人作出的新决定。

## 4. 先约定验收，再决定如何拆任务

跨 Agent、共享入口或涉及旧状态兼容的交付，在 Issue 中增加一小段共同验收：

```text
共同交付：用户从哪个入口得到什么结果或准确限制。
分工：谁实现提供方，谁接消费者，谁确认真实组合。
必须一致：输入输出、单位／期间／来源、失败含义、旧结果处置。
材料：固定材料在哪里，参与者是否都能取得。
验证：用哪个已有入口，谁维护和执行。
预期差异：允许什么改变，哪些必须保留。
合入出口：哪些可独立先合，什么满足后共同目标才算完成。
```

**开发负责人先提出自己的证明；接收者补遗漏的消费者、反例和组合边界。**不是让所有任务先排队等接收者写验收方案。

旧版成功也不是正确性的最终标准。成功变拒绝可能是在纠正错误放行；新增成功可能是丢掉难处理内容。因此要比较状态、内容、归属和来源，而不只是通过率。

## 5. 不改作者分支，也能验证最新目标组合

新版将下面两件事明确分开：

**自动重写作者分支，不做。**

**在隔离现场构造"固定目标 B＋候选 H"并验证，做。**

Git 的 `merge-tree --write-tree` 可以计算组合结果而不修改工作区或索引，适合作为这个机制的基础能力之一；具体版本、冲突处理和测试现场仍需开发时验证。[Git](https://git-scm.com/docs/git-merge-tree)

这样，作者不必每次只为了"追一下 main"就更新自己的分支、重新提交、重新转述。

但合并树一致只证明代码内容一致，不证明环境、外部数据和业务正确性。实际合入与受测组合不同，也必须如实保留"已合入，但证据待核对"，不能伪称没有发生，更不能自动回滚。

# 二、系统具体如何运行

## 1. 每项交付都有一句明确的下一步

不是"等待中"，而是：

> **由历史消费者在候选 C 上复验来源选择与复跑行为；补齐两项证据后，交接收者重新判断。公共实现者可继续无关任务。**

这句话包含责任人、动作、对象、通过条件和后继责任。

多个测试可以并行；但负责将结果收齐、形成完整交接的责任不能悬空。

## 2. 交接留在原 PR，程序取得的事实不再抄写

开发者提交或返修，说明实际改变、范围、证据、独立性、如何回应上轮问题和剩余限制。

接收者返回，说明受审对象、结论、已核对范围、仍失败的复现、有限通过条件和下一步负责人。

head、base、目标、实际命令结果等能直接采集的事实由程序取得，不再让作者、接收者、索引维护者各填一次。

PR 正文保留当前摘要，关键事件保留在原评论或正式 review。更新正文要保护人工编辑并读回核对；不另开一条同义"平台汇总评论"刷状态。

## 3. 判断、运行和交付分别保存

| 层面 | 举例 |
|---|---|
| **运行事实** | 已启动、运行中、等待、完成、失败、未知 |
| **审核判断** | `PASS`、`REWORK_REQUIRED`、`OWNER_DECISION_REQUIRED` |
| **交付状态** | 待接收、接收中、待修正、条件齐备、请求中、已合入指定目标 |

一轮运行完成，可能得到返工结论；一个 PR 已合入，可能尚未正式采纳业务结果。

旧审核晚到只能归档到旧候选，不能覆盖当前状态。关闭线程、CI 变绿或解除 Draft，也不能单独清除尚未复核的阻断问题。

## 4. 队列控制接收积压，不只控制开发并发

默认顺序是：主干严重问题优先；随后收尾已有充分证据的成果和明确退回项；能解锁这些交付的依赖提升顺序；其他候选按已批准优先级和等待处理。

接收环节同时展开多少项实质工作应有上限。等待依赖的任务不占用正在处理的席位；必要上游不能永远排在被它阻塞的任务后面。

**不中断正在运行的长验证，也不因为接收积压就机械地停止所有开发。**程序展示队列和代价，责任人处理真正的优先级取舍。

## 5. 请求未知时，核查原操作，而不是再做一次

发布、合并、消息和额度认领，都先保存操作，再调用外部系统。

响应丢失时查询原 PR、评论、Run 或请求；服务重启恢复原记录。状态未知不能自动释放工作区，也不能成为再认领一次额度的理由。

合并请求使用 GitHub 支持的 head 条件，但普通接口没有同时锁住任意观测 base 的通用保证。发送前重读和请求受理都不能冒充"精确组合已经合入"。[GitHub Docs](https://docs.github.com/en/rest/pulls/pulls)

# 三、如何开发：四个阶段，八个工作包

这次不再沿用旧 D0—D7 作为实施入口，统一改为 **W0—W7**。它们是工作包，不是已创建的 GitHub Issue。

## 阶段关系

```text
G0：只读摸底
       W0
        ↓
G1：GitHub 交付接收版
       W1 → W2 → W3
        ↓
G2：单 PR 执行闭环
       W4 → W5
        ↓
G3：完整多 Issue 协作
       W6 → W7
```

**G1 不等待两种原生执行器接通。**已有 Agent 可以继续在原生工具中工作，同序先把它们产生的交付接起来。

## 开发任务表

| 工作包 | 要开发什么 | 必须交付的结果 |
|---|---|---|
| **W0：事实与政策基线** | 核对目标仓库、有限授权、现有工具和材料、在途 PR、下一步责任 | 真实基线、W1 Bridge、可编码的 W1 Issue 草稿 |
| **W1：事实采集与原 PR 交接** | 完整分页、固定候选、交接包、下一步责任、必要恢复记录 | 一个真实 PR 的目标、版本、证据和下一步一次看清 |
| **W2：可执行证据与临时组合** | 调用已有工具，隔离运行，构造 B＋H，解释内容与覆盖差异 | 可重跑检查、不改变作者分支、缺材料与工具故障明确 |
| **W3：队列、授权与可靠操作** | 接收席位、受限发布、逐次／委托模式、合并回读和未知恢复 | **G1 接收闭环可用**，无重复批准、无盲目重试 |
| **W4：真实执行器适配** | 两种引擎的启动、指定接续、最终事件、批准和能力验证 | 准确 session／turn 与真实结果；未验证能力不开放 |
| **W5：审核循环自动转接** | 按项目分工完成审核、必要核实、综合、授权修复和再审 | **G2 可用**，自动链不再人工搬运模型报告 |
| **W6：分配与交付通信** | 三种派发、角色寻址、真实依赖、消息和产物消费 | 多任务真实交接，不新开竞争写入，不强制集成分支 |
| **W7：完整体验与交付** | 三视图、外部报告、安装恢复、已知缺口回归和现场验证 | **G3 完整协作可用**，能回答六个用户问题 |

### 技术实现采用最小结构

独立产品仓库默认推荐 **TypeScript＋受支持 Node LTS＋SQLite**，已有合适技术栈时由 Bridge 判断复用。

G1 先做 CLI／本地任务入口、GitHub 页面和离线导出；G2、G3 在同一核心上添加执行器与浏览器控制，不再建立第二套状态。

核心模块只需覆盖：事实采集、固定候选、证据调用、接收与下一步、队列、授权核对、操作恢复。**不需要先引入微服务、通用消息总线、Redis 或流程编辑器。**

### 开发组织

先由一个主执行者负责共享协调核心。W4 的两个适配器，在接口固定后可以按不重叠目录并行；不要同时让多个 Agent 修改状态和授权核心。

已有测试工具的接入应由了解该工具的人提供接口和边界，不重新描述给另一个 Agent 从零复刻。

每个实施 Issue 都包含用户目标、非目标、真实代码触点、必要不变量、对应 T 场景、权限、失败恢复和文档影响。审核者不需要回头读这几轮对话才能判断 PR 是否合格。

# 四、如何验收：不只检查"不能乱做"，还要检查"能够继续"

HTML 的"如何验收"页已经列出 **T01—T32**。每项都有操作、必须观察到的行为和原始证据要求。

## 1. 首先明确四层证据不能混用

| 验证层 | 证明什么 |
|---|---|
| **逻辑／契约测试** | 状态、去重、绑定、拒绝与恢复逻辑 |
| **本地组合测试** | 服务、数据库、Git、工具和界面能够串联 |
| **真实接入测试** | 当次 GitHub／原生会话／身份／消息的实际行为 |
| **用户路径验收** | 目标完成、信息够用、机械介入和维护负担是否减少 |

模拟响应可以测试状态分支，不能证明 Codex 真正运行过。截图可以证明界面显示，不能证明实际合并、投递或消费。

## 2. G1 的第一次现场验收

使用专门测试仓库，至少准备三类候选：

**普通独立 PR、指向非主干的叠放 PR、需要共享检查的 PR。**

先只读导入，核对真实 head、base、实际目标和下一步责任。让多个候选竞争接收席位，再让一个任务等待依赖，检查必要上游能否推进。

然后调用现有检查工具。故意缺一份输入材料，系统必须显示不完整，而不是"没有变化"。在隔离现场构造目标与候选的组合，确认作者分支和工作区没有被改写。

授权分别验证：

| 情况 | 正确表现 |
|---|---|
| 只读模式尝试写 | 不执行 |
| 逐次模式缺少确认 | 不发请求 |
| 有限委托内的技术动作 | 无需再次找你批准 |
| 超范围、已撤销或来源不明 | 不发新的受影响动作 |
| 请求已发但回执丢失 | 查询原结果，不发第二次 |

最后核对真实合入目标和受测对象。**这条链走通，才可以报告 G1 受管接收版可用。**

生产试点先影子对照现有接收者；明确交接 main 的写入责任后再接管，不能双开两个"兜底合并过程"。

## 3. G2 的真实审核循环验收

选一个确实存在可复现缺陷的 PR，按采用的项目流程执行独立审核、必要核实、综合、授权修复和再审。

过程中检查三件事：

**输入是否准确？**不是审 H1，却收到 H2 的差异。

**结果是否真实？**只接受匹配 Run 的顶层最终结果，不读取中间的 PASS 词。

**自动化是否真的减少搬运？**你不应再复制模型 A 的完整报告到模型 B，也不应反复补填平台已经知道的 Issue、head 和会话标识。

再使用可控响应验证错误 finding、同 head 新证据、Owner 决定、格式错误、配额限制和反复返工。可控响应与真实模型发现分别记录，不互相冒充。

## 4. G3 的完整协作验收

覆盖原产品的三个顶层责任与三种子任务分配：

**同工具新会话、另一工具新会话、并入负责人待办。**

并入待办可以产生后续顺序 Run，但不能新增竞争会话或同时写同一现场。

完成一次真正跨工具的固定产物消费，分别观察送达、读取到匹配版本、实际消费验证。让一个范围决定只阻塞相关工作，其他独立任务继续。

覆盖一条直接合入路径和一条确有必要的集成路径。中途让一个已确认退出的会话交接，由新 Agent 通过 Issue、原 PR 和证据接手，而不是由你重述全部历史。

最后只看三视图，应能回答：

> **什么可用？什么没完成？谁在等谁？哪个证据适用于哪个版本？代码实际进入哪里？现在需要我决定什么？**

答不出来，即使后台全部运行正常，完整体验仍不通过。

## 5. 这几项恢复场景必须专门验收

**决定落实恢复。**决定已确认，新 head 让实施证据过期；重新验证实施后能够继续，不要求你重做同一产品决定。

**同类问题修复。**退回的是有限范围内的共同机制，不是不断补新词；原来已核对的证据有条件复用，不能每次全盘清零。

**错误 finding。**核实不成立时允许用反证重新判断同一候选，不制造空提交，不增加返工次数。

**未知操作恢复。**查到原请求已成功后，恢复原操作及相关页面状态，不再创建第二个"成功动作"。

**验收拒绝。**`reject`、`request_evidence`、报告过期，都不能显示"用户验收完成"。

# 五、怎样判断这套系统值得继续做

不以 Agent 数量、消息数或合并数量为主要成功指标。

先观察一批明确纳入的真实交付，记录首次有效接收反馈的等待、有效通过后到合入的等待、退回原因、重复问题、合入后严重遗漏、你的机械操作，以及维护同序新增的工作。

需要同时看到：

> **更多同类问题在提交前被工具发现；交付等待和机械介入下降；严重遗漏没有增加；新增维护没有吞掉收益。**

G1 允许尚未自动化的模型转接明确保留，不能因这一点抹掉接收层的价值；但 G2 宣称自动闭环时，链内人工搬运必须消失。

同样，**观察覆盖、重新计算、代码合入、已验证业务结果、正式采纳**必须分别报告。不能把"看过这些位置"写成"已经重新交付这些结果"。
