# 项目首次工作准备与成果返回

从主干正常工作台选择 GitHub 项目，在项目首页点“从 Issue 开始一项工作”，或在 Issue 详情点“处理这项 Issue”。右侧秘书中的工作准备按钮进入同一页面。三个入口按账号、仓库数字身份和原工作 ID 查同一记录；刷新、重开和切换项目不会发送新任务。

第一次填写该项目本机 Git 文件夹即可。程序核对 origin 与当前仓库身份，保存可复用设置。没有具体任务的预登记目录也能先保存工作草案；路径、登录或目标缺失时保留原话、失败原因及下一步。已有准备版本后的新原话单独保留为待准备草案，刷新后仍可继续；它不会改写旧版本目标或批准范围，建立新准备版本时才采用。准备时读取 GitHub 当前默认分支的固定提交，缺少对象时用已登记 GitHub 登录取得该提交，不切换用户分支、修改 index 或覆盖未提交文件。

## 同序负责工程准备

“让同序准备这项工作”显式启动一次只读调查，使用项目已选 Codex 秘书模型和现有订阅。调查可以列固定提交文件、读取有界文本，提出目标、验收、可改文件、保护材料和验证建议；不能写文件、批准或执行。每次最多32次工具调用、768KiB材料，沿已登记原生超时。缺目标、适用规则或可执行验证时返回问题，不自行扩大权限。重新准备产生新版本，旧输入和原件仍保留；已发且状态未知的原操作不会由此重发。

当前首版支持已有文本文件、已登记 Docker Node 环境及模型提出的有界 Node 验证脚本。脚本先以固定起点运行，执行环境不健康时不发送实施输入；原断言失败作为修复基线交给实施者；实施中及完成后仍沿原消费者测试。此验证只证明选定材料和断言，不能称为整个项目安装或完整业务回归。Python、训练、任意主机 shell、依赖下载不是这个入口自动取得的能力；需要这些条件时应提出问题。

项目可有大文件和二进制文件。实施输入只含选定材料；可改文件总量仍受原384KiB限制，全部材料仍受768KiB限制，单文件读取256KiB、目录8192项。工作区保留完整 Git 提交树和未选文件的对象、模式与历史；模型和测试容器只能看选定材料，容器不暴露 Git 对象库。不能以抽取小仓库、重建历史或遗漏未选文件代替成果返回。

## 本人确认与原实施

准备完成后核对目标、实质限制和完成标准。技术文件和脚本在可展开说明中，不要求用户填内部 JSON。

普通工作台查看钥匙可以请求在本机浏览器打开独立的“本人确认”窗口，不能取得窗口的短期批准能力。窗口绑定准确项目、工作、准备版本和内容摘要，10分钟有效且只消费一次；拒绝或服务退出后不能再批准。模型没有这个入口。打开窗口不是批准。

本人确认后，程序以部署时已登记账号在原 Issue 代发准确范围与实施／测试批准，读回并交原 AuthorityRecords 核验。共享账号须有已登记的明确决定；它不证明实际操作人与执行者分离。准备依据及许可最多24小时有效，仍受原配置更短时限约束。发送失去回执时，原工作保留在批准核对阶段。点击“核对原批准并继续原工作”，由本机窗口核对同一版本后查回原评论；无法核清就保留未知，不自动再发，也不以重新准备代替查回。停止和服务关闭都会在真正新增评论前阻止后续发送，已经发送的评论仍按原件查回。

随后复用原 IssueImplementationControls、QueueStore、权限、资源、原生执行与完整报告。项目工作库只保存设置、准备、版本和原请求引用，不保存第二套派发事实。原条件性空预算路径仅在实际账本、批准引用、计划和请求都为空时适用；配置不能制造免费额度。不增加计费权限，不使用账号重置。

## 成果与补充

原执行完成且测试、捕获和资源核清后，同序自动把完整成果提交导入真实项目自己的 `tongxu/work-…` 分支，并建立独立成果工作目录。原用户检出、index 和未提交文件保持原样。页面显示准确提交、分支、工作目录、全文与实际差异；这一步不包含远端推送、PR审核、主干合并、部署或本人成果接受。

接回中断只重读同一完整结果。程序保存准确接回意图、自建目录身份和 Git 执行原件；自身目录尚未完成检出时，只有原执行已结束、目录及索引为空、初始 Git 配置未变才能续办原步骤，不能把任意无 HEAD 目录当作可覆盖。分支被外部移动、被其他检出使用、成果目录有修改时停止并保留原因，不能覆盖；重复接回已一致结果不新增 Git 改动或模型输入。

“在原对话中提出补充”选中原责任和原结果，复用现有补充消费者、有效文件与测试范围。超出原批准范围须重新准备和本人确认。原回合、补充和完整报告都在同一工作中，补充提交自动接回原成果分支。停止阻止后续发送；仅阅读和重开不能恢复执行。

## 部署一次，项目自行复用

工作台计划的可选 `projectWork: {path, sha256}` 引用一份固定配置，需要已有 GitHub 项目入口及项目秘书。配置为 `{root, executor:{path,sha256}, verification, owner}`：root 是私人准备目录，executor 为已有原生实施配置，verification 为原 Docker 配置，owner 为已有 Owner 来源模板（项目与 Issue 由当前工作绑定）。这些是部署者一次性选择的执行环境和账号边界，不是每条任务手工生成目录、授权 JSON 或搬运成果。旧固定目录、旧报告格式与关闭此功能的入口继续使用原路径。
