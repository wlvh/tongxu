# R3：原实现者可靠续做与最小显式交接

本分支以用户 [2026-10-22 最新澄清](https://github.com/wlvh/tongxu/issues/8#issuecomment-6331971488) 为当前边界。它明确替代 [旧实施评论](https://github.com/wlvh/tongxu/issues/8#issuecomment-6331483980) 开头和第 4 条把“同一物理工作区 A→B 原地接管”固定为交付方式的要求。旧评论、已写源码、失败原件和历史审核保留；唯一写者、状态核查、权限、资源、停止/撤销和独立审核要求继续有效。

## 默认路径与先后顺序

1. 原实现者 A 持续负责实现。B 的独立审核和影响核实结果返回 A，由 A 修复。正常审核循环不转移写入权。
2. 优先完成 A 的可靠接续与受管工作区复用。区分任务负责人、操作、原生会话和进程。新会话必须如实记为新上下文，并关联原任务/原结果；原运行已执行或未知时不能盲目重发。既有同一 operation 的核查恢复继续保留。
3. 解决旧操作结束后的永久占用：原控制器保护、登记的进程/容器与副作用、写者租约、当前候选及准确权限均核清后，允许合法后续操作复用任务/发布分支。不能仅凭 PID 消失、超时、删除锁或换目录释放未知责任。
4. 保留明确选择换负责人或“将 B 的已有工作统一到 A”的最小显式路径。保存原成果、版本、暂存与未提交内容，核清 B 的执行及必要远端事实，新负责人取得准确权限并实际消费成果。新角色不凭报告内容取得写权；正常反馈不自动触发换人。
5. 延续方式按结果选择：在满足原安全条件时复用同一受管工作区；或固定提交并分别保存暂存/未提交差异与原证据，在新的受管工作区继续。新现场必须说明采用了哪些内容及来源，不能把未提交变化当成旧提交，也不能借换目录绕过原写者活跃/未知。
6. 完成以上最小能力后继续原生会话控制、工作台入口和原完整用户流程。不扩展通用迁移、自动换负责人、任意外部 App/IDE 会话接管。

## 当前可调用的最小续做

`review-records-cli continuation-source --store ABS --operation UUID --mode same_owner --source TEXT` 只读核查已完成的原 repair，给出 `continuation` 引用和当前 HEAD、暂存/工作区变化清单。它不释放责任、不调用模型，也不授予写权。

后继 `tongxu-queue-repair` 计划可携带该完整 `continuation` 对象。默认 `mode=same_owner` 要求前后实现者相同；仅显式选择换人时用 `explicit_handoff`，并在原协调安排的新修订中记录来源负责人和新负责人。两种模式都使用已有 `review-records-cli repair --plan ABS`；现有 `coordination-cli repair` 可将同一计划接入调查→执行→结果消费流程，不需要复制报告。

实际执行前重新核查原件，在原控制器互斥和原队列事务内把旧操作与唯一后继绑定，再沿现有权限/资源/停止控制启动。换目录或发布分支不允许绕过同一原任务的占用。只选取原结果的准确已提交 H 作为新基线，原暂存和未提交内容分别保存在原队列的捕获中，包含实际 Git blob、索引原字节和逐路径前后状态；它们不会被偷偷合入新 H。后继输入携带原独立审核等必要上下文，新结果保持自己的 operation/session。

未完成原操作优先使用原 `repair --plan ABS --reconcile-ended`：先读原运行和已发生修改，在同一工作区核清后恢复。暂存区若与已登记的允许路径修改不一致，程序保存索引与暂存对象后拒绝自动提交，不覆盖另一版暂存，也不把无关路径夹带进 commit。已登记的部分修改及匹配暂存可以完成原候选的测试、提交和新鲜审核，原写入请求不重复发送。

当前新路径的实际正向执行是明确标注的本地角色协议夹具，Git、SQLite 和 Docker 测试真实运行；未新增官方模型调用。三个定向场景包括 A 合法续做并反证旧 finding、显式 B→A 消费固定成果、原目录中断后恢复且只新增必要审核。所有原失败与修复日志保留。独立固定源码复核及真实模型/用户界面串联分别取得证据后另记，不能由这些场景直接宣称全部 R3/T07/T20/T27/T47 完成。

## 真实原件复用发现的兼容修补

首个固定候选 ea1aa69 在复用原真实 Codex 受控修复时拒绝了官方工具宿主：原执行器只记录 observed-official-child 的 launch/process 观察，没有它的 exit.json。该实际缺陷记为 WH-F01/P1，原 ENOENT、独立复现和 REWORK 保留。

核查器现在区分直接启动的进程和实际观察到的官方子进程。前者仍要求原 exit；后者必须位于已验证完成的原生 Codex 阶段，匹配原父 PID、官方同包工具宿主身份、原完成回执中的 transport hash、完整动态调用及对应响应，并确认父子 PID 均结束。子进程退出码仍写 not_observed，不造 exit，不以 PID 消失单独放行。

已用原 PR48 的真实受控修复只读核对这条兼容路径：507 个原文件的 hash/大小/mtime，以及原 operation 和事件数均不变；读取原30个登记进程与8条 Docker 执行记录，未启动任何原生进程或模型。它证明当前结束核查可消费该真实原件，不等于新执行了一条真实后继链。缺普通 exit、伪造 observed child 或缺真实父捕获的安全样例仍拒绝。

随后独立复核在私有合成协议变体中发现 WH-F02/P1：原 LiveProcess 缓存机制允许同一工具请求及回复重传，readRepairSession 也按这一契约消费，但新 helper 关联检查错误地要求原流中请求只出现一次。修补只对完全相同的 request/hash 沿原调用关联，保留全部原帧；同 RPC 改参数、错父进程、缺原回复或缺 helper 仍拒绝。原36f3042 的 REWORK 和独立反例保留；合成变体不计为新真实运行。
