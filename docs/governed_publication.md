## 原权限、资源与请求恢复的接入

原发布计划增加可选字段：

```json
{
  "governance": {
    "authorityIntent": "已保留的准确publish意图",
    "resourceRequests": ["原资源请求的64位摘要"]
  }
}
```

已有Owner来源配置时，入口按明确治理计划启用发布消费者，保留原保护定义及升级记录；这一步不授予发布许可。准确动作必须属于background角色、当前材料和原接收操作，并以`publicationAuthorityPayloadSha(plan, documentSha256)`固定允许公开的投影和执行身份。投影使用`publicDocument`确定生成，`documentSha256`是其JSON原字节摘要。原许可和资源ID不进入该输入摘要，避免先后准备的循环依赖。

继续使用`node dist/src/publisher-cli.js prepare --plan /绝对路径/plan.json`准备，再以`publish`发送、`reconcile`只查原结果。`prepare`直接返回`documentSha256`和`publicationPayloadSha256`，供原权限流程引用；预览文件为了可读而带缩进，不能对预览文件重新哈希来替代这两个准确摘要。明确拒绝时才使用`retry-rejected --plan /绝对路径/plan.json --source 明确重试依据`。这些入口不生成Owner决定，也不从报告中选取权限或shell命令。

首次新写先绑定原操作／计划／投影／许可／资源，再经原provider认领。认领本身会更新授权观察，实际写入前重新读取Owner来源；旧观察不能冒充最后一次核实。接收许可、其它发布内容或其它执笔者不能替代准确publish动作。零资源也保留唯一绑定；已经配置资源提供者时不接受空资源集合。

每个POST在同一原发布操作下，先持久保存准确目录、请求和前置观察，再在队列事务中核当前材料、停止、授权、原held资源，完成实际spawn和首输入。事务回滚不会抹去之前的请求登记和进程侧原件。旧已打开的发布／资源消费者仍受存储守卫约束，不能绕过新绑定。

恢复先读取原请求：准确证明没有启动进程时，保留未启动记录并按原权限继续；进程已结束且可能发送时，恢复同一请求身份并查回原远端对象，不因缺少数据库intent或响应而重发。原件不完整、进程活跃或未知继续待核。只有明确拒绝才能按原有界重试规则再试。改变计划、目录或许可不能替换未知请求。

未启动事实只能由当前控制器在确认未调用发送步骤后持久记录，不能从可变错误文件里的false字段推导。新请求准备还签发同一进程内的一次执行凭据；原登记遗留在磁盘或队列中并不产生新的执行凭据。恢复只能读取它，不能重用旧目录直接再次调用发送步骤。

详情和status均精确读回、原发送终态核清后，才记录发布结果并向原provider结算；资源结算回执丢失查原请求。发布完成、资源结算、当前远端仍匹配、技术判断和业务接受分别记录。事后撤销阻新写，原事实仍可回读。`prepare`在已有发送记录时返回`prepared_original_dispatch_exists`，不会把旧发送说成未发送。
