## 运行与证据边界

`delivery-assessment-cli prepare|run|reconcile|close-unstarted --store <绝对队列路径> --request <固定请求>` 复用原events/blobs与消息运行。请求绑定准确批次、输入证据摘要、所选场景及已取得终态的验证原件；程序自动装配完整材料，不接受截断为完整覆盖。`prepare`不发模型，`run`使用已固定原消息计划，`reconcile`只读原捕获。已确认未发送且没有未结资源的请求可显式关闭，活跃或未知运行不能换id重发。

模型返回的完整原文始终保存。格式、场景引用或结论自相矛盾时是`returned_invalid`，不会自动重发。部分或等待结果保持原运行未解决。实际消息提交前在同一原事务内核批次、输入证据和停止条件，数据库门拒绝旧消费者绕过该核对。

若仍未发送而原用量观察过期，可用`run ... --billing <新的既有订阅观察>`继续同一计划；它只更新原消息机制的用量观察，不改变原请求、费用边界或授权。已有provider账本沿原认领/查回/结算，不因报告“通过”自动释放资源。缺原回执时保留未知。

`state|report --store <队列> --id <原判断id>`读取阶段或完整原文。工作台在固定成果内显示判断和覆盖，完整报告来自同一后端。秘书新增全文查询需要同时显式设置`deliveryOutcomes: true`与`deliveryReports: true`；只有原`deliveryOutcomes`的计划保持旧工具契约。判断加入后形成新的证据集合，本人采用仍走原准确来源和前版核对，模型不能代签。

## 格式升级和原反例修补

首次成功 `prepare` 在同一事务中启用队列格式 17。旧客户端新开该队列时明确拒绝；已经打开的旧客户端不能再把原 Owner 来源投影为当前有效接受。格式 17 单独记录此前实际启用的功能版本，不能借升级假定接收、资源、写入或任务功能已经配置。此后的显式功能升级保留格式 17 及独立判断的数据库约束。没有独立判断的旧队列，普通读取不会改变格式。

早期候选已准备但未发送的请求，可以对**同一原请求**再次执行 `prepare` 完成格式升级。原 run、计划、材料和捕获不重写；未升级的旧准备记录不能直接开始新模型输入。不要手改版本号、删除原记录或用另一个 id 绕过恢复条件。

资源绑定及实际新认领分别在原事务内重核批次和输入证据。已发生投入的查回和结果结算保持可用，不因撤销而阻止清理，也不擅自退款。验证原件保持可按标注编码还原的完整字节，包括 UTF-8 BOM；合法的外层 JSON 代码块与原消息协议共用解析规则，完整但不合约的报告进入 `returned_invalid`。

完成的判断可以从队列在线备份回读，仍引用原 run 和原捕获。复制目录不授予新的执行责任：未完成的备份只可检查或消费已经存在的完整捕获，继续执行必须回到准确原工作区；不能通过移动目录重新发送。

回归检查需已有 Docker 配置 `TONGXU_TEST_DOCKER_CONFIG`。若要重跑旧客户端兼容反例，另用 `TONGXU_TEST_LEGACY_DELIVERY_MODULE` 指向独立重建的前置 `queue-store.js`；未提供时该项明确跳过，不记成旧客户端已验证。
