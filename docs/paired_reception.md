# W6：两个固定接收任务的阶段协作

本子范围在已有真实执行器、原队列接收、发布和受限秘书基础上，细化 #8 的一个可执行片段。固定前置为 PR24 `e5ca71fa4883b0546758d3e6c0b793e8fdc806a1`，独立分支 `feat/w6-paired-reception`，真实 target `feat/w4-readonly-secretary`。独立双任务示例是两个固定候选 A/B 的接收工作；仅 B 的共享接收阶段等 A 的指定独立判断，不等整个上游 Issue 关闭或合并。

本批既有本人边界不变：同序本地开发和限定验证；现有订阅，不新认证或费用；不 main/merge/自批/部署，不操作 SEC_metrics。技术顺序由既有持续开发委托细化。本条不是本人生产采用、完整 G2/G3 验收或新增写权。

CP01 一个入口固定同一原队列中的两个不同 item、各自候选/材料包、接收计划 hash、共同范围来源与阶段安排。任务 A 形成指定能力的接收结果；任务 B 对使用它的当前候选完成接收。运行前核两个计划、实际当前材料及已有占用，保存原计划。禁止模型报告改变执行器、权限、候选、路径或顺序。

CP02 B 的本地材料检查可在 A 原生接收进行时完成；B 的共享接收明确等待 A 的当前、完整、范围内接受结果。B 先检查不会消耗接收席位等待 A；原任务 A 的其他实施、Issue 关闭和合并不作为该门。普通失败保留具体原因，不能将证据不足或部分结果当已满足。

CP03 后端在 B 准备和实际发送前重核 A 的准确 item/packet/H/绑定/判断及停止与占用；A/B 候选或材料变化只使相应新阶段待核，不改写历史结论。同库原客户端也不能绕过新增阶段门派发。仍复用原 events/blobs/operations/claims/controls，不创建独立调度账本。

CP04 程序将 A 的完整判断与准确原引用作为数据加入 B 的固定输入，保存其 hash。B 返回明确的消费引用与完整报告；仅文件存在、发送成功或退出 0 不算实际消费。A 报告没有工具或指令权限。对无必要发现的结果不制造返工。

CP05 同一入口重复只读取/核对原运行。等待、中断、错误终态、捕获缺失、未知原进程都不能换目录或新 operation 重发。原执行确已结束且捕获完整时，依现有 reconcile 继续；部分结果保持未知并保留原现场。停止新增投入作用于后续新模型发送，已有原件和独立本地读取仍可访问；停止实施/合并不偷换成暂停所有只读工作。

CP06 使用明确标记的本地样例验证阶段阻止、独立步骤继续、同库跨进程竞争、重复、材料变化、撤销与中断恢复。固定候选经必要独立复核后，运行一次真实 A/B 接收与产物消费；保存实际执行版本、两个原会话、完整输入/输出、原操作和消费关联。真实与样例证据分开。首片段只支持两个固定只读接收任务；不宣称任意开发任务调度、共享代码写权转移、统一负责人、所有 W6 或完整 G3 已完成。

源触点：queue-store.ts 的原账本及阶段检查；receiver.ts 的输入/消费绑定；新增 paired-reception.ts 与固定 CLI；W6 定向回归。源文档与原 #8 实施条款发布读回后编码；PR24 保持独立可接收。

## 本地入口与结果含义

先用原 W1/W2 创建两个准确候选的材料包，并导入同一原队列。该队列应已显式启用接收与补材料（格式6）、没有活跃或未知占用；席位数不为配对增加。两个任务共享同一个已采用范围，目标分支不同。已有队列历史不删除；本子范围每库固定一组两个任务，不允许更换原安排来重发未知任务。

分别准备已有 receiver-cli 接受的两份完整计划。配对计划只引用其准确字节：

```json
{
  "schemaVersion": 1,
  "kind": "tongxu-paired-reception",
  "source": "原共同范围与阶段安排的准确来源",
  "first": { "path": "/absolute/private/a-plan.json", "sha256": "REPLACE_WITH_ACTUAL_SHA256" },
  "second": { "path": "/absolute/private/b-plan.json", "sha256": "REPLACE_WITH_ACTUAL_SHA256" }
}
```

```sh
node dist/src/paired-reception-cli.js run --plan /absolute/private/pair.json
```

程序在同一队列中登记两个固定材料包和计划，将格式显式升级为7并安装数据库阶段保护。原格式3—6仍保持可读；旧程序打开7会拒绝，已打开的旧接收SQL也不能替换任一登记计划或缺少前置绑定就派发B。模型计划、原接收状态和停止检查仍由原模块实施。派发阶段的限制不是只在界面上提示。

本地控制器互斥文件位于该队列 `pair-<准确计划hash>/controller.sqlite`；只作同一次入口的进程互斥，不保存第二套调度数据。业务状态与原操作仍在同库 events/blobs/operations/claims/controls。重入使用相同计划和原目录；完整捕获先核回读，缺失或未知不替换。等待先前接收时不为B留一个空占用。

`completed` 表示两次接收流程已返回、B对A的准确报告完成消费，不表示B一定被接受。必须另外读取 `second.receiver.judgment.verdict` 与完整报告。`waiting_or_unresolved` 保存具体阻塞和原操作，不能当成功或自动重试许可。没有回写代码、合并或生产动作。

## 当前候选验证

构建通过。初版117项相关本地检查零失败、零跳过，包含初版9项新双任务场景，以及原队列、接收、发布、秘书、结果适配和修复回归。新场景中两个独立CLI争用时只有一个控制器；控制器在A原捕获完成后被强杀，恢复仍消费原A并只启动一次尚未派发的B。模型消息均为明确标记的样例。测试初次使用Mac系统别名临时目录被既有规范路径检查拒绝，改用项目内规范临时目录后通过；未放宽路径检查。

真实两候选模型接收与独立复核须使用本子范围的对应原始证据，不能用上述测试数代替；最新准确候选、运行和判断见原 #8 与对应 PR。

独立首审发现：从单任务入口替换 A/B 接收计划仍能绕过配对安排，以及投资停止误阻止 B 的已有材料检查。修补把双方计划 SHA 绑定到登记记录、原接收准备/发送和数据库保护；B 的独立阶段直接核固定原材料并记原 events，不申请接收占用，停止投资时仍可读取。新定向10/10覆盖公开入口反例与停止后原安排恢复；初审原件保留，修补由独立复核重跑原公开入口反例。这里的独立材料检查不启动模型，不证明独立人工/模型判断。

修补后118项相关检查零失败/跳过。另4项真实Docker边界/退出记录回收检查通过，历史PR20的无init原Docker包被新消费者完整读取；原文件不改。CP06容器检查使用显式init后重跑全部原定场景，不删失败用例。原两项独立P1和新候选适用性在对应PR保留。

扩大真实容器检查还观察到测试替身用 truncate/write 更新 fake-remote.json，竞争检查偶尔读到半份JSON。测试替身改为原子替换并保留原断言；不重写固定旧候选或其失败。该测试修补只消除替身的文件观察竞争，不改变发布程序的互斥或远端语义。

原生CLI有时将唯一JSON最终结果包在一个Markdown代码围栏内。接收器仅接受整个输出就是单一完整JSON围栏（可带`json`语言标记）或原裸JSON；不从解释正文搜取对象，不接受多个围栏、部分JSON或错误终态。解析仍核原捕获、全部身份/候选/计划/消费绑定，原final文本不改。已经完整捕获但因围栏留为未知的原操作可以在确认原执行结束后回读，无需重新请求模型。
