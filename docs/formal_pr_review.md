# 单张 PR 的正式审核与修复接续

<!-- capability-anchor: CAPABILITY.formal_pr_review -->
依据已采用 [Issue #72](https://github.com/wlvh/tongxu/issues/72)。该入口已实现程序路径及协议样例/真实 Git、Docker 组合验证，状态为 `pending_validation`：正常入口的真实 Codex/Claude 外层演练及本人成果接受仍需在准确安装环境完成。它与已有局部 repair、独立接收、合并和验收分别记录。

## 从正常页面使用

在已配置项目的“任务与完整报告”中选择一张 PR，在“正式 PR 审核”点击“启动正式审核”。后台从原候选和采用的 Issue 准备输入，再核接收权限、原资源和停止状态。登记不表示已发送。页面按轮展示准确 H（审阅提交）、B（目标分支基线）、target（真实目标分支）、阶段和完整原报告。

新的 Codex reviewer 取得完整 PR 差异、全部变更文件的前后内容、Issue、采用范围、根和适用目录的 AGENTS、SOP 与配置的上下文。后续允许修改的文件不限制审阅范围；reviewer 可从同一不可变 H 读取必要的其他调用方，或运行已注册隔离测试。工具不执行仓库命令、工作区脚本或报告中的指令。二进制、不支持文件、材料超限或必要上下文缺失会明确等待，不截断后冒称完整审核。

完整 PASS 且没有 P0/P1、覆盖缺口和业务问题时立即结束。仅 P2 记录在原报告中；不额外启动 fact、impact 或修复，也不产生无必要提交。空 finding 但缺证据不是 PASS。

REWORK 的全部 P0/P1 构成一个固定批次。新 Codex 查事实，新 Claude Code 独立核影响；事实方先反证不短路另一方的初始验证。完整影响报告回到本批原 Codex 事实会话综合。有分歧才交换证据，最多三轮；仍不足就列待补证动作。verifier 不能签正式 PASS。全批被反证且候选和采用要求未变时，新的独立 Codex 承接正式 reviewer 责任，核原完整审阅和双验证，追加正式结论，不制造提交或无条件重做全部检查。

## 授权修复与发布边界

确认需要修复后，后台复用已有有效实施/测试权限，不反复要求同范围确认。只有原事实会话仍由本控制器持有，才能向它显式交接写权。工具仅能修改配置的已有文件；保护测试不能改。实际注册 Docker 测试通过、受测文件树和提交对应后，由宿主形成本地 H2。原源仓库保持只读。准备工作区时分别保留准确 H、B 的历史并核对共同祖先；即使目标基线 B 与 H 已分叉，后续采集和完整再审仍读取原 B，不改变目标或将 B 替换为共同祖先。

程序生成完整私人 Review / Fix Record 和可交付的 PR body 草稿，显示“本地修复完成，待发布与新候选材料”。当前代码不新增 Git push、PR body 写入、合并或部署通道；由项目已有获准交付路径发布代码和记录。远端 H2 和修复记录核回后，若尚无当前候选材料，后台调用原采集器和受控 Docker 验证器生成新原件并导入。验证器的真实在运行报告只作为“不完整材料”绑定准确测试权限，不能冒称 W2 完成；原容器结束证据核清、资源结算后才导入最终报告。不能拿本地 H2 当远端新 head，也不能手工把旧 W2/PASS 改成新候选证据。

前台工作台每 10 秒做一次有界接续检查，最多 360 次；也可点击“核对已发布的新候选”。准确远端 H2、原 B/target、对应 PR 修复记录和当前已导入候选材料全部具备时，自动开新轮、新 Codex 上下文做完整审核；再有 P0/P1 就形成新批次。未接发布、采集受阻或缺少新候选验证权限/资源时停在具体等待原因，查看原报告不启动模型。前台关闭后没有后台服务继续跑。

返工计数沿原 ReviewRecords 的 `repair_batch_published` 和同 head 去重；只在代码及对应修复记录实际发布并核回后计一批。模型讨论轮次、证据交换次数、本地写入及本地提交各自保留，不能充当发布批次。超过三批仍进入原简化反思入口，不新建第二套计数。

## 查看、停止和重新打开

“查看完整原报告”按原角色全文显示，不由秘书改写。原始输入输出的摘要、角色、实际 session/thread/turn 绑定和固定提示装配可在同一报告核对。分轮捕获保存当时完整的原日志前缀；事实会话仍活着，不把单轮结束冒称整个进程退出。

“停止后续动作”先在本机核原入口、operation 和项目归属，立即记到原 operation，不等待新的 GitHub 查询或项目来源补查；后继轮沿原请求记录的上一轮关联（previousOperation）逐轮继承停止，包含准备新材料期间和子轮已经登记或发送之后；后续新角色、工具写入、测试启动及提交仍过原停止门，后继状态也显示已停止。已有输出和修改保留，不自动回滚。新项目请求把已核实的账号、项目及仓库身份保存在原请求中，因此冷重开离线也能停止；旧请求缺少这项绑定时不改写原输入，只能使用本机已经发现的项目身份核归属，缺少时明确拒绝，先恢复项目身份再停止。停止仍需查看钥匙和同源请求，不放行其他项目或新增执行。请求已发而结果未知时不能换 ID、换目录或冷重开重发。原事实会话失去持有权时明确等待，不能另开会话冒称原会话。已知完整结果只回读，直接 PASS 后刷新和重开新增模型输入为零。

H、B、target、采用的 Issue/范围或材料改变，原报告保持原候选归属，旧 PASS 和写权不能直接用于当前候选。只有实际业务取舍才列 owner 问题；沿原 Issue 记录问题、影响和答复理由，再用新采用的要求和权限重新核准。没有可用的获准 Issue 写入路径时，报告给出原 Issue 和待记录内容，不能冒称已经发布。全批反证后的正式复核和同会话修复若合法提出真实业务选择，均保持“需要业务决定”；完整报告展示原问题及原 Issue 记录提示。普通覆盖或技术证据不足仍为待补证。

最终正式 PASS 同时核原要求摘要和当前正式采用记录，并消费刚读取的采用来源；写入终态的原事务再核一次。即使 H/B/target 和 Issue 正文未变，在途新采用的验收版本也会使旧报告暂停放行，包括仅 P2 和全批反证后的正式结论。旧完整报告与已经发生的资源结果仍保留，重复查看或重新打开不重发；新要求沿原准入准备，不改写旧请求。仅准备而未正式采用的提案不会使当前要求失效。

## 安装配置

在私人 WorkbenchPlan 增加 `formalReview: {path: ABS_CATALOG, sha256: SHA256}`。目录只由安装者配置，页面只能选已有入口和请求 ID。

catalog 为 `schemaVersion: 1`、`kind: "tongxu-formal-review-catalog"`、`entries`。每项包含：

- `id`、原 `source`、私有 `root`、固定对象源 `objects`、`config` 路径和摘要。
- `issue` 的 number/bodySha256/adjudication；`requiredPaths`、`contextPaths`；已采用的范围来自原 AuthorityRecords。
- `repair` 的 allowedPaths/materialPaths/protectedPaths、contract、testPlan/testPlanSha256、generatedDirectories、demonstrationFixture。
- `authorization.receive/implement/test` 原决定摘要；`budgets` 的 phase（analysis/fix/candidate）、ledgerId/resourceRef/unit/quantity。

执行配置沿既有 RepairConfig：实际 Codex/Claude/Node 入口、固定角色策略文件、禁用 MCP、允许指令来源、已有订阅的费用证据及超时。角色完整系统提示和当前 AI 选择在准备时冻结；已有运行不被后来的设置覆盖。原授权、治理接收扩展、正式资源消费者和原账本须由安装者沿既有机制明确启用；加载页面不会授予权限。GitHub 读取使用原注册 EventProfile；未配置时如实拒绝。

每轮读分析共用原 receive 资源组；进入写阶段前核完整回合并结算，再用不同 implement 动作的原资源组。新候选自动验证另用 candidate 测试资源组，不能默默增加 analysis 的额度。测试另核准确 test 权限。没有本地余额或自动退款推算。
