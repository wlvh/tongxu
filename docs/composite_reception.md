# 固定多成员组合的独立接收

接续原 #4/#5/#8 的组合材料与接收缺口。固定前置 PR28 `6583c21f22eea1c41d112a553dc84b1a6c52567b`，独立分支 `feat/w3-composite-reception`，真实 target `feat/w5-review-records`。来源为本人持续 goal；保留原单成员入口、原失败、旧判断及全部 W1—W3 原件。

CR01 可信导入请求明确给出同一 W2 组合报告的全部 W1 包，2—8个，顺序与原 inputs 一致，主锚点为末成员。核每份 manifest/候选/原 artifact 字节、同 repo/base/真实 target、每个前缀的 parent/H/T、原测试计划/样例/执行材料和最终树。缺成员、错顺序、同摘要伪替代或缺原件保持缺口；不只删除原 additional_members guard。

CR02 组合是有明确成员/顺序和受测最终树的接收对象。其稳定任务身份包含这些实际成员，原观察/原测试提交/材料摘要另保留。单成员 PASS 不复制给组合，组合 PASS 也不表示任一成员单独通过。原队列 operation/目标占用和 SQLite 记录继续使用；显式格式启用让旧客户端拒绝或被数据库保护，不得由旧入口漏传组合身份。

CR03 独立接收输入必须包含完整组合说明、每个成员准确 H 的选定源码、各前缀测试证据、准确 S/r 和材料缺口。原生程序仍为官方 Claude 无工具受限入口，原完整报告/会话/实际收到的 subject hash 可核。schema1单成员计划不能启动组合接收，schema2必须为所有成员明确列出材料范围，超限拒绝而非悄悄裁剪。

CR04 发出前重新核当前材料与所有成员在各自 PR 的最新源观察；同一PR有多阶段时保留各阶段，以末阶段作当前性核对。任一成员出现更新、范围变化或矛盾观察只阻断相关组合，原操作仍可读回。重复导入/重复运行不重发，未知先查原捕获；补证必须保留原组合与旧判断。

CR05 完整结果单独标为组合范围接收，具有准确 subject/成员/最终树绑定；普通发布/修复/依赖入口不能把它投影成末成员的独立 PASS 或单成员写权。需要将返工交给成员时仍须具体问题、准确成员、写入责任和对应重新组合验证，未有该桥接前明确待办；不静默选一个成员修复。该桥接与受管合入继续按原依赖推进。

CR06 验证包括真实 Git/固定组合执行与程序独立接收输入消费，模型替身清楚标注；原捕获、错误候选/成员/顺序/树/材料、更新与未知占用、恢复和单成员兼容用安全样例检查。需要真实供应商验证时复用已有认证/用量边界与固定输入，具体新接口才发有界任务，不重做认证迁移。

CR07 不合并 GitHub PR或main，不自批、改target/保护、部署、增加费用或操作SEC_metrics。组合材料可被独立判断与生产权限/正式合入/用户接受分开；原完整G1/G2和其它Issue缺口继续保留，不因这一个对象可接收就宣布全部完成。
