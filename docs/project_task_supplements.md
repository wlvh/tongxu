# 给原实施任务补充，并接回完整回复

本项落实 [Issue #71](https://github.com/wlvh/tongxu/issues/71) 的首条限定路径。前置是已登记的 #74 Codex 实施任务、原项目秘书，以及原候选的实施/测试授权和资源。源码 checkout 没有默认生产安装或额外模型用量权限。

## 正常操作

在右侧项目秘书的“发送给”中选“补充原任务：Issue …”，输入并保存。原任务或秘书正在处理时仍可收件，原文、目标和会话会持久保存；相同请求重复提交只回同一条记录，改内容或目标不能复用旧编号。收件只是保存，尚不表示送达原生执行。

原有界回合成功结束、宿主确已形成 H1、完整报告和资源结果核清后，程序才准备后续实施。后续继续同一逻辑负责人，以新的原生上下文读取 H1、原报告和补充，不恢复或接管旧原生会话。它使用独立的受管执行副本和原 QueueStore 执行记录，保留原任务定义、H0 请求、工作区和捕获；内部执行记录关联原 task/operation，并明确同一 logicalOwner。页面仍把这些处理当作原任务的补充，不新增一组用户任务或任务版本管理界面。

后续仍受原范围、允许文件、已注册测试、本人来源、停止和原资源约束。补充文字不能扩大权限。各段完整原报告平铺进入必要材料，不递归复制此前请求封套；普通问题/报告中的 JSON 是原文。必要代码、真实 Docker 测试和宿主提交继续由既有实施消费者负责，秘书模型仍只有查询工具。

完整原任务回复直接显示在最初项目/会话的补充记录中，并标明新上下文；不要求用户搬报告，也不强制多一次模型转述。旧秘书的原生回答不改写。刷新/冷重开读取原记录，不自动派发；冷重开后确实未处理而原前置已齐的补充，可明确“继续原补充”。

已完成补充在其执行来源退出目录后的历史读取，沿[项目秘书的原报告规则](project_secretary_chat.md#办理已审定工作)，复用当前已配置队列中的准确原件。

## 等待与取消

原回合运行、失败、停止、未知、只有未提交成果或资源未核清时，补充保留等待。首版只支持成功结束后的这条接续，不提供中途安全点、任意现场恢复、迁移未提交成果或自动换负责人。原H1/工作区或捕获后来变化时先核原记录，不悄悄用新内容替换。

后续请求已登记但因席位忙尚未准备完成时，在实施记录使用“继续原请求”，沿同一请求补完准备；原 H1、责任、补充原文和准备材料保持。

开始、读取和取消补充都会核对它与原任务、原 operation、责任及原文的固定关联。同名的另一份实施请求不能代替该补充；遇到不一致会拒绝，保留两份原记录，不启动或取消另一请求。

“取消未发送补充”沿原取消约束保留原文；编译前的撤回与开始编译相互排斥，已经登记的执行由原实施消费者判定是否确证未发，已发/未知不能删除当作未发。停止秘书、停止原实施、取消补充是三个动作；停止不依赖秘书先回答。仅停止原任务不抹去已收补充。

## 验证范围

协议模型/本人/资源样例已用于正常 HTTP 的运行中收件、实际文件修改、真实 Docker 测试、原 H1 到后续新上下文、全文回流、冷重开和取消/停止反例。样例与真实模型分开。另有正常入口真实 Codex 的运行中保存补充、原回合成功后同一逻辑负责人以新原生上下文处理及全文回流证据，见 [有界真实演练](formal_pr_review.md#有界真实演练与待验范围)；它不表示运行中接管旧会话。独立审核、安装、生产效果与本人接受仍各自留证，不能据此关闭 #9 的全部 F10/F11。
