接续原 #8 和完整 52 场景中的 G11，并绑定已有 G01/G03/G04/G06/G12 接口。当前准确前置为 PR37 的 027f2bbf311a966af34300ace19563e68ce76ab3，target feat/w6-addressed-messages；其代码与真实恢复证据已获限定独立复核，正常不中断同 Codex 路径仍待真实验证。以下为整个子范围的实施条款，不能仅凭部分代码称 TC01–TC06 全部完成。

TC01 在同一 QueueStore 的 events/blobs 登记少量准确任务与共同范围、各自候选、原负责人、原操作和拟接入部分。登记、联系、等待当前版反馈、部分可继续、共享阶段可实施分开。找不到原写者或没有回复时，共享写入保持等待，独立材料调查不被全项暂停。路径命中只作线索，模型报告不能自行颁发写权。

TC02 组织计划固定采用范围 S、技术协调版本 r、来源和受影响部分；支持并行、指定阶段等精确能力/产物、统一负责人。依赖在后端检环。新安排只约束尚未派发的受影响阶段，不强杀在途运行。独立小修不新增普遍审批；已配置本人来源时沿用 G01 准确授权与撤销检查。

TC03 反馈绑定准确任务、r/接口摘要、实际角色消息及完整原文。旧 r 的迟到回复只作历史，不能放行新共享阶段。责任、接口和范围变化只让受影响部分待核；精确上游能力到位并被消费后可恢复，不等待整个 Issue 关闭。

TC04 同工具新会话、另一工具新会话、并入原负责人待办三种派发有真实执行记录。待办按原任务责任顺序执行，不新增竞争写者；仅只读关联的任意 App 会话不能升级为控制入口。受管角色通过现有消息/执行接口读取固定材料，登记、送达、回复、产物消费分别记录，报告不成为 shell 或权限来源。

TC05 对任务、准确工作区和发布分支登记唯一写入责任。开始共享修改和每次实际写入前重核当前候选、S/r、三类停止、现行授权、原资源认领和占用。统一负责人或恢复要求原执行已经核实结束，原操作、未提交修改、后台副作用与远端状态均有准确现场依据；活跃或未知不接管，原件保留。该约束接入现有受限修复入口，不能只做返回“允许”的演示函数，也不另建全机锁或资源余额。

TC06 固定本地样例实际验证：未回复共享阶段被阻但调查继续；r1 反馈不能放行 r2；阶段门与精确产物消费；无循环等待；三种派发与待办无竞争；写责任并发/候选变化/撤销/原执行未知；原执行确已结束后有记录地继续；资源未知不重复认领；重启和重复入口不重发。真实成功路径复用已核消息/受限修复执行器，限定非业务受管工作区，不改正式候选制造缺陷。

共同成果 X1/X2 与人控制界面仍是后续 G13；精确接收/集成和最小单次目标更新仍按 G05 实施；秘书协调依 G07 接入同一后端。它们保留在原 goal 内，不因本子范围交付而改为已完成。无 main 直推/强推、合并、自批、管理设置、部署、新认证/费用或 SEC 操作。

## 已接入的只读协调入口

`node dist/src/coordination-cli.js prepare|run --store /原队列 --plan /协调计划.json --request /执行配置.json` 在同一队列保存版本、完整上下文和实际消息引用。`status --store … --run 准确协调计划哈希` 读取当前阶段与等待原因。`prepare` 不启动模型；`run` 按精确依赖准备角色输入，不同负责人可独立讨论，同一负责人顺序处理待办。每次都是程序新建并持有的受限只读上下文，不能把它称为外部旧写者的原会话；原写者联络及写权清场仍须另有实际证据。

执行配置为 `tongxu-coordination-readonly-execution`：固定现有执行器及哈希、各任务原始工作说明、当前计费证据、每个任务的协调授权 intent、超时与 fixture/native 标记。程序使用完整 `issue_owner` 提示和原上游流程；模型不能改角色、执行器、材料路径或权限。配置中的任务说明是可信入口数据，报告始终只作证据。既有 G12 工具、订阅、权限和已配置资源消费者的检查仍生效。

共享反馈必须来自准确角色的完整原生回执，引用当前共享部分、绑定候选和完整材料。新版本只使改变的共享部分待核，未变部分的旧完整反馈可有界复用。上游产物先保存完整原文，实际进入消费者的固定输入，并由完整结果确认材料引用后，才记为已消费；文件存在、模型表示赞同或上游任务完成都不能替代这个记录。

这些只读反馈和依赖检查返回 `phasePrerequisitesMet`，含义是这一阶段的技术前置已满足；`executionAuthorized` 和 `writingPermissionGranted` 仍为 false。实际修改、测试、正式接收和发布必须通过各自入口。尚未接上的 TC01 原写者联络／TC05 写责任与资源消费者，以及正式实现产物类型，继续保留为本分支未完成工作，不将只读消息报告当成修复结果。

原始任务说明和执行器配置固定；同一任务／用途只有一个选定消息。已发送或未知的任务只核原运行，不随新计费证据再发。完全未发送且已核结束的准备失败，才可显式 `refreshUnsent:true` 更新当前计费／授权证据，最多三版，旧文件和选择保留。执行前核选定消息标识，不能靠替换生成的计划执行另一任务。

## 受管修复的现有授权与资源接入

`tongxu-queue-repair` 可显式带 `governance:{authorityIntent,resourceRequests}`，引用原队列中的当前 implementer/background 实施授权和原账本请求。候选、操作、材料、允许路径、执行类型和资源集合都必须一致。现行本人来源在模型投入、工具修改和测试前重新读取；原供应方认领先查询、按原请求认领，未知结果只查原记录，不另造请求。完成后以原修复终态报告资源结果；撤销不阻止读取已完成结果或报告已发生的事实。

该扩展仍使用原队列数据库保护。启用时要求没有活跃或未知操作；旧入口的直接 `repairing` 状态变化仍被拒绝。新入口只有在同一事务中核过准确授权和原资源后，才留下与操作、候选及完整输入匹配的准入记录。协调任务还须有具体工作区／写责任交接；尚未绑定时继续拒绝，不能用这个资源接入代替 TC05。
