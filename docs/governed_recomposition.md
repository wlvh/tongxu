## 使用原入口

仍运行 `npm run member-repair -- recompose --plan /绝对路径/recompose.json`。固定计划的可选 `governance` 为：

```json
{
  "testAuthorityIntent": "已经登记的本次测试意图",
  "testResourceRequests": ["原资源请求的64位摘要"],
  "integrationAuthorityIntent": "另一个新集成意图",
  "integrationDelegation": {
    "authorization": "已有委托决定的64位摘要",
    "adoption": "该委托采用的范围决定的64位摘要"
  }
}
```

最后一项是可选的。它引用既有委托，不创建批准。没有委托且新集成意图尚未登记时，程序先保留测试与转交事实，返回 `recomposition_integration_authority_pending`，把新候选的准确动作保存到原目录的 `integration-authorization-pending.json`。在原权限机制登记该准确动作后，重新运行同一入口继续；不会重跑测试，也不会把被冻结的 `authorityIntent: null` 偷换成新值。

测试动作必须是 background 角色的 `test`，item／packet／H／B 属于原已完成成员修复的操作，`payloadSha256` 由 `recompositionTestPayloadSha(plan)` 得到，明确固定本次成员RETURN、原修复计划、新成员清单、测试计划、存储与来源。许可和资源请求的ID不放进这个摘要，以免产生循环依赖；资源请求本身又准确绑定许可的动作摘要。测试许可与新集成许可不得相同，implement／receive 许可不能借用。

先准备准确资源请求，再运行入口。程序沿原 repair operation 保存新测试的 events/blobs，不覆盖原 `result.repair`。全部所需资源仍由原 provider 认领和结算；存在资源配置时不能用空数组绕过。新集成是已有独立消费者，只构建私有Git产物、要求自己的 test 意图，不从重新组合测试借资源或一次性确认。

## 实际执行和恢复

Git／Docker 的启动前读取当前来源、停止状态、授权和原资源，并在同一队列事务内完成最后检查与同步启动。目的受限的测试许可一登记，就安装跨消费者和资源准入约束；已打开旧消费者不能在新控制器准备之前抢用它。原format20／21准入事件继续共用，不建立第二本账。

`test-producer.json` 与原队列登记准确关联唯一W2 run、计划、输入清单、上下文和测试来源。结果消费同时核对实际Docker终态原件；只改报告里的完成字段不能结算未知进程。已登记的原运行优先读取捕获，授权事后撤销不阻止读取结束事实；原文件缺失、部分捕获或未知执行仍保留原请求与资源，不能换目录重发。

W2执行完整、比较完整、样本断言失败和可转交性分别记录。已核清的失败执行可以向原provider报告失败，不能变成通过；资源结算回执丢失时返回 `recomposition_test_resource_result_pending`，查回原请求后继续。测试结果被消费、导入组合和关联原修复各有记录；导入后中断按原已固定捕获恢复，不要求已经过时的成员来源重新授权。

新集成候选仍需要自己的独立来源、W2和新接收。这里不会推断远端新PR已发布、成员旧PASS仍有效、Owner已经接受成果或允许合并。

## 独立发现与修补

1388517的独立审核为REWORK_REQUIRED：GRT-F01/P1在自有实际W2捕获中复现。把某实际Docker终态改为未知，再仅将报告tool改成blocked并删除执行引用，会使旧读取器跳过该实际执行。虽然新候选转交因不完整而拒绝，资源却被提前报告完成。原反例和失败结论完整保留。

修补从原验证目录独立枚举实际Docker执行，逐个核原run／计划／目录和终态，再与报告引用集合逐一对应；未被报告引用的实际执行仍不能忽略。引用不得重复，实际终态原件必须对应原sandbox字节，报告的执行完成字段也按工具覆盖和状态重新核对。未知状态、删工具／删阶段／伪装blocked均不能登记结果或结算；恢复准确原件后仍用同一run继续。共用此读取器的交付验证入口保持相同约束。

作者复验取得4个定向场景通过（包含原反例扩展、完整链、消费中断和真实启动前停止），另5个旧交付验证场景通过；修补后准确H的独立结论另行绑定，不能套用旧138的7项正向结果宣布关闭P1。

d0的独立窄复验关闭了原目录仍在的反例，但保留GRT-F01/P1残留：实际未知目录被改名、报告改裸blocked后，单靠前缀枚举仍能漏掉已发起的执行并结算failed。原d0失败封存保留，没有发布为通过。

后续修补在每个W2工具调用之前，先将run／stage／tool／H／tree／计划／执行目录登记到原队列events/blobs。捕获必须匹配这份准确登记集合，登记摘要随原结果保存；删引用、目录缺失或改名都不能抹掉已登记身份。工具实际调用前登记失败可记blocked，但只在原登记证明该slot未发起时按未运行处理；已登记而原件缺失继续unknown。探针仍必须从其固定原路径核终态。原重组和交付验证消费者共用这一契约，不开第二套运行账本。

旧已完整捕获的原结果继续读取；没有启动登记的历史裸blocked记录不再用报告自身来证明未执行，也不因此重发旧测试。修补后的新运行仍需独立复验，不能因换为队列登记就提前宣布缺陷关闭。

启动登记与结果消费还有存储守卫：首次新注册启用v1执行集合；结果写入必须来自已核原捕获的当前准入。已打开的旧读取器即便忽略新字段，也不能往原队列插入未经登记集合核实的结果。旧已保存结果保持可读，不把旧原件补写成新协议。

队列登记修补的作者定向验证：10项重组／共享交付验证通过，另1项真正调用前拒绝的未执行证明通过；加入旧消费者存储守卫后6项复验通过，包括准确bad5669所含d0旧读取器的实际运行。旧读取器尝试消费“目录改名＋裸blocked”的原结果时被存储守卫拒绝，资源仍held；当前读取器恢复原件后沿同一run完成一次结算。仍以新准确提交的独立复验为最终检查点。

## 旧运行接续保护

d2独立复验另确认GRT-F01的升级分支：旧版本已开始的运行在新入口读取损坏原件失败时，保护还没安装，随后旧入口仍能错误结算。修补将保护安装作为独立持久步骤，放在显式运行／接续入口和重复prepare/register之前；后续原件校验失败不会撤掉保护。纯状态读取不伪造新的捕获记录。

当前捕获准入同时绑定完整结果摘要；原资源结果准备和实际报告出口也核该准入，避免旧实验结果已经写下、尚未结算时绕过结果插入守卫。已知d2旧守卫定义按明确迁移升级，不接受任意改写的未知定义。历史原结果保留，`captureValidationCurrent`另表明是否已由当前读取器核实。交付场景和下一次验证不能把未经核实的旧结果当作已结束前置。

正常的完整旧结果可以用原入口reconcile：读原捕获、保留同一run、零新执行，并补当前核实记录。已经写下错误结果的未发布实验队列不会被静默覆盖或新结算；原失败继续作为反例保存，不冒称自动迁移为有效成果。
