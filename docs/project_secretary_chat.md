# 项目秘书对话

选择GitHub仓库后，工作秘书常驻右侧，直接输入并发送问题。中央可以查看Issues、PR、任务、报告或AI设置，不必为了提问离开当前页面。它不依赖旧任务秘书模板，也不要求先登记开发任务。可以在同一对话中追问、查看全文和来源记录，或新开一段对话。历史按GitHub账号与仓库数值ID保存，换项目不会带入其他项目的问答。

右侧可以收起，右下角入口始终可展开；窄屏默认收起，展开后使用抽屉。收起、同项目切页和查看报告不会停止或重发模型输入，正在处理时仍读取原进度和最终结果。未发送草稿在当前页面会话内按项目与对话保留；刷新或关闭浏览器前仍应自行保存尚未发送的文字。已发送问题和结果按原机制持久保存。桌面上的完整报告在中央打开，右侧可以继续沟通；秘书仍按当前项目的原读取工具取得材料，页面可见内容不会因此被自动拼入问题。

秘书能读取当前项目的资料、Issues/PR列表与完整正文，以及该项目已关联任务的原状态和完整接收报告。它可以解释记录、梳理待办和帮助澄清目标；普通问答只有查询工具。若安装者配置了本项目已审定 Issue 实施，用户可在“发送给”明确选择“办理已审定工作”；只有这次已保存的工作请求增加一个受限协调工具，秘书把固定原话交给原实施消费者。秘书仍没有业务写入、执行测试、批准、发布或合并工具，也没有通用创建开发任务能力。模型获得的材料和回答都作为数据处理。

秘书也能读取同一选定仓库的 Issue／PR 普通对话评论。每条评论附作者、创建及编辑时间和原链接，作者已删除时为空。评论作为资料进入原观察记录，回答可用原链接回查。PR 的逐行审核线程和审核正文有各自的来源，本工具只读取普通对话评论。

评论从最新创建的记录向更早记录分页，每次查询最多五条；较早评论后来的编辑会反映在它被实际读取的页中。`hasNext` 和 `nextCursor` 表示还可向前续读，`totalCount` 只表示该次远端计数。页面按实际序列化体积保留在 96KiB 内，放不下的更早整条评论留待下页，并标明 `deferredBySize`；续页从本页实际最旧评论继续。单条正文超过该页上限时返回 `body:null`、原链接及 `bodyOmission` 的原因和原字节数，空正文则保留为空字符串。即使已到终页，正文缺项仍须说明。

查询是逐页实时读取，新增、编辑或删除评论可能使跨页计数和覆盖变化。秘书应区分实际读到的评论与尚未读取的页或正文，按问题需要继续查询，并在回答中说明影响结论的缺项。翻页游标绑定原账号、仓库、条目种类和编号；过期或不匹配时明确拒绝。查看保存答案继续核验原观察与捕获。

## 对话与原件

每次发送先在一个事务内登记准确问题、对话与上一个消息，再由原受限Codex执行器调用模型。同一requestId的重复进入只读取原登记，不能替换问题或重复发送。每个项目同时只开始一轮问答，其他输入等待其结束。网页只提供问题、请求ID、对话ID与前一消息；执行程序、存储位置、权限和工具来自本机固定配置。

追问传入该对话此前保存的完整问题和回答。每条新消息使用新的原生上下文，记录准确会话/轮次，**不冒称接回同一原生会话**。单段历史最多64个问题，完整上下文超过192KiB时要求显式新开对话；原全文保留，不自动截断或总结替代。查看旧答案会核对原始捕获及来源引用，不重新调用模型。

模型使用现有ChatGPT订阅。原执行器在实际发送前读取当前账号与订阅内限额，并拒绝API计费覆盖和不可确认的普通用量；没有重写旧秘书模板中已过期的用量日期。模型和工具版本按实际能力准入，每次运行记录真实身份。输入、原始事件、最终回答、来源观察和失败记录保存在配置的私有对话目录。

每条问题最多调用24次项目秘书工具，包括已审定工作模式下的协调工具。模型从初始项目观察和每次工具观察取得总额、已用和剩余次数，优先读取当前问题需要的条目及相关完整正文；剩余为0时用已有观察作答，明确尚未读到的材料及结论限制。预算随原观察一起保存和核验。超过上限或调用未登记工具仍会拒绝，可能没有完整回答；页面说明原失败，旧请求不会自动重发。资料范围超出本轮可读取范围时，可以明确新开问题并限定具体条目。

最终回答从已取得的观察中选1至8条最相关的结构化引用，每条使用实际观察的64位小写十六进制ID。输出格式和项目角色说明均告知该要求，普通提问与已审定工作模式一致。完整可读报告继续使用Issue/PR自然链接说明其他已读来源，全部读取观察仍保存在原件中，回执仅列所选引用。最终格式或引用不合要求时显示未形成完整回答并保留原记录，宿主不会代选引用或自动重发。旧任务秘书的输出格式及历史捕获按原约定读取，旧项目已完成捕获也保留原格式。

## 停止与恢复

“停止本轮”只控制当前入口拥有的准确轮次，通过原生中断请求和进程收尾保存原件；停止回执与完整终态分开记录。即使GitHub暂时不可用，已有受管请求的停止仍可使用，不因此授予新输入权限。关闭入口会停止本入口的问答并收尾，不新增后台模型循环。

刷新、换项目和重新打开只读取原记录。注册后中断、部分输出、失败或未知捕获不会记作完整回答，也不会自动重发。原执行者仍活动或状态未知时，保留等待；进程身份原件缺失、损坏或无法读取时不推断它已经结束。恢复有效原件并确认原进程结束后可以继续；确认它结束后仍没有完整回答，则显示未完成历史。用户可明确发起后续问题，旧请求本身仍不被重跑。

## 本机连接

安装器在原WorkbenchPlan中配置`projectSecretary`，包括私有记录目录、现有Codex入口、受限配置和超时。正常使用不需要用户拼JSON。GitHub来源仍通过原只读项目服务，原任务仍通过原QueueStore读者，没有复制任务队列。旧任务秘书的完整历史回答、原核查提醒与已配置跟进保留在页面的“原任务历史与跟进”。

协议使用明确的`project-conversation`来源类型，绑定账号、仓库、对话和初始来源摘要，不伪装成PR或已登记开发任务。仓库没有提交时，提交和分支字段为空，不捏造H/B。

验证需分别记录测试程序响应和真实模型问答，覆盖直接发送、两轮全文上下文、跨项目拒绝、重复与冷重开、额度失败、部分回答、停止及原件损坏。真实试用只能证明实际执行过的范围，不代替本人接受或权限批准。

本机角色设置复查补充：页面显示该次入口配置的等待上限。当前本机安装对高推理强度的新问题允许最多10分钟，旧请求仍保留原180秒配置。到达上限时，控制器只中断自己持有的准确轮次，并记录是等待到期而非本人点击停止；中断应答不冒充完整结果，也不自动再发输入。页面说明未完成及原件保留。正常关闭/重开不改变原问题、原模型和原结果。


## 办理已审定工作

在“发送给”选定本项目的已审定 Issue，输入完整原话并点击“交给秘书办理”。普通提问不会根据文字或资料内容悄悄切换为派工。模型不能通过工具参数另选目标、路径、原话、授权或预算；受限协调工具没有这些参数。安装者沿既有 `issueImplementation` 一次配置支持列表和原实施权限/资源，日常用户不用写计划。超出已审定范围的附加要求不因此成为新采用，仍需原范围流程。

首次实施使用与该秘书请求相同的请求 ID；完整原话及对话关联以 `origin` 进入原实施请求、输入清单和实际模型输入，原采用目标、验收、Issue 正文摘要和旧请求均不改。已存在唯一准确责任时关联原任务；新聊天 ID 不能重派同一已审定工作。多条原责任或身份无法核清时等待，不按名称、最近会话或“最新结果”猜测。并发请求在原队列的最后登记事务再次检查，只能创建一项原责任。

关联既有任务时，新聊天仍有自己的请求 ID，并另外保存原实施 ID；它没有把本次新文字改进旧 origin，也没有宣称旧 A 已消费新文字。实际新增内容使用“补充原任务”。工作意图和关联留在原对话数据库，准备、实施、实际捕获与资源仍只从原 QueueStore / IssueImplementations 读取，没有第二套执行队列或成果账本。

原对话显示准备/等待、已发或未知、H1、无改动、需业务决定、失败/停止和完整原报告。秘书回答已完成不等于实施已完成；完整报告损坏时保留不可用，不退回秘书摘要。原资源未核清时单独说明。直接任务页和 CLI 仍看同一个原实施，秘书离线不独占控制。

原队列实际登记并核准的关联一旦建立，重复继续不会替换为另一项工作，即使原项已未发撤回且后来建立了新实施。准备中的临时选择不授权读回、停止或撤回；各入口核对已保存目标和原话身份，合法关联旧责任仍保留其原 origin。撤回先保存意图，再查原队列，只有准确原项才能被控制；同名 ID 本身不是关联证明。

忙席位或准备等待时保留原登记，点击“继续原工作请求”沿相同 ID 明确继续；刷新、冷重开和读报告不新增模型输入。已发/未知不换 ID。撤回先保存取消意图，再由原队列核确证未发的请求，最后登记与派发检查仍会复核；已发或终态不能假装未发撤回。“停止原实施后续动作”沿原实施停止，“停止本轮”只处理秘书持有的轮次，不偷偷终止已独立开始的实施。

取消意图不等于撤回成功。已发或未知导致撤回被拒后，页面仍按原执行和资源状态继续读取完整结果；原资源尚未核清时单独显示，已核清的终态及从未登记原实施的取消意图不会持续空刷新。

新秘书输入使用当时的项目角色选择，已登记输入和捕获不换模型；实施者沿原执行配置、权限与预算。费用证据过期保持等待，不刷新时间或切付费渠道。此代码的首条有限组合使用协议模型、真实 Git/SQLite/HTTP/进程及已有 Docker；正常安装的真实模型路径、浏览器视觉与本人接受分别留证。
