# 同序 v2.4｜完整产品体验（候选）

> v2.4 候选的收尾修订，不新增 v2.5。本说明描述成功开发后的完整体验；PR #11 仍待审，当前 main 的 v2.3 不因此改变。仓库和原型修补不等于真实服务上线，未启用的保护／身份隔离必须保持可见。

**你掌握目标、组织方式和委托边界；工作秘书负责安排与跟进；技术Agent完成开发、审核和交付。** 本文是完整开发成功后的目标体验。目前仓库交付设计、prompt及离线界面，不是已经上线的AI服务。

Issue 是一项开发任务，PR 是等待审查和合入的代码变更。一批用户成果可以涉及多个 Issue，一个 Issue 也可以分多次交付；你不需要按内部拆分逐项批准。

## 1. 打开后，你看见的不是一堆待你批准的PR

首页先回答：这一批要做什么、不做什么；现在有什么可以实际使用；哪些事情超出了已给的权限；你调整的安排是否生效；代理自行处置过哪些值得抽查的事。

五个直接入口是「本批目标」「组织方式」「委托与停止」「成果验收」「复盘与抽查」。下面是工作秘书对话。原来的「项目总览」「任务／会话／PR」「通信与交付」继续存在；细节按需展开，不要求你读完全部聊天或每个PR。

你既能说话，也能自己点按钮。两者调用同一后台；秘书离线时，查看依据、改变安排和收回委托仍然可用。它不持有只有它知道的目标或权限。

## 2. 系统里谁负责什么

工作秘书默认是独立Codex会话，经本地Codex App Server接入。它读取状态、联系负责人、分派已明确且获准的工作、跟进和汇报。它不写业务代码、不跑测试、不作技术验收、不批准或亲自合并，也不拥有任意shell。

每个Issue有技术交付负责人，使用Codex或Claude Code；子任务可同工具另开会话、换工具，或进入原负责人待办。原生工具继续承担编码、终端、调试和内部子代理，同序不复制一套IDE。

独立审核按采用流程使用新的上下文；默认Codex正式审核，需核实时Codex查事实、Claude Code查影响。PR接收／集成Agent默认使用独立Claude Code CLI，判断交付和最小安全合入范围。普通后台投递消息、查权限、执行获准操作并回读结果。

角色不是九个永久在线进程。一次简单修补无需走所有角色；整体复盘复用新鲜独立审核模式，不另开常驻“总审计师”。默认引擎是产品分工，不是模型优劣结论；实际版本、认证与费用在接入时验证，不保证CLI免费或任意订阅均可使用。

## 3. 你有新任务时，怎样开始

你说：「新增历史财年导出，先和现有单公司任务协调，不增加业务调用费用。」

秘书保留原话与限制，找到相关A、B负责人。新负责人可以调查，不能立即写冲突的共享部分。A、B核对已经提交和正在修改的工作，再判断三种方式：可以独立并行；共享实施按阶段先后做；高度耦合则合并到一位负责人。

你采用的是一批成果及边界，例如「指定公司和财年，输出正确CSV与出处；不做跨年份对比，不增加费用」。团队在这个范围内确定接口、消费者、测试、写责任及合入顺序，不需要你给每个子Issue重新签字。技术约定与本人采用在页面中分区。

若你说「A、B先后做」，工作台会显示精确效果：B的共享实施等A1接口及证据到位，独立调查继续。它不是只发一条提醒。若选择统一负责人，原写入者必须核查并安全交接；未知状态不能直接夺取现场。

## 4. 开发中，Agent怎样沟通

任务Agent主动联系彼此，普通后台按任务和角色找到准确原生会话、投递、取回执；不经过秘书逐句批准或摘要。同工具可靠原生通道可复用，跨工具由适配层转交。

GitHub保存正式记录，不作为所有日常聊天的中转站。技术澄清走工作台；正式范围、交付、退回和验收在原Issue／PR，随后发引用通知。评论已发布不代表会话收到；消息送达不代表消费验证通过。

接口、失败含义、来源、保存／复用或新的实质反例改变时，通知相关人重核受影响部分。无关工作继续，没有固定“每小时汇报一次已收到”的仪式。秘书只跟进阻塞和需要你决定的事项。

## 5. PR由谁收，什么时候合

作者提交建议及真实证据，消费者核对依赖，独立审核检查代码；PR接收者决定当前候选怎样接收和合入。后台再次核对当前版本、真实目标、必要检查与有效授权，执行并读取结果。秘书只能联系与催办，不能签技术PASS或直接merge。

默认按事件与条件推进，不到点全部合并，也不等整个Issue完成。例如X由两个Issue共同交付：A1增加兼容接口可先合；B1只等A1而不等A整个Issue；A2接通用户入口，等待B1及组合验证。无关A3按自己条件交付。

如果分开进入主干必然损坏系统，先调整兼容拆分；仍不能安全拆开才使用最小集成候选，一次主干更新交付。两次快速合并不等于同时生效。所有相关PR合入也不自动意味着X用户目标完成。

## 6. 你日常怎样控制项目

「本批只做单公司，历史扩展放下一批」：锁定当前成果边界。新X2不会悄悄扩大X1。

「A、B共享改动串行，资料准备继续」：实施阶段受具体门约束，不停止所有工作。

「先别开新任务」：停止新实施，已有运行保留并按安全方式收尾；没有假装已杀掉所有进程。

「收回自动合并，但开发和验证继续」：阻止新合并请求；已发送或结果未知的请求继续核查。恢复新开发不自动恢复合并权限。

「这个扩展不值得，停止继续投入」：停止本批未开始部分，保留已经交付的代码、成果和证据。运行中的副作用需要核查，不自动回滚。

「给我能实际用的版本」：返回真实入口、示例产物、独立验证范围和限制，而不是只报测试数。

只读、逐次确认与有限委托都可使用。边界内正常技术选择不找你；改变目标、可接受失败、费用、权限或正式启用等才在后果发生前让你选择。秘书呈现各方依据、选项、成本／风险和受阻塞范围，不用自己的总结证明你批准了。

## 7. 怎样验收，以及怎样知道委托可靠

你在末端看真实用户路径、结果和限制，决定成果是否值得接受。重复检查、原件核对、领域验证可以委托独立执行者，不要求你亲手跑所有测试。技术合入、用户场景通过、入口启用、正式采纳和部署是不同状态。

工作台把一次重要判断与后来结果连起来：放行后有没有可复现漏检；finding是否被反证；某次升级其实是否在原授权内。记录候选、任务风险类型、模型／提示版本、实际观察范围和严重程度。没有报告缺陷不算准确，小样本不给精确可信率，不把不同难度任务做模型排行榜。表现好也不会自动扩权。

一批实际交付后、重复出现跨任务问题或你提出要求时，可以安排一次独立整体复盘。比较上一批已接受的目标和规则、累计变更、当前行为及文档，查重复抽象、分叉约定和范围偏移。只比较当前代码与当前文档不够，因为它们可能一起偏了。缺基线就说缺基线，不宣布没有漂移。

文档中，人的稳定边界、团队技术约定和事实说明各有变更权限：技术事实纠错不需要你每次“修宪”，但改文档也不能自动批准改变产品行为。

## 8. 出问题时怎么继续

会话断线、投递或合并无回执，先查原对象，不重新派发或重复副作用。界面显示未知、待核、已发生，不把请求当成功。实际合入与受测内容不一致，保留已合入事实并补实际版本证据，不自动回滚；错误目标不能靠补测试追认。

秘书停止不影响已有授权任务、消息和接收，恢复时重读正式状态与未完跟进。关闭浏览器不是取消任务；本地主机关机不承诺持续运行。原生不支持的控制不会伪装成有效按钮。

## 9. 什么才算同序成功

不是Agent更多、消息更顺畅，而是人少作机械决定，方向控制仍有效；已知问题更早被工具发现，必要判断有明确责任，交付等待减少，严重遗漏没有增多，维护同序没有吞掉节省。

第一版是单用户、单仓库、单台已验证主机。先交付只读和接收能力，再接两种原生执行器，最后完成秘书与协作界面。W0 现在按当前有效 #2 调查，和 #10 的治理核查并行，不等本候选或全部设置完成；下一份反馈应来自真实 W0 交付，不再先扩写下一版设计。现在的离线 HTML 用虚构数据演练这些交互，不是已经上线的真实秘书。

## 10. 谁能改工作台的规则，保护怎样逐步启用

治理页把规则文件、服务端要求、执行身份、本人批准和实际验证分开显示，不用一个“已安全”掩盖缺口。审核与接收 prompt、产品说明中的控制承诺也属于本候选的保护路径。Agent 可以在分支中提修改，但不能用自己新写的规则批准本次请求。

初期可以先启用“主干变更要求 PR、禁止强推／删除、管理员及 App 不享有操作绕过”，暂不要求批准。这个阶段让变更路径可见，**不能保证只有你本人能够合并**；同一有权限身份仍可能请求合并，代理不得把“技术上能做”当作你允许做。界面应显示“路径约束已核验／人工批准隔离未完成”，而不是全部绿灯。已有更强规则不能被自动降低。

随后核验独立的 App 安装身份、最小权限和不会回退个人凭据；CODEOWNERS 进入目标分支后，再启用边界文件必须由本人审核，并验证拒绝和合法通过。使用 CLI 或连接器本身不决定身份，实际凭据决定操作归属。当前共用用户署名的写入按代理代笔记录，不拿它自证本人批准；代理不获得你的管理员 token 或 App 私钥。

首次 #11 的安装只针对你核对过的最终候选，由你亲自作出限定采用与合并。系统记录来源、实际版本、当时尚未生效的保护及接下来要启用什么；合入文件不等于设置已经启用，也不产生以后跳过规则的特权。若有效规则暂时不允许，保持待处理，不自动关保护解锁。

当前没有完成真实服务器保护和身份隔离。#10 负责这两步的实际设置与验证；W0 的只读调查不等待它们。普通 Issue 更新与评论依据明确委托办理，不为每条交接建一个 PR。代码和版本化规范仍经 PR。

## 11. 本批有真实位置，决定可以复用

本批默认使用 GitHub Milestone 分组，主 Issue 保存你的采用边界、团队约定与验收。秘书点卡片可以打开原对象；描述被修改、Issue 被挂入、Milestone 被关闭，都不等于你批准了新目标。长期任务涉及多个批次就按成果引用，不为满足单个归属而复制整项任务。

你已经作出的有效决定可以在项目 decisions.md 中索引。秘书与负责人先找相同适用条件，再告诉你这次引用了哪条、有什么差别；不把一次允许增加调用解读成以后随便花费。不适用但仍在技术委托内由团队处理，真正越界才来问你。页面区分原始采用、代理复用与待采用建议。

`TX-DEC-001` 已准备为未来维护委托草案，目前是 proposed，不能被用于自动授权。你可确认代理起草的具体边界、版本、期限，无须亲自打字；过去一次“可以改仓库”不会被追认为永久授权，合并草案文件也不等于采用该委托。

## 12. 你确认的是一个具体变化

你说「B 等 A1，材料准备继续」，秘书呈现：B 的共享实施由可并行变成等待 A1；资料准备不受影响；正在运行的工作不被强杀；本批版本和引用依据列明。你确认这个结构，而不是盲信一段“我明白了”。确认前目标或权限变了，系统重新展示差异。

「暂停新合并」是明确限制：经本人认证后立即阻止新请求并回显，不再等待秘书二次确认。它不声称撤回已发请求，也不自动回滚已合未发布的代码。恢复和扩权仍按明确对象确认；查询、定向澄清和已授权低风险安排不反复打断你。

## 13. 同一个按钮，可能产生不同后果

PR 面板显示后果：仅改变受控分支，还是会自动部署、修改数据、对外发送或触发付费消费；可回退什么、无法撤回什么、哪些尚未知。委托同时限制动作、对象和后果，不是只看“merge”这个词，也不把几个风险数字相乘当真相。关键后果未知时，相关高后果动作等待核查，不让无关只读任务停工。

## 14. 换模型与抽查也有具体流程

某角色的可观测模型、提示或工具变更后，界面显示“该角色等待有限回放”，而不是把所有历史信用清零。先选少量真实已知候选作为哨兵，观察过去的关键通过、拒绝和反例还是否成立；三五个样本只是起步，不是全能准确率。缺版本或样本如实显示，成本仍在原预算内；只对受影响角色按既定策略临时限制新高后果动作。

除高风险检查，还从正常放行候选中随机选取底样本。复审者先看相同代码、契约和原始材料，不看原先 PASS／风险标签，独立回答后再对照。随机不保证抓住全部盲区，换一家模型也不保证独立；它提供额外发现机会。比例和预算由已有策略控制，重复事件不反复抽签，未执行不会记成通过。好成绩不会自动扩大权限。
