# 证据不足后的原任务补充

接续 #5，固定前置 PR21 `4629c000ec4d4b9ad5476cecf6ece4637e96043e`，真实目标 `feat/w3-native-reception`。首条真实接收已返回完整 `INSUFFICIENT_EVIDENCE` 并写回原操作；其中部分检查早有准确 H 的原始记录，但未装入输入。补充应解决“原件未交付”，不能改成测试没执行、重复烧额度、删除第一次判断或绕过同包不重发限制。

NS01 可信操作者显式提供原 operation、准确判断 ID/binding、补充来源与原因及固定文件路径/hash。仅允许对当前候选已经完整返回的 `INSUFFICIENT_EVIDENCE` 补充；活跃、未知、被新候选替代或原字节损坏时拒绝。报告本身不授予权限、不选择文件或程序。

NS02 在原 SQLite 中创建同 item 的下一份 packet，固定候选、原 W1/W2/context 原字节不变；新材料以不可变 blob 保存，链接前一 packet/operation/完整判断和补充清单。新增内容必须有此前未交付的字节；改原因、顺序、文件名、接收时间或 JSON 重编码（键顺序、空白） 不构成新补充。相同补充重复提交返回原 packet，不创建新操作。最多两次补充（含首次接收共三批）；不能无限补核。

NS03 补充只登记，不启动模型。普通 run 随后消费准确当前 packet，仍经原前置、三类停止、候选、席位和目标占用门。一个 packet 至多一次接收；旧结果只属于旧材料，新结论独立保存，不覆盖旧报告/捕获。新证据的时间不假称新 W1 远端观察。

NS04 新字段需显式闲置启用 schema5，沿用原表。旧客户端不得在忽略补充材料后启动接收；包括启用前已打开的旧连接。新增接收绑定当前 packet fingerprint，数据库保护阻止缺这个绑定的旧派发。原 schema3/4 默认可读不隐式升级，原完成操作恢复仍可核。

NS05 验证相同任务补原件→下一 packet→独立接收→新判断的真实路径；首次证据不足与原始捕获保留。安全夹具核重复/重编码、候选变化、未知或活跃操作、停止投入、旧客户端、损坏材料、批次上限。测试、技术复核、实际模型判断及生产合入分开记录；仍不授权 main/merge/自批/部署/新费用/SEC_metrics。

最小入口：`receiver-cli enable-supplements --store ABS_QUEUE` 后，`receiver-cli supplement --plan ABS_SUPPLEMENT_PLAN`。计划仅接受固定元数据和内容引用；返回新 packet 和原 item，再由既有 run 入口实际消费。补充和新运行分别记录；重复登记不是重发。

补充去重只比较文本原字节与 JSON 规范化内容，不能理解任意自然语言或包装对象的语义。操作者须选择与原缺项有关的真实原件，不能增加无关字段触发新模型任务；模型无补充/派发工具。

补充计划使用 `schemaVersion:1`、`kind:"tongxu-receiver-supplement"`、`store`、`operation`、`judgmentId`、`bindingHash`、`source`、`reason` 和 `material:[{name,path,sha256}]`。身份须来自原操作的完整已存判断；path 是现有私有普通文件的绝对路径。最多30份UTF-8文件，合计768KiB；最终模型输入仍受既有1MiB上限约束，不静默删减。名字和说明仅为数据；不变更候选、S/r、工具或权限。原输入hash/绑定、完整原判断和新材料一起进入新接收的绑定，原输入全文继续保存在同一库中。
