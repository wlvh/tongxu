# 来源补查后的正常接收入口

本项落实 [Issue #73](https://github.com/wlvh/tongxu/issues/73) 的一条限定路径：一个已配置项目、一个已验证候选和一个受支持独立技术接收。现有补查和受治理接收后端继续负责材料、授权、资源和原捕获；这里接上正常任务页，不新增队列、账本、后台服务或 PR 正式审核循环。

## 使用

安装者先在 `tongxu-controlled-workbench` 计划中一次登记 `receptionControls: {path, sha256}`。原 `sources` 仍定义可选任务；选中项目只能打开属于其仓库的来源。配置不是查看标识，也不产生本人授权。

用户选择项目、打开原任务，在“来源补查与独立技术接收”点击“补查来源”。这一步只读来源和更新原材料，零模型输入。若评论新增反例，当前 packet 变化，旧报告仍可读且不再代表新材料。核当前对象后点击“接收当前材料”；条件齐备才进入原接收。完成后点击“查看原接收全文”，读取经过原捕获校验的全文，不重新发送。

发起新接收前，可在项目“AI 与角色设置”为“独立技术接收者”选择已检测的 Claude 或 Kimi。安装者必须已登记适用的[费用证据和原接收条件](governed_reception.md#选择-kimi-独立技术接收)；保存设置本身不启动模型或扩大用量。旧模板默认仍是 Claude，不随其他消息或影响角色的选择变化。

仅 checks 更新不新增不必要的接收。来源暂不可用时阻挡新发送；恢复且材料没变时复用原结果。H/B/目标变化须先由原候选入口重新固定并验证，页面不会暗中替换候选。技术判断 `ACCEPT_WITHIN_SCOPE` 不表示正式 PR 审核 PASS 或本人接受。

## 安装配置

目录格式为 `schemaVersion: 1, kind: tongxu-reception-controls, entries: [...]`。每项包含唯一 `id`、对应 sources 的 `source`、已固定 `{path,sha256}` 的 `template`、已采用 receive 确认或委托的摘要 `authorization`，以及 `budgets`（每项 `ledgerId/resourceRef/unit/quantity`）。模板是既有 `tongxu-queue-receiver` 计划，store/item 必须匹配原来源，不能预塞另一个 operation 的 governance。具体 CLI/计费/路径要求沿 [native_reception](native_reception.md) 与 [governed_reception](governed_reception.md)。

新材料接收从原本人来源重读已采用范围/确认或委托，给当前 packet 的原操作准备准确 receive action 和资源请求。旧一次确认已消费时保持等待，须当前动作的有效许可；模板或查看标识都不能替代。真正发送前的来源、停止、撤销、资源守卫仍由原 receiver 执行。用户不需要逐轮生成计划、搬报告或输入内部 ID。

## 等待与恢复

页面显示当前原接收阶段与具体拒绝原因；同项目请求失败的原因在本次状态刷新后仍可见，切换项目后的迟到回复不提示到新页面。缺许可/资源、停止、撤销和来源失效只限制受影响动作；补查和读取历史按原权限继续。

已有原接收记录时，按钮显示“查回当前原接收”，沿同一 operation 核原进程和原捕获。停止新增投入仍可查回；停止期间没有原接收记录的新工作继续禁止启动。原控制器仍在处理时等待，原结果不完整时保留未知，不换 ID 重发、不自动退款或释放未知资源；完整匹配结果可以关联并完成原资源结算。返回后仍保留原报告和旧输入。关闭页面不表示模型已停止；重新打开核原状态。

原接收先于来源刷新和当前 AI 设置查回。若计划已经保存、模型尚未发送，也继续该固定计划；准确字节先绑定在原队列中，文件丢失可从原绑定恢复，文件变化或没有原绑定则拒绝，不用当前设置替换。新的模型偏好只作用于尚未固定选择的新接收。原 Claude 请求因服务端403失败时，选中 Kimi 不会将它重发。来源或新设置暂不可用不抹去已发送的原请求与原捕获。

源码基线 `e003a947ca3fecb630c37d18b6a927689b96823a` 已有 sourceTick、受治理 receiver 和后台组合测试；原 WorkbenchPlan/路由/页面未装配这条一般接收动作。该调查与新增场景限定证明这处连接，不能推论其他接收或后继链都缺失。新入口以明确模型/本人/来源/资源协议样例核本机 HTTP、SQLite、实际子进程和原报告。另一次正常入口真实 Kimi 接收已取得 `ACCEPT_WITHIN_SCOPE`，实际使用真实 GitHub/Owner 来源，并核完整原输入、输出、报告及重复回读零新增输入；详情见 [有界真实演练](formal_pr_review.md#有界真实演练与待验范围)。该次接收前的材料变化为 H1→H2 和同 H 的 PR 正文修正；#73 AC02/AC07 写定的“新增反例评论后再接收”精确真实场景仍待验。协议样例和这一次接收都不能代填该场景或 #9/F12 的其余范围。
