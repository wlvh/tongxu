# 读取真实协作与修复记录

本片段接续 #9/#4：既有工作台和秘书查询现在从同一队列快照读取所选任务的协调、消息、受管修复及资源结算。它不启动模型、查询供应方、清理资源、改写停止状态或批准候选。

普通状态只提供准确的任务、运行、消息、会话、当前性、阶段前置和原件摘要。它不返回任务正文、完整报告、私人文件路径或其他未选任务的材料。完整消息按所选 item/run/message 的准确接收角色单独读取；仅知道同队列的运行编号，不能取得另一任务接收的回复。报告包含原最终全文，始终按文本显示。

界面分别呈现发送登记、送达、回复与材料消费；运行结束和完整捕获另列。`Reply` 是已登记回复，不自动表示整个工作包、正式接收或合并条件完成。历史候选、历史安排、已被替代的准备和当前材料分开。原件损坏显示无法读取，不退回缓存的成功结果。

资源已释放与本次执行结算仍按后端凭据分别判断；尚无匹配 outcome 时页面保持未结算。查看、刷新和秘书查询不向原 provider 发出请求。修复面板显示原操作、修改前后候选、实际测试结果和新候选审核引用，私人差异、路径及原测试输出不进入普通状态。

`owner_backlog` 目前表示按登记角色依次处理的新受管上下文，界面明确没有据此证明已经联系外部原负责人或接入其原待办。新上下文接续也不显示为恢复了原生旧会话。后续真实联络、可执行秘书安排、五类人控制、成果接受和 X1/X2 仍需独立接入；本片段不把只读显示当作这些能力已完成。

运行入口继续使用 `node dist/src/workbench-cli.js --plan ABS_PLAN`。服务器只绑定本机回环地址，查看钥匙保留在该次入口的 URL 片段中；原有访问、同源、只读及文本渲染约束保持。无需安装或部署服务。秘书的 `tongxu_task_status` 返回同一后端投影，不再依据页面摘要猜测协作状态。
