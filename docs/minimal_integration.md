# 必要最小集成候选与成员返工

接续原 #4/#5 的 G05、T12/T40 和 #34 留存的组合集成缺项。已有 W2 有序组合、组合接收、单 PR 受管合入、成员来源和原修复执行器继续使用。本增量解决“已知必须一起交付的几个固定成员，怎样形成一个独立可核验的候选”，不重建调度器或通用依赖分析。

当前分支 `feat/w3-minimal-integration` 从 Draft #46 的准确 H `35d3d8932e2378119fab6ced816da4d23bd1661e` 建立，真实 target 为 `feat/w7-delivery-assessment`。这是当前综合源码基线，不要求先取得前置整个 Issue 的完成或真实本人接受。将本子范围写回原 #5 并读回后编码；本文件是实施契约，尚无新执行或集成完成声明。

MI01 固定有界集成请求：同仓库、实际目标、起始 B、所选有序成员 H 与原材料摘要、范围和安排、为什么兼容序列仍不足、允许的受管输出位置。最小集合由明确选择和独立核实确定，程序只保证忠实使用这些成员，不声称自动求出所有可能方案的最小解。不从模型报告采纳命令、路径或新权限。

MI02 在独立受管现场重建所选成员的准确 Git 对象和最终树，形成可供后续审核的单个集成候选、完整差异和来源清单。作者分支、工作区、索引及未纳入内容不变。单独成员与中间前缀的失败原样保存；生成候选不等于接收通过，不得为获得绿色而删除这些结果。新候选有自己的 H/B/T、验证和独立接收，不借用某个成员的 PASS。

MI03 组合存在已核实问题时，明确影响成员、准确当前候选、允许路径和写责任；将限定任务接入原修复执行器。未知或活跃原写者不被接管，组合报告不能单独授权写入。成员得到新 H 后，旧组合、旧判断和原失败保持历史，重建受影响组合并对新候选验证、独立再审；不把修补某个成员视为组合已恢复。

MI04 需要向目标交付时，把准确集成候选及原组合来源交给原受管合入消费者。原本人来源、独立接收、当前 B/H/target、唯一目标责任、停止条件和原资源均须成立。一次目标更新使用一个准确请求；不得将两次成员合并伪称原子。当前用户边界不授予真实主干合并，本轮用隔离仓库和原明确假服务验证软件，真实来源不足只暂停相应远端动作。

MI05 所有准备、构造、修改和发送继续沿原 operation/events/blobs/claims 机制关联，重复读原结果。候选变化、旧来源、文本冲突、语义失败、部分修改、已发未知及失回执都有准确状态。先查原操作和已发生副作用，不删锁、换目录或重发掩盖未知；确认结束并完成显式交接后可继续。旧消费者不能忽略新增集成前置而放行。

MI06 在明确隔离测试仓库中保留“分别提交不安全、所选组合可用”的实际 Git/测试证据，以及组合反例导致成员修补、新候选再审和单次目标更新的完整链。核作者现场、未纳入变更、失败后恢复及重复零新动作。真实 Agent 与过程夹具分别标记，退出 0、模型意见、独立接收、实际目标变化和本人接受分别记录；必要的真实执行仍在现有订阅和工具边界内进行。

交付维持独立分支和 Draft PR；不 main/强推/合并/自批/管理设置/部署，不迁移认证、启用额外额度或操作 SEC_metrics。此处的接续不关闭原全部 52 场景，也不把 G06/G11/G14 的持久会话、完整责任接力和用户旅程缺项隐去。

构造入口为 `node dist/src/integration-cli.js run --store /绝对队列路径 --request /绝对请求文件`。请求固定原组合 operation、subject、S/r 和对象来源；输出位置由原队列派生。程序从原 events/blobs 保存完整来源，在私有仓库构造只有一个父提交 B 的候选。它只读取作者仓库对象目录，不加载作者 Git 配置，不拉取缺失对象，也不修改作者分支或索引。命令、标准输入、原始二进制输出、结束记录、完整 diff 和 bundle 都保存。

`state --store … --id …` 只读状态。`reconcile --store … --request …` 消费原完整捕获，既不重新执行 Git，也不发送模型输入。原请求已经成功或明确失败时重复入口返回原结果；确定尚未开始才可 `close-unstarted`。部分捕获且原执行无法确认时仍是 `started_or_unknown`。已确认结束的部分执行接续和组合成员修复仍待实现，不能据此宣称 MI01—MI06 全部交付。

构造测试使用明确的隔离仓库：生产端和消费端单位分别变化，单独成员与中间前缀失败，组合通过；同时保留作者额外提交、暂存内容和未暂存内容。执行的是实际 Git 与 Docker，模型均为零输入。另覆盖明确失败、实际启动边界撤销、完整捕获后的消费中断恢复、未知原执行拒绝、作者配置不加载及缺失对象不自动补取。原失败输出与成功输出分别保存。

新候选使用独立 PR 与自己的 W1/W2 材料进入原队列。`attach-candidate --store … --request …` 接收固定的 `tongxu-integration-candidate` 请求（integration、item、packet、fingerprint、source），核对准确 H/B/T/target、原 S/r、单候选完整验证，以及 PR 不冒用原成员身份，再创建保留原材料的关联 packet。这个入口不发布 PR，也不把私有 Git 对象称为已发布 PR。后续原接收入口自动交付集成原因、完整 diff、原组合和失败原件，并要求准确的 `consumedIntegration` 回执。成员新 H、原来源或范围变化使旧判断失去当前适用性；原报告保留。

原受管合入入口要求新候选本身的接收、准确 `integrationReference`、当前本人授权和资源及唯一目标责任，原组合路由 PR 仍不得直接合入。明确隔离的实际 Git 目标与本地假服务验证了正常的一次目标更新，以及更新后失去 HTTP 回执时仅回读原操作、不再 PUT。此处测试的模型、Owner、资源和发布服务均是夹具，目标是本地隔离仓库；不表示实际 GitHub 合入或本人验收。

格式 18 保留此前实际启用的队列能力和完整历史，增加集成关联及消费者检查。旧接收入口不能忽略关联材料或跳过当前来源检查，旧修复入口不能直接把集成候选当作一个成员修补。一次性 test 授权在原 events 上跨集成构造和交付验证入口唯一绑定；已消费或未知的原动作不能换入口再投入。进程记录自身结构及准确字节由结束记录绑定，损坏时保留待核，不以其他输出完整替代。

旧版本已经登记、尚未开始的请求沿用同一请求和原材料；新版本在实际 `start/effect` 的事务内也核查并安装上述约束。仅有登记时检查不足以覆盖升级后的续跑。真实旧版本回归可用 `TONGXU_TEST_LEGACY_INTEGRATION_ROOT` 指向保留的 `852d1cd` 源码及其已构建 dist，核验“旧 prepare → 新 run → 旧第二消费者被拒绝”。单纯回读已结束结果不会自动升级历史库。
