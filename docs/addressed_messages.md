## 当前入口与结果

运行 `node dist/src/message-cli.js run --store /绝对/原队列 --plan /绝对/消息计划.json`。`status --store … --run 准确计划哈希` 只读原记录；`reconcile --store … --plan …` 只核原捕获，不发消息。程序只使用计划注册的角色和执行器，不能把 App 的只读关联条目升级为发送入口。

计划包含 `participants`、顺序 `messages`、固定材料、现有计费边界证据以及可选的原协调授权 intent。每个参与者固定 item、角色、引擎、程序路径/哈希、MCP 禁用清单和允许的准确原生指令来源。reviewer/verifier_fact 使用 Codex，verifier_impact 使用 Claude；均无模型工具。`parent` 表示计划中任务的父子关系，不宣称它是原生引擎创建的子代理。消息 `from=null` 是操作者计划输入，其他 `from` 必须引用该角色已经返回的完整报告；程序如实记录自己转交报告，不伪称模型主动发出了操作者编写的话。

Codex 使用一个仍由当前控制器持有的独立 App Server 会话接收后续轮次；Claude 使用固定新 UUID、stream-json 输入与用户消息回显核对。注册的原生 ID、输入摘要、接受的 turn/消息 UUID、完整最终回答和消费引用分别保存。输入超限会等待处理，不截断上游报告。读取原件的来源校验不是对任意外部日志生产者的认证。

Claude 消息通道按实际协议分别支持 2.1.233 和 2.1.304，不按版本大小自动放行。304 使用 `client_composed=true` 传递原字面输入，额外核对 queued→started→completed 命令事件、最终结果的准确用户消息 UUID、无额外排队、无工具拒绝/安全中止/子代理执行，完成命令事件到达后才转交。原 233 输入格式和原捕获仍独立读取；新的消息通道适配不宣称旧单次纯文本 relay/receiver 的 304 路径已经实测。程序的版本、认证和执行预检均禁止自动更新，不改本机全局更新设置。

实际 304 同会话两轮捕获进一步确认：每条输入各有一条 init。实时与回读都逐个命令窗口核版本、权限、工具和会话；同一窗口重复 init 或下一轮权限变化仍拒绝。早期“全会话只能一个 init”的失败分类，仅在原件、退出和所有摘要完全相同、每条原输入及最终结果都经严格回放后，追加 `claude-304-per-input-init-v1` 核实记录；旧 ended 不改写，也不重发原消息。

- Held：尚未登记发送，等待前置、停止解除或有界输入。
- Unknown：发送已登记但未得到完整可核回执，保留原收件人。
- Delivered：准确原生 turn/start 回复或 Claude 用户消息回显已观察到。
- Refused：准确原生请求返回明确的无效请求/参数拒绝；不会把模型文字“拒绝”当传输拒绝。
- Reply：完整最终回答已观察到；`reportedConsumption` 另外要求正确消息 ID 和前序全文哈希。

`completed` 还要求各运行器的完整原捕获与成功退出均通过核对，不能仅凭 Reply、文件存在或退出 0成立。队列中的历史原件继续保留；若磁盘原捕获后来损坏，本次 reconcile 返回失败，不能靠重算摘要绕过原库对照。

转交前会核对已观察到的全部原生请求回复：同一请求的重复/冲突回复，以及没有对应请求的裸回复，均不能产生可交下游的 Reply。旧版本曾把完整的无效参数拒绝归为捕获失败；仅当同一原件、退出记录及全部摘要不变，且严格回放确认拒绝而无迟到执行时，追加 `message_runtime_revalidated`。原 ended、Refused 和历史问题均保留；这不允许替换未知收件者或重发原任务。

所有发送意图、回执、原文索引与历史尝试复用原 events/blobs。两个控制器不能重复派发同一计划；不同计划也不能占用仍活跃或未知的同工作项/角色现场。只在原件证明运行器已结束且完全没有提交模型输入时，允许后续同一入口最多三次启动尝试；旧捕获和原计划保持。已有发送意图的未知消息不能改地址或换会话重发。

启用了本人来源的队列还须重读准确来源，并匹配整个计划哈希、当前 S 和协调委托；报告没有权限。当前消息消费者遇到已配置资源账本会明确等待尚未接入的资源消费绑定，不能退回无账本路径。停止新增投入作用于后续新消息，独立原件读取照常；停止实施或合并不自动阻断只读讨论。

本批只有固定可信计划的有界只读消息流。任意旧 App 会话控制、运行器退出后的持久会话续接、模型自主选择联系对象、写权交接、配置账本后的实际消费及工作台按钮仍在原 goal 内继续。它们不因本子范围完成而改为已交付。真实模型成功路径与独立审核状态在固定候选的交付记录中单列，夹具不能替代它们。

## 仅完成最后一条尚未发送的消息

如果前序消息全部有完整回复、准确消费引用和严格核实的结束记录，仅最后一条尚未登记发送，可使用 `node dist/src/message-continuation-cli.js prepare --store /原队列 --plan /原计划.json --request /接续请求.json`。`run` 使用同样参数执行接续；重复入口先核原捕获，已经发送的任务不会再发。复制队列可用于独立检查，但不能取得原队列的控制权。

接续请求固定 `schemaVersion:1`、`kind:"tongxu-complete-unsent-message"`、来源说明 `source`、明确的新上下文许可 `allowNewContext:true`、当前协调授权 `authorityIntent`、原格式的 `billing` 证据以及 `replaceKnownUnstarted`。它不能传入新的角色、程序、工具或命令。`prepare` 只装配文件并登记选择，不启动模型；有本人授权配置时，派发仍须匹配新计划的准确哈希。

程序自动保留原角色收到的完整输入、所有前序完整报告、固定材料和原会话引用。新消息要求模型确认这份材料包的准确哈希，程序另存实际接受的输入、原生会话、完整最终结果及退出。新上下文明示 `nativeSessionResumed:false`，原未发送消息、原收件者与历史失败不改写；`originalRunCompleted:false` 与接续结果分开报告。它不会把新会话称为原生会话恢复，也不会把报告文字当作权限来源。

同一原任务只有一个固定接续位置。并发控制器互斥；直接执行生成的计划也会锁定并重读原捕获、检查原候选。活跃、未知、拒绝或不完整的来源不能接续。只有原接续完全没有登记发送、其启动进程也已核实未发送并结束时，才能显式设 `replaceKnownUnstarted:true` 更新计费或授权前置，最多三个准备版本；所有旧版本保留。任一已登记发送的接续都不能换请求重发。完整原材料超过输入限制时会拒绝，不裁掉报告来凑成功。
