# 固定成果批次、实际验收证据与有权接受

接续原 #9、#8、#5 的 X1/X2 与成果控制部分，遵循 v2.3 的 T42/T43/T49；原全部52场景保持不变。固定源码前置为 Draft #44 范围控制候选 `9d862ef44031225cb4deaa0c6b1cc567b33f82fd`，新分支 `feat/w7-delivery-outcomes`、真实 target `feat/w7-scope-controls`。若前置有修补先核差异。本项复用原 QueueStore events/blobs、准确候选和本人来源，不另设授权账本或自动合并入口。

DO01 一批成果具有稳定身份、不可变版本、明确前版、采用范围、用户目标/非目标、成员候选及验收场景。登记时绑定原队列中准确成员/packet/材料摘要。X2新批次单列；同批修改须显式前版匹配，新scope须匹配新的有效采用。登记只是材料事实，不等于本人采用或成果完成。

DO02 原执行、场景验证和成果接受分开。实际验证记录绑定准确批次、场景、候选、原operation、执行方式、步骤/预期/实际和完整原件摘要。复用既有执行器和原报告；读一份报告只证明读取与判断，不伪装实际运行场景。外部导入声明明确标成未经执行层证明，不能把其PASS作为整批已验证。代码合入、启用、场景、接受/部署分别显示。

DO03 成果决定有接受、退回、补证据及停止后续投入四种结果，固定所选批次和证据集合。本人决定沿用原独立来源与新鲜读回；Agent文字、页面临时标识、一般技术接收和accept_baseline都不能冒充成果接受。接受不新增写权、merge、部署或费用。未满足的场景和当前性缺口继续显示，不由一条接受文字改成已验证。

DO04 用户可以在既有授权内委派重复/领域验证，执行者与接受者分开。程序准备准确材料并接原受限执行/结果消费路径，保留原run；不执行报告拼出的命令、不制造新权限。重复或中断先核原操作，未知不重发。真实来源/外部业务不可用时只阻对应动作，软件和明确隔离验证继续。

DO05 工作台与秘书读取同一成果/证据/决定原件，界面显示本批目标、可用部分、缺口和下一步；默认只读。人可以从固定入口提出明确的成果决定并看到待采用/已采用来源；本人身份不与秘书共享。原范围停止控制继续可单独使用，停止不清空旧成果、不杀未知进程、不退款。

DO06 实际覆盖：X1固定后新增X2不改变X1；获准范围演进使受影响旧证据历史化；全部成员合入仍无场景证据时不得完成；验证失败/补证据/恢复/有权接受各有准确记录；假来源、旧版本/旧证据、重复、撤销及模型冒充接受均被拒或保持未知。先完成软件及隔离全链，再按已有费用与可用身份取得必要真实证据。源码、原失败、独立复核、分支/Draft交付与本机接续均保留。

该片段不替代 G05 最小集成生产者、原外部写者交接或完整安装/升级/退出旅程；这些仍是全goal中的后续工作，不能改成已完成或全部外部阻塞。

## 当前实现与继续入口

首个实现检查点提供 `delivery-cli register --store <绝对队列路径> --batch <固定批次文件>` 和 `delivery-cli state --store <绝对队列路径> --batch-sha <准确摘要>`。登记使用原 events/blobs；查询为原只读事务。批次固定成员 packet/材料、场景和前版；相同请求重入不改历史，竞争前版只有一个成功。没有采用来源时是明确待采用材料；不能在同一批内偷偷改目标，新范围实际采用后可用新的固定成员继续。

批次登记基础已经独立修补复核；实际验证消费者也已接入。DO01–DO06 尚未整体交付：有权成果决定、领域判断和成果UI仍须接续。`scenarioExecutionVerified` 来自准确运行与场景捕获，`scenarioAssertionsPassed` 另列断言结果；`currentScenarioEvidence` 还核批次/材料/采用当前性。`userOutcomeAccepted` 目前仍为 false，只有后续相应有权决定才能改变，不由测试退出码推导。

## 程序执行、回读和恢复

`delivery-cli verify --store <绝对队列路径> --plan <固定验证计划>` 使用原W2的Docker隔离执行器：启动时固定原批次/成员、W1快照、受信测试计划与场景到结构化样本的映射；原操作先登记，再保存原W2运行、控制器/Node版本、关键运行模块摘要、工具命令/输出、受测HEAD/树及全部源原件。目录由原操作身份决定，调用者不能另指定重发目录。该入口只执行固定本地测试，不调用模型、不使用业务API、不授予主机写路径；已有Linux/bubblewrap验证入口保持原安排。

验证入口将原队列保存的快照原件复制到自己的受管目录，核原摘要并保留W1的raw/git布局。后续结果消费不依赖调用者保留原下载位置。已登记测试授权必须匹配固定background/test角色与准确候选；已有本人来源须重新读取，范围/候选/停止门在Docker实际start前的原事务内再查。没有本人配置的影子验证依旧不代表采用、merge或部署许可。

每个授权预留（`authorityIntent`）只绑定一个准确验证操作和计划摘要。即使旧操作已结束，也不能换id、批次X2或版本复用这次预留；有效持续委派可以为另一项明确验证登记新的预留。旧记录在首次新写入时核对原计划，保留原件和既有读取方式；数据库唯一索引及登记/启动门阻止已打开的旧消费者插入未绑定别名。新投入还必须核同一逻辑批次的旧终态原件，不能只看到result索引就继续。原件损坏时暂停对应新投入，恢复准确原字节后可继续原未启动请求。

`reconcile` 只回读原运行。完整执行后在结果消费前中断，可从同一个原run消费，不再执行测试。未知或缺失的启动/容器原件不能换id重发。确认原执行已经结束但测试失败时，失败结果完整保留，操作者可以显式登记下一次验证；它不会改写原失败。尚未启动的准备经原控制器互斥和原目录检查后可继续，或使用 `close-unstarted` 明确关闭；已启动/未知拒绝该关闭。关闭未开始的追加验证不消除先前有效证据。

查询原批次或 `validation-state --store <队列> --id <原验证id>` 读取原状态；登记、已启动/未知、终态已核、断言结果与成果接受分开。结构化样本是原测试器的断言，不是独立业务正确性结论；领域验证和有权成果接受继续是相应角色的后续步骤。
