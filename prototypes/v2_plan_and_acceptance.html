CHAPTER 02产品目标与四个交付阶段

2.1 产品是什么

同序是一个以交付为中心的本地协作台：Issue 说明要实现什么；PR 或固定产物承担具体交接；接收者判断是否达标；程序连接可确定的事实、证据、责任和队列；Codex、Claude Code 留在原生工具里调查、开发和验证。

它要消除的是人工找会话、重复填版本、复制长报告、追问谁负责下一步、反复核对真实目标，以及已获有限授权后仍无理由等待。它不消除业务判断，不以合并数代替价值，也不增加一个全局主 Agent。

**最终用户必须能回答六个问题：**现在什么可用；什么没完成；谁在等谁；哪个版本经过了什么验证；这次代码实际进哪里；哪项事情确实需要我决定。

2.2 分阶段交付，不把前置研究做成漫长门槛

2.3 首版不做什么

不做统一聊天、编辑器和终端；不做通用流程编辑器、通用依赖闭包免审器、自动扩写范围、自动 rebase 作者分支、多仓库多用户、跨主机调度、通用财务账本、订阅费用推算和每个子代理的永久工单。

不强制集成分支，不强制“每个任务一个 PR”，不强制每项交付都增加三个角色签字。**有限委托下的技术合并可以自动执行；无委托的合并必须取得具体确认。**两者与无条件自动合并完全不同。

CHAPTER 04权威与责任：每类事实只有一个正式来源

4.1 载体职责

项目接收索引 角色／授权来源、跨任务等待关系、正式交接入口 人工复制的全部 PR 动态和长报告

PR 是代码交付的主要交接入口，不是所有产物的唯一入口。没有 PR 的数据包或接口样例，先在关联 Issue／已有产物记录下交接；以后产生 PR 时引用原交付，不能复制出一套独立状态。

4.2 角色不是固定的常驻会话

产品负责人负责目标和超出授权的取舍。交付负责人负责实现与合成。独立审核者判断代码、测试、契约及复杂度。接收者判断本次交付是否能进入目标、协调剩余工作；不必新增一个全局上级 Agent。

每项未结束交付有一个下一步交接责任人，记录“谁／做什么／作用于哪个候选／缺什么／完成后交给谁”。验证可以并行；负责把结果收齐的责任不能悬空。机器步骤的责任可写为“接收服务，由接收角色负责处理异常”。

同一角色可以跨天持续，会话可以更换；独立审核不得继承作者工作对话。一个会话空闲不能说明交付完成，一个会话失联也不能取消其未确认写入责任。

4.3 防止摘要成为第二权威

当前状态在原 PR 正文中简短展示，关键事件在原 PR 评论／正式 review 留痕。可直接取得的 head、base、检查状态由程序生成，作者不再重复填。叙事、边界和判断由责任人写。

沿用目标 PR 模板，在既有 Review / Fix Record 内索引原始证据；不再新建一条同义“同序汇总评论”。程序只维护获准的正文区块，写入前重读；发现他人编辑则保留并重新合成，不覆盖整篇。该重读不宣称是 API 不支持的跨系统原子锁。实质变更后读回内容核对，关键更正用短评论指向被更正记录。

G1 在未获写权限时只导出更新建议。人工发布路径明确标“待发布”，不能因为本地产生 Markdown 就显示远端已更新。

CHAPTER 05任务分派前的共同验收

仅对跨 Agent、共享入口、保存／复用条件、旧状态兼容或真实热点变化补充共同验收。独立小修补复用现有测试政策，不增加普遍开工审批。

由开发负责人先写“我改变什么、什么不该变、怎样证明”；接收者补遗漏的消费者、反例和组合。双方使用一个正式 Issue 段落，不建立两份可漂移的契约。

共同交付：用户从哪个实际入口得到什么结果或准确限制。
分工：谁实现提供方，谁接消费者，谁确认真实组合。
必须一致：输入输出、单位／期间／来源、失败与拒绝含义、旧结果处置。
材料：固定材料位置与身份；作者、消费者、接收者均可取得。
验证：使用哪个已有入口，正常与关键失败场景；谁维护与执行。
预期差异：允许什么改变、哪些必须保留；其余变化需要解释。
合入与退出：哪些可独立先合，什么证据满足后共同交付才算完成。

先让最短的真实用户路径接通，再扩展公司、年份和异常。共享样例用于提前对接，但最终必须换真实实现，不接受双方各自对自己的假数据通过。

公共输入输出、错误含义、持久化／复用规则变化，或出现实质新反例时，重审受影响部分。代码未变但出现新反例，旧通过结论也可能失效。普通补链接、进度更新不自动重置范围。

**旧版是对照，不是正确答案。**成功变失败可能是纠正错误放行；失败变成功可能是删掉困难材料。验收要比较状态、内容、身份、来源和副作用，而非只看通过率。

CHAPTER 06交接只用两类结构，不要求重复抄事实

6.1 提交或返修

沿用原 PR 正文，保留以下信息；已由程序生成的项目引用它，不再人工填同义字段。

本次交付：实际改变、范围之外、用户入口。
受审对象：程序生成的 head、实际目标、base／受测组合、采用范围。
证据：命令与预期、固定材料、结果、范围、环境及原始输出。
独立性：作者自测／消费者复验／独立审阅，分别注明。
返修：回应哪条原反馈，已做什么，哪些旧证据仍适用及理由。
剩余：限制、需要决定的事项、建议的下一步责任人。

6.2 接收、退回或要求补证据

对象与结论：对哪个候选、哪部分范围接受／退回／待补证据。
已核对：本轮成立的证据；未来复用须满足什么条件。
仍失败：命题、触发路径、后果、复现与原始证据。
通过条件：怎样的最小充分修正或补证据可以重新接收。
下一步：交给谁；仅阻止哪部分工作；无关部分是否可继续。
建议：非阻断改进另列，不混入必须修复。

结构完整只能证明没有漏填，不能证明事实与语义正确。历史 PR 不因缺少新字段被一律倒退；W0 建立采用边界，新受管交接遵守该结构，旧记录缺项按风险补取。

**按类修复：**同类反复出现时，退回应指出共同失效机制、既有契约、当前范围内变体及有限通过条件。不能继续只补新词，也不能借此要求证明全部自然语言或扩出通用框架。第一次已看见根因即可按类处理，不必等固定次数。

CHAPTER 07从事实到动作：机械检查的正确边界

可直接机械确定 需要语义判断 程序不应冒充的结论
GitHub 实际 head/base/目标、提交包含关系、变更路径 是否拆分合理、额外提交是否符合交付范围 没有文件交集所以没有业务冲突
命令实际开始／结束、退出码、原始结果位置 测试是否检查了真正风险、异常是否合理拒绝 测试命令成功所以业务通过

证据与候选／输入／工具版本是否匹配 原证据是否仍覆盖当前主张 patch 字节相同所以自动免审
授权的角色、资源、范围、时效等字段是否匹配 新动作是否改变业务含义或超出原取舍 评论声称同意所以已有本人授权

影响脚本输出“已登记关系与潜在碰撞”，不是完整依赖证明。只读提示不要求开发者为每条建议创建 Issue。目标分支不符、证据对象不符、权限不符等可确定错误可以阻断；消费者是否列全不能靠非空字段断言。

新增长久检查须覆盖真实缺口；优先扩展已有场景。没有具体收益的声明、台账和重复检查保持不添加。

CHAPTER 08版本、材料与证据怎样固定

8.1 一份候选需要表达什么

候选 C 记录 repo、PR、源 head H、实际目标引用、观测目标提交 B、merge base、可选受测合并树 T、采用范围 S、适用政策／提示版本，以及本轮真实读取的材料位置。

代码和 diff 按固定 Git object 读取。PR body、Issue、授权文字等可变内容保存本轮快照及来源 ID／更新时间；远端变化时保留历史，不拼出 H1 标签配 H2 差异。只用 head 不能定位本轮全部证据。

8.2 一条证据证明什么

证据记录：候选或产物版本、运行的工具版本、实际输入／样本范围、命令或人工步骤、环境、预期、实际结果、退出码（适用时）、原始输出、作者与独立性、限制和副作用。

机器能从原生事件或工具输出读取的事实，不以模型文字替代。工具没有提供关键证据时显示缺失；模型生成报告不自动补出“零真实调用”“全部样本通过”。

昂贵测试可以复用有效证据或按明确风险抽样，但记录抽样依据与未覆盖项。廉价关键回归优先实际重跑。需要新付费调用时，测试授权与业务调用授权分开。

8.3 新鲜度与复用

新 H、相关 B、采用范围／权限改变，或新反例影响判断时，旧证据保留但重新判断适用性。原始证据可复用，不自动复制 PASS。重复 webhook、轮询和传输不启动新审查；同候选有新证据时允许合法重审。

只在候选真正进入接收或准备合入时集中处理 base 增量，不为每次主干推进重开所有兄弟 PR。添加本轮报告引用不导致报告自我失效；实质改写测试主张、限制、目标或范围才重核相应部分。

临时报告和候选材料放在仓库外；需要在 GitHub 交接的正式证据按项目已有政策归档。不能发布对接收者不可访问的私人路径后声称“证据可用”。

CHAPTER 09把已有验收工具接起来，而不是重造测试平台

G1 首先复用目标仓库已有的实际入口。SEC_metrics 的 D02 比较工具已由 #264 合入，可作为一项项目适配；其他项目使用自己的命令，不硬编码 D02、公司名或财年到同序核心。[S4]

同序只做：选择获准测试项；固定输入、代码与工具；在隔离现场执行；收集原始结果；把返回分类与限制呈现给责任人。脚本与临时组合中的代码均视为待审代码，不能拿发布凭据直接运行。

对照分类 接收时必须核对
SAME_OK 状态相同且相关内容／身份／来源相同，仍需知道比较实际覆盖了什么
CHANGED_OK 都成功但内容不同；不得吞成“无变化”
FAIL_TO_OK 新成功是否完整、正确，是否掩盖拒绝或遗漏
OK_TO_FAIL 是新回归，还是纠正旧错误放行
SAME_FAIL 仍未证明业务成功；不能作为正确结果计数
CHANGED_FAIL 失败原因是否更准确，还是更早失败掩盖原问题
NOT_COMPARED／工具故障／缺材料 未覆盖或执行不完整，不得算作 SAME 或 PASS

这些分类沿用 D02 工具示例，不强制其他项目采用同一业务格式。目标工具的 COMPLETE／退出码 0 可能只表示比较完整，不等于所有样本业务正确。工具定义的 fail-on 规则只形成告警或已采纳的限定断言，不能把“只准成功增加”推广为全局标准。

工具也要被验收：漏样本、空样本、工具异常、丢范围／出处、输入被改变，都应有可复现负例。首次看见某类工具缺陷时扩展原测试，不另建第二套准备流程。

CHAPTER 10接收状态与下一步责任

交付、运行、审核三层分开。运行完成可带来返工；交付已合入不等于正式结果已采纳。正式审核沿用 PASS / REWORK_REQUIRED / OWNER_DECISION_REQUIRED；解析失败是“没有有效判断”，不是第四种业务 verdict。

等待原因另附具体对象：等材料、等依赖、等审批、等外部服务。不能只写“协调中”。每个未完成状态都有责任与下一步；等待本身不能清空已获得的证据。

迟到的旧审核只能归档到其候选，不覆盖新状态。新的 PASS 不自动抹掉独立开放 finding；必须有适用的处理与复核记录。关闭 review thread 也不单独证明问题已解决。

CHAPTER 11队列：先完成交付，再增加开工

11.1 简单、可解释的次序

主干严重错误优先；随后处理已具备证据、只差有限收尾的交付及明确退回项；能够解锁这些交付的依赖可提升顺序；其他新候选按已批准优先级和等待时长处理。紧急插队写一句原因和接续点，不要求长报告。

等待上游的任务不占用“正在处理”的席位；其必要上游可以提升优先级，避免依赖永远排在被阻塞任务之后。老任务的等待要可见，不能因不断有新候选而永久饥饿。不中断正在运行的长验证，只在安全边界接续。

11.2 限制正在展开的接收，不限制所有等待项

试用默认可设同时最多两项实质接收、同一目标分支一个推进过程；这是可调整运行参数，不是产品正确性定理。只读或相互隔离的测试可并行，共享额度／工作区须另核资源限制。

接收积压时提示负责人先收尾退回项与已验成果，不把所有开发强制停掉。已批准的重要工作可以继续，但解释代价和原因。程序提供队列，Agent 处理业务优先级取舍。

11.3 事件优先，补查保底

复用已有 CI 事件、原生事件流、授权可用的 GitHub 通知。单机 G1 没有 webhook 入口时，以普通程序增量轮询和 ETag／游标补查，不为“事件驱动”先建公网基础设施。

活跃候选适度补查，空队列降频，故障退避并显示最后成功时间。周期由实际限流与反馈确定，不再写死每两小时启动一个模型巡检。超时触发提醒或核查，不视为默认同意、退出或可重复调用。

CHAPTER 12授权模式、身份与共享资源

12.1 三种运行模式

模式 可做什么 不可做什么
只读／影子模式 采集、比较、队列建议、生成待发布交接包 写正文、评论、分支或执行新增真实调用
逐次确认模式 执行本次具体获准动作 把一次确认扩大为未来所有同类操作
有限委托模式 在已核验委托范围内自动发布、技术合并或修复 越过目标／角色／费用／破坏性操作边界

没有既有委托就不自动增加。已有有效委托，不要求每 PR 重批；对委托的首次接入只核验来源、范围、执行身份和可撤销性，不将其重做成一项更窄的新授权。遇到冲突只暂停受影响动作。

#153 的书面分工允许接收角色在条件明确时进行技术合并，同时保留业务定义、新真实调用、采纳／部署和破坏性操作给用户。它证明需要尊重项目差异，不证明本次文档已经授权同序接管那个角色。[S3]

12.2 权限绑定动作，而不绑定一句话

采用委托时至少明确：来源、委托角色、仓库／目标、允许动作、作用范围、必要门槛、资源上限、是否有到期条件、撤销入口。实际请求绑定当前候选；有效委托不必逐 head 由人重签。

撤销、范围改变或授权来源不能确认时，未发送动作不继续；已经发出的动作先查结果，不能假装撤销远端已完成的副作用。决定已确认、实施证据过期时只重验落实，不要求 Owner 重选同一选项。

“技术接收通过”不是“业务采纳”，普通工具批准不是“增加预算”，机器人写下 Owner 已同意不是本人确认。多个 Agent 共用用户账号时，账号只能证明凭据身份，不能证明人的意图。

12.3 身份与执行边界

首版采用 A 档：防漏步骤、错误对象、重复动作和善意执行者顺手越权，不承诺抵御与平台同权限的主动恶意程序。只保护受管入口，不宣称全机进程锁。

G1 只读不需要先迁移所有现存 Agent 的账号。受管写入上线前，明确实际凭据路径并隔离人的确认与执行者。建议受限发布进程持有机器人／App 凭据；执行器只提交已定义请求，不取得任意 GitHub 代理。机器人身份本身不保证无法合并，仍须限制发布入口与目标规则。

核查环境变量、gh 配置、Git credential helper、SSH agent 和可访问配置；缺机器人凭据时不得回落个人身份。测试进程不携带发布／批准凭据。不能通过“这是测试”执行真实付费或破坏性操作。

共享 main 的推进过程只有一个；这不要求某个特定会话永不退出。交接时核对原操作、工作区、未提交内容、后台副作用与远端结果，确认安全后再移交。不凭租期到期或 heartbeat 消失自动抢占。

12.4 额度只认项目原账本

同序保存授权与账本入口的引用，不复制预算余额。授权、准备可执行请求、取得密钥、认领机会、实际调用、最终结果分别判断。未知或失败是否消耗机会由原账本政策决定，同序不擅自归还或生成新请求绕去重。

#293 的候选实现可用于理解预留／认领边界，但必须等其实际合入与执行路径核查后才能依赖；不把该固定 81 次模型／1 次 SEC 的项目配置写入同序通用核心。[S6]

CHAPTER 13分支、临时组合与实际合并

13.1 三种关系分开

父子 Issue 表达共同目标；实现依赖表达缺什么接口或产物；合入依赖表达进入目标前需要什么。数据包依赖不自动成为代码分支依赖，小任务也不强制独立 PR。

子改动可分别合入并保持目标正常，默认直接对实际主干或项目目标。只有共同启用才可交付或确需隔离组合验收时，建立集成分支。默认关闭开关和数据化登记不天然隔离影响，仍验证导入、配置、复用和旧路径。

13.2 真实目标与最终出口同屏

每个 PR 显示 source → actual target；同时给出共同交付最终出口与中间关系。发现实际 base 与采用安排不同，停止该合并并交责任人核对，不自动改 base，也不因为正文写了 stacked 就放行。

按实际提交／树关系展示本 PR 会带入的额外内容。叠放 PR 指向下层分支并非自动错误；错误是它与意图、验证或授权不一致。涉及额外未接收内容，必须明确范围与全部前置，不能借一次合并请求隐式批准别的交付。

13.3 构造临时组合，不重写作者分支

固定 B 与 H，计算合并结果 T，在隔离 checkout 运行测试。git merge-tree --write-tree 是可选基础能力，它不修改工作区或 index，但会在 Git 对象库写入树；需要实测当前 Git 版本、冲突输出和仓库策略。[S7]

只在平台自己的隔离对象库／测试目录操作。不自动 cherry-pick、rebase 或 push 作者分支；文本冲突交回对应责任人。语义组合错误即使零文本冲突也会阻断相应交付。

记录 B、H、T、合并方法、工具环境、输入与测试入口。代码树不能代表依赖包、运行环境、外部数据或构建中读取的提交身份；测试会读取 Git 元数据时，必须核对临时候选与真实合并方法的差异，不能只看树相同。

13.4 审核与集成验证不是一回事

正式审核面对固定代码候选与契约；集成验证证明与目标的具体组合。各子 PR 已 PASS 可以复用局部证据，但最终组合仍需风险导向判断。只有冲突提交需要审查、diff 的并集自动安全、import 闭包外自动免审，均不采用。

13.5 按授权发请求，读回实际结果

合并前依次核对工作流证据、GitHub 原生条件、有效具体确认或有限委托，再取得目标推进占用。请求使用支持的 head SHA 条件；API 成功受理／入队不等于实际合并。[S8]

普通 REST 合并不提供同时锁定任意观测 B 的通用条件。发送前重读也不是跨系统原子保证。要求“只合入精确 B”时，必须使用经过验证、能承担此承诺的服务端机制；没有就关闭该强保证下的自动路径，不能降级后仍称满足。

仓库原生 merge queue 可用时优先评估；它受仓库类型／套餐限制，CI 需处理 merge_group。本地队列用于接收调度，不冒充 GitHub 的服务端队列。[S9]

合并后读取真正的 merge commit 与目标，检查该提交的树而不是已经又前进的最新 main。若与受测 T 不同，保留“代码已合入，但组合证据待核对”，暂停依赖该证据的继续推进；调查后针对差异验证，不自动回滚或删除结果。树相同仅证明代码内容一致，不替代业务判断。

CHAPTER 16G2：接通审核—核实—修复，而不偷偷改流程

16.1 流程版本如何选择

先核对目标项目现行政策、已接受决定及上游模板的适用范围。普通目标采用 coding-workflow@1772cd2c… 时，正式审核为新独立 Codex；有需要处理的 finding 时，再由新 Codex 核事实、新 Claude Code 核影响面，Codex 综合，授权内修复后再独立审查。[S2]

SEC_metrics 的现有接收角色和第三方审查不能被同序悄悄替换。W0 写明采用的具体角色与职责：已有检查覆盖同一风险时复用其任务，不无理由再强制三方签字；修改原有审核分工属于显式政策变更。首版支持一个已采用项目流程，不造任意可拖拽流程引擎。

16.2 转接与运行中投递分开

G2 所需的是“X 本次工作明确完成 → 固定结果 → 填入 Y 的输入 → 启动 Y”。不是向任意正在运行的会话注入消息。中间日志、子代理回复、标题中的 PASS 不触发下一步。

保留完整报告，并以最小结构化字段关联 candidate、verdict、findings、evidence、限制；结构校验不冒充语义证明。格式补正不重跑已结束的副作用任务。新上下文还须核对是否继承作者聊天、自动记忆或隐藏状态，不能只换线程名字。

16.3 修复授权与写入移交

先核实、再决定是否修；默认按现有指令在综合后取得修复确认，也可采用已明确授予的有限自动修复范围。无授权不从只读自行升级。原 finding 不成立时交反证复核同候选，不制造空提交。

若采用上游规定在 Codex 验证会话修复，就验证同一会话后续轮次及工作区变更的能力。不能默认新建替身后仍叫“原会话接续”。不支持的能力显示缺口，只阻塞依赖它的闭环。

对任务实施范围、规范化 machine＋worktree、同源分支发布责任取得后端事务占用。原执行者与后台命令未确认结束时不抢占；只读测试在隔离 checkout 写临时文件，不修改作者现场。

16.4 停止与反复返工

证据分歧按已采用流程最多三轮交换事实；未补齐就保持需要返工，不以模型投票裁决。返工计数只计真正已执行并发布的修复批次，不计重复负面审核与网络重试。

超过三次实际修复时，停止自动堆轮次，生成网页端 GPT 的简化反思待办；这与三轮证据讨论不是同一计数。限额／模型配额不足时停在可恢复位置，不切换收费路径。没有新工作不靠空转保持负责人存活。

CHAPTER 17G3：三种派发、准确会话与通信交付

17.1 派发方式

同工具新会话：独立范围与现场；另一工具新会话：同样独立但换执行器；并入负责人待办：复用原责任及队列，不开启同一工作区的第二个写进程。该方式以后可以有独立顺序 Run，验收点是没有新增竞争会话／并行写轮次，而不是永远只能一个 Run。

每次派发前核对已有任务、产物和实施状态。相同任务或共享现场已有未知尝试时不重派。任务、角色、原生会话与机器分开记录；不能用“最近会话”定位。

17.2 接口路线与能力

Codex 优先核查官方非交互结构化输出，需要控制与批准时使用 App Server；turn/steer 面向匹配的活跃 turn，不匹配时不得悄悄变为启动新 turn。Claude Code 优先核查 -p 的 JSON／stream-json 和指定会话后续轮次；运行中通信优先实测启用消息能力的本机 socket。[S10][S11]

文档提供接口候选，不证明用户安装版本可用。具体命令、认证、session／turn 生命周期和批准由 W4 实测。仅支持创建不推导出支持恢复／中断。关联、可观察、可控制按具体操作开放，新会话握手前不能一律升级为 control。

原有长期会话先关联观察；不为探针重启、迁移或夺取控制。原生批准必须由已接通客户端处理或明确停等，不能自动接受全部请求。认证与订阅适用性单独核对，不假设 CLI 子进程等同于任何 SDK 产品均可沿用订阅。

17.3 消息和产物

消息先按 Issue／角色寻址，实际发送时固定会话和请求；已发送／未知消息不随角色更换静默重定向。发送者来自真实连接，不由模型自报 Owner。原生支持安全接收时点即可，不要求强行打断每个活跃轮次。

消息区分待投递、发送中、送达、暂存、拒绝、未知和回复；socket 连接成功不等于消息送达，Delivered 不等于对方完成。产物另分已登记、已接收、已验证：版本匹配且能读取才接收，经实际消费入口核对才验证。新版本要重核，人工复制只算调试，不算跨工具自动交接通过。

查回原消息后，同一回执更新消息和原 Operation。普通技术讨论不改采用范围；正式范围变化经有效决定写回 Issue 后再采用。必要时一个新调查会话可解释已发布接口，但不能替原写入者报告未提交现场。

20.1 收益怎样判断

用一批明确纳入的实际交付及其观察窗口比较，不承诺一周必然证明长期效果。记录：进入待接收到首次有效反馈的时长；本次有效接收通过到合入的时长；退回原因与重复类别；合入后严重遗漏；人的机械操作、决定次数与等待；新增维护成本。

有效反馈不是“收到”，而是实际接受、明确退回或可执行补证据请求。存在新 head 导致接受失效时，保留每轮事件，不用旧通过时刻掩盖新等待。处理中时间取真实 Run，工作时段由用户规则确定；缺数据时只报告日历时长／未知，不猜“沉默即等待”。

观察覆盖、新计算量、代码合入、正确业务结果和正式采纳分别计数，重复记录按实际对象去重。不用模型说“N 项”作为计数来源；样本范围与缺失数直接从结果取得。

通过的收益信号应同时出现：更多同类问题在提交前被工具发现；交付等待和机械介入下降；严重漏检没有增加。单次看不到严重错误只能说明该观察窗，不是安全率证明。G1 不要求模型间搬运为零；G2 自动链才要求为零。

CHAPTER 22怎样亲自验收：四条现场路径

22.1 G1 接收路径

使用明确批准的测试仓库和至少三类固定候选：普通独立 PR、指向非主干的叠放 PR、需要共享检查的 PR。固定真实目标、输入材料和受管操作范围；不要第一次就在生产 main 故障注入。

先只读导入，核对实际 head/base、旧报告与下一步责任。让两个候选竞争一个接收席位，再让一个因依赖等待，确认必要上游可先行。执行已有可重跑检查；缺一份材料时应显示不完整而不是通过。

在隔离现场生成 B＋H 组合，验证不改作者分支。分别测试：逐次确认模式缺确认拒绝；有限委托模式范围内不重复请示；范围外／已撤销拒绝。失去合并响应后查询原结果，不发第二次请求。实际合入目标和受测对象分别核对。

生产试点先影子对照现有接收者，不中断长期任务。正式接管写入前核对主干资源与凭据，明确旧执行过程已交接。

22.2 G2 审核循环

选一个真实可复现缺陷，在采用流程中完成独立审核、必要两路核实、综合、授权修复与再审。模型没找到预设缺陷就如实失败或未覆盖，不能脚本注入 finding 后声称独立发现。

再用可控响应覆盖无问题 PASS、错误 finding、新证据同 head 重审、Owner 决定、格式错误和限额分支。故障注入只针对测试进程。观察自动链是否还要人复制正文、手填 head 或寻找正确会话。

22.3 G3 三目标协作

使用原产品三个顶层目标覆盖两位 Codex 与一位 Claude 责任，分别用独立同工具、另一工具和并入待办。共同交付不等于强制三份实现。

完成一次真正的跨工具数据包消费；让一个范围决定只阻塞相关任务；将一条独立交付直接合入，另一条确需组合的交付经过集成候选。运行中投递可排到原生安全接收时点，但必须到正确原对象。

中途更换一个已确认退出的执行会话，用 Issue、原 PR、固定材料恢复；不依赖用户重述所有历史。演练未知不能抢占，恢复后不是永久死锁。

由未参与实现的使用者只看三视图，回答第 02 节六个问题；把“已观察／已验证／已合入／已采纳”说清。记录原流程与新流程的机械操作和维护动作，必要决定不被当成应消灭的负担。

升级前停止接新写任务，保存本地数据库与证据引用，核对未完成操作。迁移失败退回只读，不清空现场。退出平台时原 PR、Issue、正式证据仍可用于接手；关键业务结论不能只在同序私有数据库中才能解释。
